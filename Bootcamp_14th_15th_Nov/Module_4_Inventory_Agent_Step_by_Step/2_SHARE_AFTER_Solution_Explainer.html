The finished system in one picture

Data side

SQLite: 3 tables (inventory, lead_time, demand), 10 products. Exact facts.

ChromaDB: 13 short notes (formulas, category rules, best practices), embedded with all-MiniLM-L6-v2. Advice and context.

Brain side

LLM (gpt-6-luna): understands the question, decides which tool to call, writes the answer.

Tools: db_lookup, list_available_skus, compute_stock_metrics. Facts and maths, never guessed.

Golden rule of this design: facts come from the database, maths comes from Python, knowledge comes from retrieval, and the LLM only does the reasoning and the talking.

Step 01 — SQLite basics

Why a SQL database? Stock numbers are exact facts that change every day. They belong in a table, not in a prompt and not in a vector store.

TODO 1 — Write a JOIN query that returns sku_id, sku_name, stock, lead_time_days, supplier_name for every product

Solution for TODO 1
rows = cur.execute("""
    SELECT p.sku_id, p.sku_name, p.stock,
           s.lead_time_days, s.supplier_name
    FROM   products p
    JOIN   suppliers s ON s.sku_id = p.sku_id
    ORDER  BY p.sku_id
""").fetchall()

JOIN ... ON s.sku_id = p.sku_id glues each product row to the supplier row with the same sku_id. p and s are short nicknames for the tables.

TODO 2 — Fetch ONE product (joined with its supplier) by sku_id; return it as a dict, or None if not found

Solution for TODO 2
row = cur.execute(
    "SELECT p.*, s.lead_time_days, s.supplier_name "
    "FROM products p JOIN suppliers s ON s.sku_id = p.sku_id "
    "WHERE UPPER(p.sku_id) = UPPER(?)",
    (sku_id,),
).fetchone()
return dict(row) if row else None

The ? placeholder lets SQLite insert the value safely (never build SQL with f-strings: that opens the door to SQL injection). UPPER(...) on both sides makes the lookup case-insensitive.

Step 02 — Embeddings basics

TODO 1 — Embed the query, score it against every passage, and return the top k

Solution for TODO 1
qv = model.encode(query, normalize_embeddings=True)
scores = passage_vectors @ qv              # one score per passage
ranked = np.argsort(scores)[::-1][:k]      # biggest first
return [(float(scores[i]), PASSAGES[i]) for i in ranked]

normalize_embeddings=True makes every vector length 1. Then cosine similarity is just the dot product, and passage_vectors @ qv scores all six passages in one line (a 6×384 matrix times a 384 vector = 6 scores). np.argsort gives positions sorted from smallest to largest, so [::-1] flips it to largest first.

QuestionExpected #1 passage
How do I calculate safety stock?Safety Stock = Z-score * demand_std_dev * sqrt(lead_time_days)
What should I know about electronics inventory?Electronics: lead times 14-30 days, high obsolescence risk.
Tell me about demand patterns for consumer goods.FMCG: short lead times 3-7 days, high steady demand.

The third one is the interesting one: the question says consumer goods, the passage says FMCG, and no words overlap. The embedding model still knows they mean the same thing. (Exact scores vary slightly between machines.)

Step 03 — ChromaDB retrieval

Step 02 kept vectors in a numpy array. A vector database stores the text, the vector and tags together, searches fast even with millions of rows, and can filter by tag.

TODO 1 — Embed every text and add ids, vectors, texts and metadata to the collection

Solution for TODO 1
vectors = embed.embed_documents([d["text"] for d in docs])
collection.add(
    ids=[d["id"] for d in docs],
    embeddings=vectors,
    documents=[d["text"] for d in docs],
    metadatas=[d["meta"] for d in docs],
)

Four parallel lists, matched by position: the 1st id goes with the 1st vector, the 1st text and the 1st tag.

TODO 2 — Embed the query and search the collection (apply the filter only if one is given)

Solution for TODO 2
qv = embed.embed_query(query)
kwargs = {"query_embeddings": [qv], "n_results": n}
if where:
    kwargs["where"] = where
results = collection.query(**kwargs)
return results["documents"][0]

where={"topic": "formula"} works like SQL WHERE topic = 'formula': Chroma searches by meaning, but only inside matching rows. The results come back as a list per query, so ["documents"][0] takes the first (and only) query's list.

Output (real run; the order of the two lines may differ)

Step 04 — Your first LLM chain

TODO 1 — Build the chain: prompt -> llm -> StrOutputParser

Solution for TODO 1
chain = prompt | llm | StrOutputParser()

Read the pipe | as "then": fill the prompt, then send it to the LLM, then turn the reply into a plain string. This is LangChain's LCEL (LangChain Expression Language).

TODO 2 — Run the chain with this SKU's parameters and print the result

Solution for TODO 2
result = chain.invoke(params)

invoke(params) fills {sku_id}, {lead_time_days} and the other blanks from the dict keys with the same names.

Example output for SKU-001 (the LLM's working varies; the Python check line is exact)
Safety Stock = 2.05 × 2 × √21 ≈ 2.05 × 2 × 4.583 ≈ 18.79
Desired Stock = (8 × 21) + 18.79 = 168 + 18.79 = 186.79

DESIRED_STOCK: 186.79

[Python check] safety stock = 18.79, desired stock = 186.79
The lesson of this step

The LLM usually gets close, but square roots and decimals are where it slips (for example writing √21 ≈ 4.6 and ending at 186.86). For inventory, money or medicine, "usually close" is not acceptable. That is why Step 06 moves every calculation into Python tools.

Step 06 — Tool calling with an agent loop

TODO 1 — One turn of the agent loop

Solution for TODO 1
response = llm.invoke(messages)
messages.append(response)

# No tool calls -> the LLM is ready to answer
if not response.tool_calls:
    return response.text  # .text = the answer as plain text

# Run every tool the LLM asked for, then go round the loop again
for tc in response.tool_calls:
    result = TOOL_MAP[tc["name"]].invoke(tc["args"])
    print(f"  [tool] {tc['name']}({tc['args']}) -> {result}")
    messages.append(ToolMessage(content=json.dumps(result), tool_call_id=tc["id"]))

Each trip round the loop is one "think → act → observe" cycle. The loop ends when the LLM replies with no tool calls (it has everything it needs). json.dumps turns the Python result (a dict or a number) into text, because messages carry text.

Example output (the [tool] lines and numbers are exact; the wording varies)
Q: Does SKU-005 need to be reordered? Show the reorder point.
  [tool] lookup_sku_stock({'sku_id': 'SKU-005'}) -> {'sku_id': 'SKU-005', 'sku_name': 'Laptop 15-inch', 'current_stock': 50, 'avg_daily_demand': 3, 'demand_std_dev': 1.0, 'lead_time_days': 30, 'service_level': 99}
  [tool] calculate_safety_stock({'demand_std_dev': 1.0, 'lead_time_days': 30, 'service_level_pct': 99}) -> 12.76
  [tool] calculate_reorder_point({'avg_daily_demand': 3, 'lead_time_days': 30, 'safety_stock': 12.76}) -> 102.76
A: Yes. SKU-005 (Laptop 15-inch) has 50 units, below its reorder point of 102.76 units
   (3/day × 30 days + 12.76 safety stock). Reorder now.

Notice the LLM chained the tools: it used the output of lookup_sku_stock as the input of calculate_safety_stock, then used that result in calculate_reorder_point. Three loop rounds, then the answer. Sometimes the LLM asks for two tools in the same round; the inner for loop handles that.

A second prompt with a {computation} slot. Whatever chain 1 writes is pasted there.

Step 08 — The full agent app

TODO 1 — Write the compute_stock_metrics tool (exact maths for one SKU)

Solution for TODO 1
@tool
def compute_stock_metrics(avg_daily_demand: float, demand_std_dev: float, lead_time_days: float,
                          service_level_pct: float, current_stock: float) -> dict:
    """
    Compute safety stock, desired stock level, and reorder quantity with exact arithmetic.
    Returns: z_score, safety_stock, desired_stock, reorder_quantity, reorder_needed.
    """
    z = Z_TABLE.get(round(service_level_pct), 1.65)
    safety_stock = round(z * demand_std_dev * math.sqrt(lead_time_days), 2)
    desired_stock = round(avg_daily_demand * lead_time_days + safety_stock, 2)
    reorder_quantity = max(0, math.ceil(desired_stock - current_stock))
    return {
        "z_score": z,
        "safety_stock": safety_stock,
        "desired_stock": desired_stock,
        "reorder_quantity": reorder_quantity,
        "reorder_needed": reorder_quantity > 0,
    }

One tool does all the maths for a SKU and returns everything as a dict. math.ceil rounds up, because you cannot order 36.79 headphones, and rounding down would leave you short.

Things to notice in the code
  • check_same_thread=False: Gradio answers each chat message in a worker thread, and SQLite would otherwise refuse to be used from a different thread.
  • chat_handler catches errors and shows a friendly message instead of crashing the app.
  • Every question is answered on its own (the chat history is not sent to the LLM). Making it remember is a stretch challenge.

Answers to "Think about it"

1. Did the LLM's number match the Python check?

Often close, sometimes off in the decimals, occasionally clearly wrong. LLMs predict likely text; they do not calculate. A small error times hundreds of SKUs means real money: lost sales or cash stuck in stock. Exact maths belongs in code.

2. What could only come from the retrieved notes?

Our business rules: "Pharma: 99%+ service level, strict FIFO, expiry dates" and the exact Z values. A general LLM may know similar ideas, but it cannot know your company's rules unless you give them.

3. Agent vs pipeline advantages?

Agent: flexible, handles questions you did not plan for. Pipeline: predictable, easy to test, fixed cost. Many real systems use a pipeline for the core flow and an agent only at the edges.

4. Why MAX_STEPS?

If the LLM keeps asking for tools (for example, a tool keeps returning an error and the LLM keeps retrying), the loop would never end, burning money and time. A step limit is a simple safety net.

5. Why only 3 notes, not all 13?

Fewer tokens = cheaper and faster. Irrelevant notes can also distract the LLM. With 13 notes you could send all of them, but a real knowledge base has thousands, so retrieval is the habit to build.

6. SKU-009 with 120 in stock and a desired stock of 119.14?

The formula says no reorder, but there is less than one unit of margin. A manager would want: upcoming sales or festival season, supplier reliability, minimum order size, and whether an order is already on its way. Tools give exact numbers; people still make the judgement call.

Common errors and fixes

You seeFix
sqlite3.OperationalError: no such columnCheck the column names and the table nicknames (p. / s.) in your SQL.
chromadb ... Collection inventory_kb already existsOnly happens if you run the creation twice in one session (for example in a notebook). Use client.get_or_create_collection(...), or restart.
KeyError: 'rag_context' or a missing {...} variableEvery {name} in a prompt must be a key in the dict you pass to invoke.
The agent answers without calling toolsMake the tool docstrings clearer and keep the system prompt rule "never do the maths yourself".
SQLite objects created in a thread can only be used in that same threadKeep check_same_thread=False in Step 08.
"Stopped: too many steps"The LLM kept calling tools. Print the [tool] lines to see which one keeps failing.
