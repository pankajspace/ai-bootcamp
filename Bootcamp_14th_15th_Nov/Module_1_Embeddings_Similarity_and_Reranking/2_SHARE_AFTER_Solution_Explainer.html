The big idea in one picture

Computers compare numbers, not meanings. So we first turn text into numbers that capture meaning, and then compare the numbers.

Text"I want a refund"
→
Embedding modellearned from lots of text
→
Vector[0.12, -0.53, 0.88, ...]
→
Comparecosine similarity

Everyday analogy: think of each sentence as a pin on a giant map of meanings. "Train ticket refund" and "cancel my IRCTC booking" land close together. "Recipe for paneer tikka" lands far away. Search becomes: find the pins nearest to the question's pin.

1.1 Word embeddings

We used GloVe vectors: 400,000 English words, each stored as 50 numbers. They were learned from Wikipedia and news text, so words used in similar sentences end up with similar numbers.

If you build the vector yourself and search with it, the closest word is king, because the result is still very close to where we started. most_similar(positive=..., negative=...) automatically skips the input words.

TODO 4 — Write a cosine_similarity(a, b) function using numpy

Solution for TODO 4
def cosine_similarity(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
Output (real run)
   king vs queen     -> my answer: 0.784 | gensim: 0.784
cricket vs football  -> my answer: 0.696 | gensim: 0.696
   king vs banana    -> my answer: 0.221 | gensim: 0.221

Reading the formula: np.dot(a, b) is large when the two lists of numbers go up and down together. Dividing by the two lengths (np.linalg.norm) removes the effect of size, so we only measure direction. The result is between −1 and 1: near 1 = same meaning, near 0 = unrelated.

1.2 Similarity search app

Now we embed whole sentences instead of single words. The model sentence-transformers/all-MiniLM-L6-v2 is small (about 90 MB), free, runs on a laptop CPU, and turns any sentence into 384 numbers.

TODO 1 — Write the cosine similarity formula

Solution for TODO 1
def cosine_similarity(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

The same formula you wrote in 1.1. We wrap the answer in float() so Gradio shows a normal number.

TODO 2 — Embed all documents and the query

Solution for TODO 2
doc_embeddings = model.encode(docs)
query_embedding = model.encode([query.strip()])[0]

model.encode takes a list of texts and returns one row of 384 numbers per text. We pass the query as a list of one item and take row [0].

TODO 3 — Score every document against the query and sort best-first

Solution for TODO 3
scores = [(doc, cosine_similarity(query_embedding, emb)) for doc, emb in zip(docs, doc_embeddings)]
scores.sort(key=lambda pair: pair[1], reverse=True)

zip pairs each document with its vector. The lambda pair: pair[1] tells sort to sort by the score, and reverse=True puts the biggest score first.

1.3 Retrieve, then rerank

Bi-encoder (Step 1)

Embeds the query and each document separately, then compares vectors. Document vectors can be computed once and stored in a vector database, so searching millions is fast. But the model never sees the query and the document together.

Cross-encoder (Step 2)

Reads (query, document) as one input and outputs a relevance score. Much more accurate, because every word of the query can be matched against every word of the document. But nothing can be pre-computed, so it is slow. Use it only on the top K.

Analogy: hiring for a job. Step 1 is the resume filter that scans 5,000 resumes in seconds and keeps 20. Step 2 is the interview: slow and careful, but you only do it for those 20.

TODO 1 — Embed the documents and the query, score them with cosine similarity, sort, keep top k

Solution for TODO 1
doc_embeddings = bi_encoder.encode(documents)
query_embedding = bi_encoder.encode([query])
scores = cosine_similarity(query_embedding, doc_embeddings)[0]

pairs = list(zip(documents, scores))
pairs.sort(key=lambda pair: pair[1], reverse=True)
return pairs[:k]

scikit-learn's cosine_similarity(A, B) compares every row of A with every row of B. With one query row we get one list of scores, hence [0].

TODO 2 — Score every (query, document) pair with the cross-encoder and sort best first

Solution for TODO 2
pairs = [(query, doc) for doc in documents]
scores = cross_encoder.predict(pairs)

ranked = list(zip(documents, scores))
ranked.sort(key=lambda pair: pair[1], reverse=True)
return ranked

The cross-encoder model cross-encoder/ms-marco-MiniLM-L6-v2 was trained on MS MARCO, a large set of real web search questions with the passages that answered them. Its scores are not between 0 and 1. They can be negative. Only the order matters: bigger = more relevant.

What you should see

  • Before reranking: short sentences that simply repeat the query words (COVID-19 has many symptoms., COVID-19 symptoms are bad.) score near the top, even though they tell you nothing.
  • After reranking: the sentences that actually list symptoms (fever, chills, cough, loss of smell) move to the top. The Dementia sentence stays near the bottom.

Scores differ slightly by machine. Look at how the order changes.

Design choice in this app

The Rerank button reranks exactly the rows shown in the Top-K table (the table is an input to on_rerank). So if you change K and retrieve again, the reranker works on the new list. If you click Rerank first, the app shows a friendly error.

Answers to "Think about it"

1. Why does the raw vector search return king?

king − man + woman moves the vector only a little, so it is still very close to king. A plain nearest-neighbour search does not know which words you started from. most_similar(positive, negative) removes the input words from the answers.

2. Why cosine similarity instead of subtracting the numbers?

Cosine measures the direction of the vectors and ignores their length. A long sentence and a short sentence about the same thing point the same way but can have very different lengths. Direction is what carries meaning.

3. Why not run the cross-encoder on all documents?

It has to run the full model once per (query, document) pair, every time a user asks something. One million documents would mean one million model runs per question. The bi-encoder's document vectors are computed once and reused, so retrieval takes milliseconds.

4. Did the reranker push down the "COVID-19 causes memory loss" sentence?

Look at where it landed: it usually does not sink to the bottom, because it looks like an answer to "COVID-19 symptoms" (right topic, right shape). A reranker judges relevance, not truth. Checking facts needs trusted sources, which is why RAG systems care so much about what goes into the knowledge base.

5. K = 2: can the reranker still find the best document?

Only if the best document is already in the top 2 of Step 1. The reranker can only re-order what retrieval gives it. In practice we retrieve more (for example 20–50) and rerank down to the best 3–5.
