The whole talk in one picture

A language model forgets everything the moment it finishes answering. Memory is everything your agent stores and brings back so it can follow a conversation (short-term) and know its users, facts and skills across days and weeks (long-term: semantic, episodic and procedural).

Part 1

Why agents need memory

Slide 1

Adding memory to your agents: making agents remember and evolve

by Shivank Agarwal

💡 In simple words

A model answers each message as if it has never seen you before. Memory is what your agent saves and brings back: what was said a minute ago, who the user is, what's true about your business, what happened last time, and how to do a task well. With memory, an agent can remember (continuity) and evolve (get better with experience).

🍛 Analogy

Your regular chai-wala remembers that you take less sugar, that you were travelling last week, and how to make your usual just right. A new stall forgets you every morning. Memory turns the new stall into the regular one.

▢ What the slide shows

An agent in the centre, connected to four parts: model, memory, tools, and planning and reasoning.

💡 Each part in one line

  • Model: understands the request and writes the answer.
  • Tools: fetch real data and take real actions (previous lecture).
  • Memory: keeps what the agent has seen and learned, and brings back the right bits at the right time (this lecture).
  • Planning & reasoning: decides the next step.

Slide 4

Why do LLM applications need memory?

▢ What the slide says

  • LLMs are stateless.
  • Stateless bots forget past turns and need repeated clarifications.
  • Memory enables: context continuity, personalization, and richer dialog (referring to the past).
  • Real-world agents have memory modules built in.

💡 "Stateless" in plain words

Each call to a model is a fresh start: it gets the text you send, writes a reply, and keeps nothing. If a chatbot seems to remember, it's because the app sends the earlier messages along again every time. That re-sending is the simplest form of memory.

⌨️ Try it in code: forgetting vs remembering

m04_stateless.pyNeeds OpenAI key
"""An LLM API call remembers nothing. Memory = sending the history again."""
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()


def ask(messages):
    reply = client.chat.completions.create(model="gpt-6-luna", reasoning_effort="none", messages=messages)
    return reply.choices[0].message.content


print("--- Two separate calls (no memory) ---")
print("A:", ask([{"role": "user", "content": "Hi, I'm Priya. I'm vegetarian and I live in Pune."}]))
print("A:", ask([{"role": "user", "content": "Suggest a dinner place for me tonight."}]))

print("\n--- Same questions, history sent along (short-term memory) ---")
history = [{"role": "user", "content": "Hi, I'm Priya. I'm vegetarian and I live in Pune."}]
history.append({"role": "assistant", "content": ask(history)})
history.append({"role": "user", "content": "Suggest a dinner place for me tonight."})
print("A:", ask(history))

--- Two separate calls (no memory) ---
A: Hi Priya, nice to meet you! Pune has a great vegetarian food scene. How can I help you today?
A: Happy to help! Which city are you in, and what kind of food do you like? Then I can suggest
a few places for tonight.

--- Same questions, history sent along (short-term memory) ---

Same model, same question. The only difference is whether the earlier message was sent along. That's "context continuity" and "personalization" in four lines of code.

🌍 Real world

Chat assistants such as ChatGPT and Claude now offer memory that carries facts you've shared across conversations. Customer-support bots look up your past tickets before replying. Coding assistants remember your project's conventions.

Slide 6

Writing memory: hot path vs in the background

▢ What the slide shows

Two timelines. Hot path: user message → update memory → AI response, every turn. In the background: user message → AI response, repeated; then, say 30 minutes later, a separate update of memory. Key trade-off: real-time vs computational efficiency.

🔥 Hot path
User message
Update memory
AI response
User message
Update memory
AI response

✅ Memory is fresh at once · ❌ every reply is slower and costs an extra model call

🌙 In the background
User message
AI response
User message
AI response
⏱ 30 min later
Update memory (one batch)

✅ Fast replies, fewer calls · ❌ new facts aren't saved until later

⌨️ Try it in code: the same chat, both ways

m06_hot_vs_background.pyNeeds OpenAI key
"""Writing memory: in the hot path (every turn, before replying) vs in the background (later, in one batch)."""
import json
import time

from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

load_dotenv()
llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
extractor = llm.bind(response_format={"type": "json_object"})

EXTRACT = ('Extract lasting facts about the user from these messages as JSON: {{"facts": ["..."]}}. '
           'Only facts worth remembering for future chats. Messages:\n{messages}')

chat = ["I'm planning a trip to Rishikesh with my parents next month.",
        "My mother can't climb stairs, by the way.",
        "Which area should we stay in?"]

print("=== HOT PATH: update memory inside every turn ===")
memory, start = [], time.perf_counter()
for msg in chat:
    t0 = time.perf_counter()
    facts = json.loads(extractor.invoke(EXTRACT.format(messages=msg)).text)["facts"]   # extra call BEFORE replying
    memory += facts
    reply = llm.invoke(f"Known about the user: {memory}\nUser: {msg}").text
    print(f"user: {msg}\n   memory now: {memory}\n   reply waited {time.perf_counter() - t0:.1f}s")
print(f"total {time.perf_counter() - start:.1f}s\n")

print("=== BACKGROUND: reply now, update memory later in one batch ===")
start = time.perf_counter()
for msg in chat:
    t0 = time.perf_counter()
    reply = llm.invoke(f"User: {msg}").text                                            # no memory work here
    print(f"user: {msg}\n   reply waited {time.perf_counter() - t0:.1f}s")
facts = json.loads(extractor.invoke(EXTRACT.format(messages="\n".join(chat))).text)["facts"]   # e.g. 30 min later
print(f"later, one batch job saved: {facts}")
print(f"total {time.perf_counter() - start:.1f}s")

   memory now: ['Planning a trip to Rishikesh with their parents next month']
   reply waited 2.1s
user: My mother can't climb stairs, by the way.
   memory now: ['Planning a trip to Rishikesh with their parents next month', "User's mother can't climb stairs"]
   reply waited 1.9s
user: Which area should we stay in?
   memory now: ['Planning a trip to Rishikesh with their parents next month', "User's mother can't climb stairs"]
   reply waited 2.3s
total 6.3s

=== BACKGROUND: reply now, update memory later in one batch ===

   reply waited 1.2s
user: My mother can't climb stairs, by the way.
   reply waited 1.1s

Both saved the same two facts. The hot path made every reply about a second slower; the background job made one extra call at the end. Inside this conversation the chat history still carries the facts either way; what's delayed is them reaching future conversations.

🍛 Analogy

A shopkeeper who writes each sale in the ledger before serving the next customer (hot path) versus one who serves everyone and updates the ledger at closing time (background).

Part 2

Short-term memory

Slide 8

Short-term memory

▢ What the slide says

  • Short-term memory (thread-scoped) keeps the ongoing conversation history within a session.
  • In LangGraph it is managed as the agent's state.
  • State includes the conversation history, uploaded files, retrieved documents and generated artifacts.
  • Persistence: state is saved to a database by a checkpointer, so a thread can be resumed.
  • Update cycle: memory updates when the graph is invoked or a step completes.
  • Usage: state is read at the start of each step for continuity.

💡 New words

  • Thread: one conversation, identified by a thread_id. Two users chatting = two threads, each with its own memory.
  • State: everything the agent is carrying for this thread right now (messages, files, results).
  • Checkpointer: saves the state after every step, like an auto-save. Come back tomorrow with the same thread_id and the conversation continues.

⌨️ Try it in code: two threads, one checkpointer

m08_checkpointer.pyNeeds OpenAI key
"""Short-term memory in LangGraph: the state is saved per thread by a checkpointer."""
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, MessagesState, StateGraph

load_dotenv()
llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")


def chatbot(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}     # the whole thread history goes to the model


builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
graph = builder.compile(checkpointer=InMemorySaver())       # saves the state after every step

ravi = {"configurable": {"thread_id": "ravi-chat"}}
meera = {"configurable": {"thread_id": "meera-chat"}}

graph.invoke({"messages": [("user", "Hi, I'm Ravi. My order number is 4471.")]}, ravi)
print("Ravi, same thread :", graph.invoke({"messages": [("user", "What's my order number?")]}, ravi)["messages"][-1].text)
print("Meera, new thread :", graph.invoke({"messages": [("user", "What's my order number?")]}, meera)["messages"][-1].text)

saved = graph.get_state(ravi).values["messages"]
print(f"\nSaved in thread 'ravi-chat': {len(saved)} messages")
for m in saved:
    print(f"  {m.type:>5}: {m.text[:70]}")
Example output (what you would see; exact text and numbers vary)
Ravi, same thread : Your order number is 4471.
Meera, new thread : I don't have your order number yet. Could you share it, along with the name or
email used for the order?

Saved in thread 'ravi-chat': 4 messages
  human: Hi, I'm Ravi. My order number is 4471.
     ai: Hi Ravi! Thanks for sharing your order number, 4471. How can I help you with it today?
  human: What's my order number?
     ai: Your order number is 4471.

Ravi's thread remembers his order number; Meera's brand-new thread doesn't. Nobody wrote any "save" or "load" code: the checkpointer stored the state after each step and loaded it on the next call with the same thread_id. In production, swap InMemorySaver for a database-backed checkpointer (for example PostgreSQL) so threads survive restarts.

🍛 Analogy

WhatsApp chats: each contact has its own chat (thread). Open any chat and the old messages are still there (checkpointer). Your messages with Ravi don't appear in your chat with Meera.

Slide 9

Managing short-term memory: trimming and deleting

▢ What the slide shows

Trim messages
Remove the first or last N messages before calling the LLM. The code uses trim_messages(state["messages"], strategy="last", token_counter=count_tokens_approximately, max_tokens=128, start_on="human", end_on=("human", "tool")).
Delete messages
Remove messages from LangGraph state permanently. The code returns RemoveMessage(id=m.id) for the earliest two messages.

💡 Why we need this at all

Every message in the history is sent again on every call. A long chat means more tokens (more cost), slower replies, and eventually hitting the model's context limit. So we keep the history small.

Trimming changes only what the model sees this time; the saved history stays complete. Deleting changes what is saved.

⌨️ Try it in code: both techniques on one conversation

m09_trim_delete.pyRan it ✓ real output below
"""The slide's two techniques on a saved conversation: trim before calling the model, delete from state."""
from langchain_core.messages import AIMessage, HumanMessage, RemoveMessage, trim_messages
from langchain_core.messages.utils import count_tokens_approximately
from langgraph.graph.message import add_messages

conversation = [
    HumanMessage("Hi, I'm Kabir. I need a laptop for college, budget ₹60,000."),
    AIMessage("Hi Kabir! For ₹60,000, good options are thin-and-light laptops with 16 GB RAM and an SSD."),
    HumanMessage("I also edit videos sometimes. Does that change anything?"),
    AIMessage("Yes. For video editing, prefer a dedicated GPU and at least 16 GB RAM; battery life will be lower."),
    HumanMessage("Which is more important for editing, RAM or GPU?"),
    AIMessage("For 1080p editing, 16 GB RAM matters most; the GPU speeds up exports and effects."),
    HumanMessage("Okay. So what should I buy?"),
]


def show(title, messages):
    print(f"{title} ({len(messages)} messages, ~{count_tokens_approximately(messages)} tokens)")
    for m in messages:
        print(f"   {m.type:>5}: {m.content[:60]}")


show("FULL HISTORY", conversation)

# 1. TRIM: what the model sees this turn (the saved history is NOT changed)
trimmed = trim_messages(
    conversation,
    strategy="last",                          # keep the newest messages
    token_counter=count_tokens_approximately,
    max_tokens=80,
    start_on="human",                         # kept part must start with a user message
    end_on=("human", "tool"),                 # ...and end with one (the question to answer)
)
show("\nTRIMMED for this model call", trimmed)

# 2. DELETE: remove messages from the agent's state for good
state = add_messages([], conversation)        # LangGraph gives every message an id
state = add_messages(state, [RemoveMessage(id=m.id) for m in state[:2]])   # remove the earliest two
show("\nSTATE after deleting the earliest two", state)

⌨️ Try it in code: the flowchart as a LangGraph agent

m10_summarize_graph.pyNeeds OpenAI key
"""The slide's flowchart in LangGraph: when the history gets long, summarise it and delete the old messages."""
from dotenv import load_dotenv
from langchain_core.messages import RemoveMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, MessagesState, StateGraph

load_dotenv()
llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
THRESHOLD = 6           # summarise once there are more than 6 messages


class State(MessagesState):
    summary: str        # the running summary, stored next to the messages


def chat(state: State):
    context = [SystemMessage(f"Summary of earlier conversation: {state['summary']}")] if state.get("summary") else []
    return {"messages": [llm.invoke(context + state["messages"])]}


def should_summarize(state: State):
    return "summarize" if len(state["messages"]) > THRESHOLD else END     # "count >= threshold?"


def summarize(state: State):
    prompt = (f"Current summary: {state.get('summary', 'none')}\n"
              "Extend it with the new messages above. Keep names, numbers and decisions. 3 sentences max.")
    summary = llm.invoke(state["messages"] + [("user", prompt)]).text
    old = [RemoveMessage(id=m.id) for m in state["messages"][:-2]]           # "clear old messages", keep the last 2
    return {"summary": summary, "messages": old}


g = StateGraph(State)
g.add_node("chat", chat)
g.add_node("summarize", summarize)
g.add_edge(START, "chat")
g.add_conditional_edges("chat", should_summarize)
g.add_edge("summarize", END)
graph = g.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "trip"}}
for msg in ["Hi, I'm Neha. Planning 4 days in Kerala in December with my parents.",
            "My father can't walk long distances.",
            "Budget is about ₹80,000 for all three of us.",
            "Should we do a houseboat in Alleppey?",
            "What did I say my budget was, and who is travelling?"]:
    out = graph.invoke({"messages": [("user", msg)]}, cfg)
    print(f"You: {msg}\nBot: {out['messages'][-1].text}\n   [messages kept: {len(out['messages'])}]")
print("\nSaved summary:", graph.get_state(cfg).values.get("summary"))

Slide 11

Short-term memory: limitations and trade-offs

▢ What the slide says

  • Trim too aggressively and you lose context: the model "forgets" earlier information.
  • Summarization can omit subtle details.
  • Deciding when to summarize versus prune is heuristic-based.
  • You must balance recency against importance.
🧪 Trim a conversation yourself

Keep only the last 4 messages. Which important facts survive?

TechniqueGood atRiskUse when
Keep everythingNothing is lostCost and context limitShort chats
TrimmingSimple, free, automaticLoses early facts (name, budget)Only recent turns matter
DeletingPrecise controlYou must decide what's safe to deleteRemoving big tool outputs, sensitive data
SummarizingKeeps the key factsExtra LLM calls; may drop small detailsLong chats where early facts matter

💡 A common, practical combination

Pin the important facts (name, budget, constraints) in long-term memory or a "summary" field, summarise the middle, and keep the last few messages word-for-word. You get recency and importance.

Part 3

Long-term memory

Slide 12

Long-term memory

▢ What the slide says

  • Persistent memory across sessions.
  • Lets the agent "remember" users over time.
  • Needs a backing store plus a retrieval strategy.
  • Remembering birthdays, preferences, history.
  • Examples in AI agents: persisting user profiles, past purchases.

💡 Short-term vs long-term

Short-termLong-term
Lives forOne conversation (thread)Weeks, months, forever
Shared between chats?NoYes: every new chat with this user can use it
LangGraph toolCheckpointer + thread_idStore + namespace (e.g. the user ID)
Example"You just said your budget is ₹60,000""Happy birthday, Ananya! Still vegetarian, right?"

⌨️ Try it in code: a store that outlives the conversation

m12_long_term_store.pyRan it ✓ real output below
"""Long-term memory in LangGraph: a Store shared by ALL threads, organised by namespace (e.g. per user)."""
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()          # in production: a database-backed store such as PostgresStore

# --- Session 1 (Monday): the agent learns things about user u_42 ---
ns = ("u_42", "profile")         # namespace = a folder per user
store.put(ns, "name", {"value": "Ananya"})
store.put(ns, "birthday", {"value": "14 March"})
store.put(ns, "diet", {"value": "vegetarian, no onion or garlic"})
store.put(("u_42", "orders"), "ORD-9001", {"item": "Running shoes", "status": "delivered"})

# --- Session 2 (Friday): a NEW conversation thread, same user ---
print("Profile of u_42:")
for item in store.search(("u_42", "profile")):
    print(f"   {item.key:<9} -> {item.value['value']}   (saved {item.created_at:%d %b %Y})")

print("\nPast orders:", [(i.key, i.value["item"]) for i in store.search(("u_42", "orders"))])
print("Another user's profile:", store.search(("u_77", "profile")), "(nothing leaks between users)")

# Updating a memory overwrites it; deleting forgets it
store.put(ns, "diet", {"value": "vegan"})
store.delete(ns, "birthday")
print("\nAfter update + delete:", {i.key: i.value["value"] for i in store.search(ns)})

Slide 13

Semantic memory: definition

▢ What the slide says

In cognitive science: memory for general knowledge, facts and concepts, not tied to a specific event.

In AI agents: stores domain knowledge (e.g. "Every order must have an order ID, a list of product IDs and a list of shipping IDs") and gives factual grounding for reasoning and dialogue.

Examples: "Refund policy: 30-day window" · "Business hours: 9 AM–6 PM EST" · "Supported currencies: USD, EUR, GBP".

💡 In plain words

Semantic memory is what is true, whether or not you remember when you learned it. You know Delhi is India's capital, but not the day you learned it. For an agent: business rules, product facts, and also facts about a user ("Ananya is vegetarian").

🍛 Analogy

The company handbook on a new employee's desk: rules and facts, no stories.

Slide 14

Semantic memory: why it matters

▢ What the slide says

It gives agents world knowledge beyond what they have experienced, enabling them to answer factual questions, stay consistent in their responses, and reason abstractly over categories.

Slide 15

Semantic memory: representation approaches

▢ What the slide says

  • Symbolic / structured: knowledge graphs (RDF triples, ontologies) and key-value stores.
  • Vector-based: embeddings of factual statements, supporting semantic-similarity queries.
  • Hybrid: a knowledge graph for structure plus embeddings for flexible recall.

💡 New words

  • Triple: a fact as (subject, relation, object), e.g. (Laptop, is_a, Electronics). A knowledge graph is many triples joined up.
  • Ontology: the agreed list of types and relations (e.g. "Product", "Category", "is_a").
  • Embedding: a list of numbers that captures a sentence's meaning, so "How long is shipping?" matches "Delivery takes 2–5 days" even with no shared words.

Slide 17

Semantic memory: usage

▢ What the slide says

  • Retrieve facts relevant to the query. Q: "How long does delivery take?" Semantic memory: "2–5 business days."
  • Guide reasoning. Episodic: "Last order took 7 days." Semantic: "Deliveries usually take 2–5 days."

m17_semantic_plus_episodic.pyNeeds OpenAI key
"""Semantic memory (what is generally true) + episodic memory (what happened to THIS user) in one answer."""
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langgraph.store.memory import InMemoryStore

load_dotenv()
llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
# A store that can search by MEANING: every value's "text" field is embedded
store = InMemoryStore(index={"embed": OpenAIEmbeddings(model="text-embedding-3-small"), "dims": 1536, "fields": ["text"]})

# Semantic memory: company-wide facts
for key, text in [("delivery", "Standard delivery takes 2-5 business days."),
                  ("refunds", "Refunds are allowed within 30 days of delivery."),
                  ("hours", "Customer support is open 9 AM to 6 PM IST, Monday to Saturday.")]:
    store.put(("company", "facts"), key, {"text": text})

# Episodic memory: this user's past experiences
store.put(("u_52", "episodes"), "2026-10-02", {"text": "Order ORD-7712 (a mixer grinder) took 7 days to arrive; user was upset."})
store.put(("u_52", "episodes"), "2026-10-20", {"text": "User asked to change their phone number."})

question = "How long does delivery take?"
fact = store.search(("company", "facts"), query=question, limit=1)[0]
episode = store.search(("u_52", "episodes"), query=question, limit=1)[0]
print(f"Semantic hit (score {fact.score:.2f}): {fact.value['text']}")
print(f"Episodic hit (score {episode.score:.2f}): {episode.value['text']}")

answer = llm.invoke(f"Company fact: {fact.value['text']}\nThis customer's history: {episode.value['text']}\n"
                    f"Customer asks: {question}\nAnswer in 2 sentences, warmly.").text
print("\nAgent:", answer)

Slide 18

Episodic memory: definition

▢ What the slide says

Episodic memory, in both humans and AI agents, means recalling past events or actions. For AI agents it is often used to help the agent remember how it accomplished a task before.

💡 In plain words

Episodic memory is a diary: what happened, when, and how it turned out. "On 3 November I tried the shipping API with order #78910 and it failed." Each entry is an episode.

🍛 Analogy

You remember the time you took the expressway and got stuck in a 2-hour jam, so you take the old highway now. That memory of one specific trip is episodic.

Slide 19

Episodic memory: why it matters

▢ What the slide says

It lets agents reflect on past failures (avoid repeating mistakes), reuse successful strategies (case-based reasoning), and personalise responses based on history.

Key difference: semantic = what is generally true; episodic = what happened in a specific case.

🌍 Real world

  • Avoid failures: a coding agent remembers "running the full test suite timed out last time; run only the changed module's tests".
  • Reuse what worked: a support agent remembers the exact steps that fixed a similar complaint last week.
  • Personalise: "Sorry your last order was late; I've added priority shipping this time."

💡 "Case-based reasoning"

Solving a new problem by finding a similar old case and adapting its solution, like a doctor thinking "this looks like the patient I saw last month".

Slide 21

Episodic memory: storage

▢ What the slide says

  • Relational DB (SQL): an episodes table for metadata (id, user, goal, outcome) and a steps table for detailed actions and results.
  • Document DB (MongoDB, Firestore): each episode as one JSON document, easy to retrieve with filters.
  • Vector DB (FAISS, Pinecone): episode descriptions as embeddings for "similar past situations".

Storing episodes in structured, retrievable formats lets agents search, compare and learn from past experience.

"""Episodic memory in SQL: an episodes table + a steps table, then 'learn from the past' (slides 21-24)."""
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE episodes (episode_id INTEGER PRIMARY KEY, user_id TEXT, goal TEXT, outcome TEXT, created TEXT);
CREATE TABLE steps    (episode_id INTEGER, step_no INTEGER, action TEXT, result TEXT);
""")


def log_episode(user_id, goal, outcome, created, steps):
    eid = db.execute("INSERT INTO episodes (user_id, goal, outcome, created) VALUES (?,?,?,?)",
                     (user_id, goal, outcome, created)).lastrowid
    db.executemany("INSERT INTO steps VALUES (?,?,?,?)", [(eid, i, a, r) for i, (a, r) in enumerate(steps, 1)])

                  ("track_order",)).fetchone()[0]

Slide 24

Episodic memory usage: retrieval and decision

▢ What the slide says

  • Episodic retrieval: a new query → retrieve similar past episodes.
  • Compare outcomes: episode 1 → failure (Tool C path); episode 2 → success (Tool A → Tool B path).
  • Decision: avoid the failed path, follow the successful one.

💡 How this looks in a real agent

  1. New request arrives: "Where's my order #55321?"
  2. Search episodic memory for similar past requests (by goal, as in slide 21's demo, or by meaning with embeddings).
  3. Put the best examples into the prompt: "Past attempt: shipping API first → failed. Past attempt: validate → DB lookup → succeeded."
  4. The model follows the successful pattern. This is often called few-shot learning from experience.

🍛 Analogy

Before a cricket match, the captain watches clips of past games against the same team: which bowlers worked, which field placements failed. Then picks the plan that worked.

⚠️ Careful

One failure doesn't always mean a path is bad: the API might simply have been down that day. Good systems store why it failed, and weigh many episodes, not just the last one.

Slide 25

Procedural memory: definition

▢ What the slide says

In cognitive science: memory for skills, procedures and how to perform actions.

In AI agents: stores policies, workflows or action scripts, and lets the agent repeat learned skills without relearning them.

Analogy: human: "I know how to ride a bike." Agent: "I know how to validate an order ID and fetch its status."

💡 In plain words

Procedural memory is know-how. For an LLM agent it usually takes one of two forms: a stored workflow (step 1, step 2, what to do if step 2 fails), or the agent's own instructions (its system prompt), improved over time from feedback.

⌨️ Try it in code: instructions the agent improves and keeps

m25_learned_instructions.pyNeeds OpenAI key
"""Procedural memory for an LLM agent: its own instructions, improved from feedback and saved for next time."""
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.store.memory import InMemoryStore

load_dotenv()
llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
store = InMemoryStore()
store.put(("agent", "procedures"), "refund_reply", {"instructions": "Reply to refund requests politely."})


def reply(customer_msg):
    steps = store.get(("agent", "procedures"), "refund_reply").value["instructions"]
    return llm.invoke(f"Instructions:\n{steps}\n\nCustomer: {customer_msg}\nReply:").text


def learn(feedback):
    old = store.get(("agent", "procedures"), "refund_reply").value["instructions"]
    new = llm.invoke(f"Current instructions:\n{old}\n\nManager feedback: {feedback}\n"
                     "Rewrite the instructions as a short numbered procedure that includes the feedback. "
                     "Return only the instructions.").text
    store.put(("agent", "procedures"), "refund_reply", {"instructions": new})     # saved: used in every future chat
    return new


msg = "My headphones stopped working after 10 days. I want a refund."
print("BEFORE:\n", reply(msg))
print("\nNEW PROCEDURE:\n", learn("Always ask for the order ID first, mention the 30-day refund window, "
                                  "and offer a replacement before a refund."))
print("\nAFTER:\n", reply(msg))

Slide 27

Procedural memory: representation approaches

▢ What the slide says

  • Symbolic rules / scripts: IF–THEN rules or production rules.
  • Finite state machines (FSMs): state transitions encode the procedural flow.
  • Neural policies: reinforcement-learning agents store action policies.
  • Hybrid: store procedures as symbolic plans, refined with learned policies.
ApproachOrder-tracking example
IF–THEN rulesIF the order ID isn't numeric THEN ask the user to re-check it. IF the DB has no result THEN try the cache.

Readable ones: written workflows, graphs (LangGraph) and instructions in prompts. They're easy to inspect, test and change, which matters when the agent touches real customers' orders.

Slide 29

Procedural memory: usage

▢ What the slide says

  • Retrieve a procedure when the task goal matches.
  • Execute the stored sequence of steps.
  • Adapt if the context differs (branching, retries).

⌨️ Try it in code: retrieve the procedure, run it, adapt with fallbacks

m29_procedural.pyRan it ✓ real output below
"""Procedural memory: a stored, step-by-step procedure the agent retrieves and runs, with a fallback (slide 29)."""
import json
import sqlite3

# --- the systems the procedure uses (small in-memory examples) ---
ORDER_DB = {"ORD-78910": "shipped, arriving Thursday"}            # main database (new orders take time to sync)
ORDER_CACHE = {"ORD-55321": "packed, leaves warehouse today"}     # cached copy, updated every few minutes
SHIPPING_API = {"ORD-60012": "out for delivery"}                  # courier partner


def validate_id(raw):    return f"ORD-{raw.strip('#')}" if raw.strip("#").isdigit() else None
def order_db(oid):       return ORDER_DB.get(oid)
def cached_db(oid):      return ORDER_CACHE.get(oid)
def shipping_api(oid):   return SHIPPING_API.get(oid)


ACTIONS = {"validate_id": validate_id, "order_db": order_db, "cached_db": cached_db, "shipping_api": shipping_api}

# --- procedural memory, stored as a JSON workflow in a database ---
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE procedures (goal TEXT PRIMARY KEY, version INTEGER, steps TEXT)")
db.execute("INSERT INTO procedures VALUES (?, ?, ?)", ("track_order", 2, json.dumps([
    {"do": "validate_id", "on_fail": "stop: ask the user to re-check the order number"},
    {"do": "order_db", "fallbacks": ["cached_db", "shipping_api"]},      # learned: "if DB lookup fails, try cache, then courier"
])))


def run_procedure(goal, user_input):
    version, steps = db.execute("SELECT version, steps FROM procedures WHERE goal = ?", (goal,)).fetchone()
    print(f"Procedure '{goal}' v{version} for input {user_input!r}")
    value = user_input
    for step in json.loads(steps):
        for action in [step["do"]] + step.get("fallbacks", []):
            result = ACTIONS[action](value)
            print(f"   {action:<13} -> {result if result else 'no result'}")
            if result:
                value = result
                break
        else:
            return step.get("on_fail", "stop: not found anywhere, hand over to a human agent")
    return f"Status: {value}"


for order in ["#78910", "#55321", "#60012", "#7A91"]:
    print("  =>", run_procedure("track_order", order), "\n")

1. If the model is stateless, how does ChatGPT "remember" what you said earlier in the same chat?

The app sends the earlier messages along with every new one. That re-sent history is short-term memory.

2. What's the difference between trimming and deleting?

Trimming changes only what the model sees in this call; the saved history is untouched. Deleting removes messages from the saved state permanently.

3. Your agent keeps forgetting the user's budget in long chats. Trimming is on. What would you change?

Summarize instead of (or as well as) trimming, or save the budget to long-term memory as a fact about the user, so it doesn't depend on the old message still being in the window.

4. Classify: (a) "Delivery takes 2–5 days", (b) "Order #4471 arrived late last month", (c) "Validate the ID before calling the DB".

(a) Semantic: a general fact. (b) Episodic: a specific past event. (c) Procedural: how to act.

5. Hot path or background: a voice assistant where every second of delay is noticeable?

Background. Reply first; extract and save memories afterwards, so the user never waits for memory work.
