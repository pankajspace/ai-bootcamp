Part 1

Why observability

Slide 1

Beyond monitoring: what is LLM observability?

Subtitle: Understanding AI agent systems through exploration rather than predefined metrics · by Shivank Agarwal

💡 In simple words

Normal software is predictable: the same input gives the same output, so a few fixed health checks are enough. AI agents are different: they think in steps, call tools, and can answer differently each time. When something goes wrong you need to look inside and ask questions you didn't plan for. That ability is observability.

🍛 Analogy

A car's dashboard warning light (monitoring) tells you something is wrong. A mechanic's diagnostic scanner plugged into the engine (observability) lets you find out what and why, even for a problem the car maker never anticipated.

🌍 Why learners should care

Every company putting AI agents in front of customers hits the same wall: "users say the bot gave a wrong answer, and we can't see why." Knowing how to trace and debug agents is now a core skill for AI engineers and forward-deployed engineers.

Slide 2

What is observability?

Monitoring checks known things. Observability helps you discover unknown things.

▢ What the slide says

Monitoring is question-driven
"Is the system up?" · "Is CPU usage below 80%?" · It checks known, pre-defined metrics.
Observability is exploration-driven
"Why is user satisfaction dropping for users in Europe?" · "What caused the agent to give a wrong answer?" · The ability to understand a system's internal state from its outputs, asking new questions without writing new code.

For AI agents: it's your debugger for a non-deterministic, reasoning system.

💡 In simple words

  • Monitoring = alarms you set up in advance. Great for problems you already know about.
  • Observability = recording enough detail about every request that, when a new problem appears, you can investigate it by slicing the data you already have, without shipping new code first.

🍛 Analogy

A smoke alarm (monitoring) only beeps. CCTV footage plus the kitchen logbook (observability) let you replay the evening and find out who left the gas on.

⌨️ Try it in code: the same data, two kinds of questions

r02_monitoring_vs_observability.pyRan it ✓ real output below
# Monitoring asks a FIXED question. Observability lets you ask NEW questions of the same data.
import pandas as pd

# One row per chatbot answer, exactly as your app would record it
logs = pd.DataFrame([
    {"region": "India",  "prompt_version": "v1", "latency_s": 1.9, "thumbs_up": 1},
    {"region": "India",  "prompt_version": "v2", "latency_s": 2.1, "thumbs_up": 1},
    {"region": "Europe", "prompt_version": "v1", "latency_s": 2.0, "thumbs_up": 1},
    {"region": "Europe", "prompt_version": "v2", "latency_s": 2.2, "thumbs_up": 0},
    {"region": "Europe", "prompt_version": "v2", "latency_s": 2.4, "thumbs_up": 0},
    {"region": "US",     "prompt_version": "v2", "latency_s": 1.8, "thumbs_up": 1},
    {"region": "Europe", "prompt_version": "v2", "latency_s": 2.3, "thumbs_up": 0},
    {"region": "India",  "prompt_version": "v1", "latency_s": 1.7, "thumbs_up": 1},
    {"region": "US",     "prompt_version": "v1", "latency_s": 1.9, "thumbs_up": 1},
    {"region": "Europe", "prompt_version": "v1", "latency_s": 2.1, "thumbs_up": 1},
])

# MONITORING: a fixed check that someone wrote in advance
satisfaction = logs["thumbs_up"].mean()
print(f"Monitoring check: satisfaction = {satisfaction:.0%} (alert below 80%) ->",
      "ALERT" if satisfaction < 0.8 else "OK")

# OBSERVABILITY: a brand-new question, answered from the same data
print("\nExploring 'why?': satisfaction by region and prompt version")
print(logs.groupby(["region", "prompt_version"])["thumbs_up"].mean().unstack())

region                  
Europe          1.0  0.0

The monitoring check only says "satisfaction is low". Because each answer was saved with its region and prompt version, one new question finds the cause: prompt v2 fails only in Europe. No new code was shipped to find that.

⚠️ Careful

"Without writing new code" only works if you recorded the right details up front (region, prompt version, model, user type…). Rich data at capture time is what makes later exploration possible.

Slide 3

From prototype to production: why observability is a must

"It works sometimes" is fine for a demo, not for customers.

▢ What the slide says

Agents shift from "cool demo" to "mission-critical" once they handle customer data, money or important decisions. Key drivers:

DriverMeaning
Reliability & trustThe agent completes tasks correctly and reliably.
Cost controlLLM calls are expensive; inefficient agents burn money.
User experienceSlow or confusing agents frustrate users and get abandoned.
Continuous improvementYou can't improve what you can't measure.

🍛 Analogy

Cooking for friends at home (prototype) vs running a restaurant on Zomato (production). Now you need the same taste every time, food cost under control, quick delivery, and you read every review to improve. You can't do any of that without tracking what happens in the kitchen.

🌍 Real world

A support agent that resolves 90% of tickets in testing can quietly drop to 70% after a model update or a changed API. Without observability, the first sign is angry customers. With it, you see the success rate dip on the same day.

Slide 4

The unique challenges of AI agent observability (1–2)

Agents are unpredictable, and they work in many steps.

▢ What the slide says

1. Non-determinism
The same input can produce different outputs, which makes reproducing and debugging issues very hard. Example: "Write a summary" can give a good, bad or hallucinated result on different tries.
2. Multi-step, stateful workflows
Agents don't just answer, they act: one task is a chain of reasoning, tool calls and decisions. A failure in any single step can break the whole process.

💡 In simple words

Non-deterministic means "not the same every time". A normal bug happens every time you repeat the steps; an AI bug might happen once in twenty tries. That's why you must record every real request: you often can't recreate the bad one later.

🍛 Analogy

Asking three friends to summarize the same cricket match: you get three different summaries, and one of them adds a wicket that never happened. And a multi-step agent is like a relay race: if one runner drops the baton, the whole team loses, so you need to see every leg.

⌨️ Try it in code: same prompt, three answers

s04_non_determinism.pyNeeds OpenAI key
# Non-determinism: the SAME prompt can give DIFFERENT answers.
from openai import OpenAI

client = OpenAI()
prompt = "Summarize in one line: Our Q3 sales in India rose 12% during the festive season."

for attempt in range(1, 4):
    reply = client.chat.completions.create(
        model="gpt-6-luna",
        reasoning_effort="none",
        temperature=1.0,                  # normal "creative" setting
        messages=[{"role": "user", "content": prompt}],
    )
    print(f"Try {attempt}: {reply.choices[0].message.content}")
Example output (what you would see; exact text and numbers vary)
Try 1: Festive-season demand drove a 12% jump in our Q3 sales in India.
Try 2: India Q3 sales grew 12%, powered by festive shopping.
Try 3: Q3 sales in India rose 12% thanks to Diwali, led by strong electronics demand.

Look at Try 3: it adds "Diwali" and "electronics demand". Neither was in the input. That's a small hallucination, and it only showed up on one of three tries.

⚠️ Careful

Lowering temperature makes answers more consistent, but not perfectly identical, and it doesn't stop hallucinations. Don't rely on "it worked when I tried it": log real traffic.

Slide 5

The unique challenges of AI agent observability (3–5)

Tools break, reasoning is hidden, and every step costs time and money.

▢ What the slide says

3. Dependency on external tools
Agents rely on databases, APIs and other services, so an agent often fails because a tool failed or returned something unexpected. Example: a flight-booking agent fails because the flight search API returned a new error format.
4. The "black box" problem
It's often unclear why an agent chose a specific tool or generated a specific response.
5. Latency & cost
Every LLM call and tool use adds time and money; inefficiency is directly measurable.

🍛 Analogy

A Swiggy order can be late because of the restaurant, the rider or the payment gateway. Blaming "the app" is useless. You need to know which step failed. Same with agents: is it the model, or the tool it called?

⌨️ Try it in code: catch a tool that changed its reply format

r05_tool_failure.pyRan it ✓ real output below
# Agents often fail because a TOOL changed, not because the AI got worse.
import json


def parse_flights(api_response: str) -> list:
    data = json.loads(api_response)
    if "flights" not in data:          # the API changed its format, or sent an error
        raise ValueError(f"Unexpected flight API response: {data}")
    return data["flights"]


mondays_reply = '{"flights": [{"id": "FL-123", "to": "Paris", "price_inr": 52000}]}'
tuesdays_reply = '{"error": {"code": "RATE_LIMIT", "message": "Too many requests"}}'

for day, reply in [("Monday", mondays_reply), ("Tuesday", tuesdays_reply)]:
    try:
        print(f"{day}: flights = {parse_flights(reply)}")
    except ValueError as e:
        print(f"{day}: TOOL FAILED -> {e}")   # log it! Otherwise the agent may "guess" an answer
Output (real run)
Monday: flights = [{'id': 'FL-123', 'to': 'Paris', 'price_inr': 52000}]
Tuesday: TOOL FAILED -> Unexpected flight API response: {'error': {'code': 'RATE_LIMIT', 'message': 'Too many requests'}}

The code didn't change between Monday and Tuesday; the API's reply did. Checking the shape of tool replies and logging failures clearly is what lets you spot this in minutes instead of days.

🌍 Real world

Payment gateways, shipping APIs and search APIs change formats, rate-limit you or time out. In production agents, a large share of "the AI is wrong" reports turn out to be tool problems once traces are available.

MELT: the four kinds of data

Slide 6

The MELT framework: your observability foundation

Four kinds of data, each answering a different question.

▢ What the slide says

LetterPillarSlide's definitionNickname
MMetricsNumbers measured over timeThe "what"
EEventsDiscrete, meaningful moments that represent a change of state–
LLogsImmutable, time-stamped records of what happenedThe "raw truth"
TTracesThe end-to-end journey of a single requestThe "story"

🍛 Analogy: a cricket match

  • Metrics = the scoreboard: run rate, overs, wickets. Quick health check.
  • Events = the highlights: "Wicket!", "Six!", "DRS review". Moments that changed the game.
  • Logs = ball-by-ball commentary: every delivery, exactly as it happened.
  • Trace = the full replay of one batter's innings from walking in to getting out: one story, start to end.

⌨️ Try it in code: what MELT records look like for ONE request

r06_melt_records.pyRan it ✓ real output below
# What the four MELT records look like for ONE request: "Where is my order #1234?"
# (one shared trace_id ties all of them together)
import json
import uuid

trace_id = uuid.uuid4().hex[:8]


def emit(kind: str, **data):
    print(json.dumps({"kind": kind, "trace_id": trace_id, **data}))


emit("event", name="agent.session_started", user_id="u_42")
emit("trace_span", name="tool.track_order", status="ok", duration_ms=180)
emit("log", step="llm_call", model="gpt-6-luna",
     prompt="Order #1234 status: out for delivery. Answer the customer.",
     completion="Your order is out for delivery and should reach you today.")
emit("trace_span", name="llm.write_answer", status="ok", duration_ms=920)
emit("metric", name="latency.total_task", value_ms=1100)
emit("metric", name="cost.per_invocation", value_usd=0.00004)

Slide 8

Events: capturing meaningful state changes

Named, business-meaningful moments in a user's journey.

▢ What the slide says

Events are structured, business-significant occurrences. Examples for an AI agent: agent.session_started, agent.decision_made (e.g. "chose to search the web"), tool.execution_succeeded / tool.execution_failed, conversation.escalated_to_human.

Purpose: track user journeys and business-level outcomes.

💡 In simple words

A metric is "how many per minute". An event is "this specific thing just happened, here are the details". Count events and you get funnels: how many sessions started, how many needed a human, how many refunds failed.

🍛 Analogy

The status updates in a Swiggy order: "Order placed" → "Restaurant accepted" → "Rider assigned" → "Delivered". Each is an event. Count them across all orders and you can see where orders get stuck.

⌨️ Try it in code: record events, then count the journey

r08_events.pyRan it ✓ real output below
# EVENTS: named, business-meaningful moments. Count them to see the user journey.
from collections import Counter

events = []


def record_event(name: str, **details):
    events.append({"event": name, **details})


# Three support conversations, as they happened
record_event("agent.session_started", session="s1")
record_event("agent.decision_made", session="s1", decision="search_orders")
record_event("tool.execution_succeeded", session="s1", tool="order_lookup")

record_event("agent.session_started", session="s2")
record_event("agent.decision_made", session="s2", decision="issue_refund")
record_event("tool.execution_failed", session="s2", tool="refund_api", error="timeout")
record_event("conversation.escalated_to_human", session="s2")

record_event("agent.session_started", session="s3")
record_event("agent.decision_made", session="s3", decision="search_web")
record_event("tool.execution_succeeded", session="s3", tool="web_search")

counts = Counter(e["event"] for e in events)
for name in ["agent.session_started", "tool.execution_succeeded", "tool.execution_failed",
             "conversation.escalated_to_human"]:
    print(f"{name:<34} {counts[name]}")
print(f"\nEscalation rate: {counts['conversation.escalated_to_human'] / counts['agent.session_started']:.0%}")

Slide 9

Logs: the immutable raw record

The exact words that went in and came out.

▢ What the slide says

Logs are the ultimate source of truth for what exactly happened. Crucial for AI agents:

  • LLM interactions: the exact prompts sent and completions received.
  • Tool calls: input parameters and raw output responses.
  • Agent "thoughts": internal reasoning steps (if the agent framework provides them).

Purpose: deep, forensic debugging.

💡 In simple words

"Immutable" means logs are never edited after writing, just like a bank passbook. When a user complains about one answer, the log shows exactly what prompt the model saw. Very often the bug is visible right there: a missing fact, a wrong number from a tool, a confusing instruction.

⌨️ Try it in code: one JSON log line per LLM call

s09_logs.pyNeeds OpenAI key
# LOGS: write down exactly what went in and what came out of every LLM call.
import json
import logging
import time
from openai import OpenAI

logger = logging.getLogger("agent")                       # our own logger, separate from library logs
logger.setLevel(logging.INFO)
logger.addHandler(logging.FileHandler("agent_logs.jsonl"))
client = OpenAI()


def logged_llm_call(prompt: str) -> str:
    start = time.perf_counter()
    reply = client.chat.completions.create(
        model="gpt-6-luna", reasoning_effort="none",
        messages=[{"role": "user", "content": prompt}],
    )
    answer = reply.choices[0].message.content
    logger.info(json.dumps({                        # one JSON line per call = easy to search later
        "type": "llm_call",
        "model": reply.model,
        "prompt": prompt,
        "completion": answer,
        "tokens": reply.usage.total_tokens,
        "duration_ms": round((time.perf_counter() - start) * 1000),
    }))
    return answer


logged_llm_call("In one line: what is the return window for electronics on most Indian e-commerce sites?")
print(open("agent_logs.jsonl").read())
Example output (what you would see; exact text and numbers vary)
{"type": "llm_call", "model": "gpt-6-luna", "prompt": "In one line: what is the return window for electronics on most Indian e-commerce sites?", "completion": "Usually 7 to 10 days from delivery, but check the seller's policy for that product.", "tokens": 58, "duration_ms": 640}

One line per call, in JSON, so you can later search "all calls where tokens > 3000" or "all completions mentioning 'refund'".

⚠️ Careful

  • Prompts often contain personal data (names, phone numbers, addresses). Mask it before logging and set a retention period.
  • Never log API keys or passwords.
  • "Agent thoughts": many reasoning models don't show their full internal reasoning (some give only a summary). Log what the framework exposes, and don't assume you can see everything.
Slide 10

Traces: the end-to-end story

The most important pillar for agents.

▢ What the slide says

  • Traces are the most important pillar for AI agents.
  • A trace visualizes the entire lifecycle of a single user request.
  • It connects all the metrics, events and logs for that task.
  • It shows the agent's step-by-step thought process and action history.
  • Diagram: User request → Agent → LLM call (plan steps) → Agent → Tool call (search flights) → LLM call (analyze results) → Agent → Tool call (book flight) → final response.

💡 In simple words

A trace is a tree of boxes called spans. Each span is one step: an LLM call, a tool call, a database query. Each records its input, output, start time, duration and status. Nested spans show which step called which.

🍛 Analogy

Tracking a courier parcel: picked up in Mumbai → hub in Pune → out for delivery in Bangalore → delivered. Each scan is a span; the full tracking history is the trace. If the parcel is late, you can see exactly which hub held it for two days.

⌨️ Try it in code: nested spans with LangSmith

s10_traces.pyNeeds OpenAI + LangSmith keys
# TRACES with LangSmith: every decorated function becomes a box (a "span") in one tree.
#   pip install langsmith openai   and set OPENAI_API_KEY, LANGSMITH_TRACING=true, LANGSMITH_API_KEY
from langsmith import traceable
from langsmith.wrappers import wrap_openai
from openai import OpenAI

client = wrap_openai(OpenAI())        # LLM calls are added to the trace automatically


@traceable(run_type="tool")
def get_weather(city: str) -> str:
    return f"{city}: 31°C, sunny, no rain expected"    # in real life: a weather API call


@traceable(name="travel_helper")
def travel_helper(question: str) -> str:
    weather = get_weather("Jaipur")                       # span 2: the tool
    reply = client.chat.completions.create(               # span 3: the LLM call
        model="gpt-6-luna", reasoning_effort="none",
        messages=[{"role": "user", "content": f"{question}\nWeather report: {weather}"}],
    )
    return reply.choices[0].message.content


print(travel_helper("Should I pack an umbrella for Jaipur this weekend?"))
Example output (what you would see; exact text and numbers vary)
No umbrella needed: Jaipur is expected to be 31°C and sunny with no rain. Pack sunglasses and a water bottle instead.

What the trace looks like in LangSmith:

├── get_weather                   0.00 s  ✓   in: "Jaipur"   out: "Jaipur: 31°C, sunny, no rain expected"
└── ChatOpenAI  gpt-6-luna        1.22 s  ✓   96 tokens · prompt and answer stored
Slide 11

Tracing an AI agent's journey

User query: "Book a flight to Paris and summarize the itinerary."

▢ What the slide says

  1. Span 1, Agent: receives the query.
  2. Span 2, LLM call: plans the steps: [search flights, book, summarize].
  3. Span 3, Tool call: search_flights_api(dest="Paris") → returns a list.
  4. Span 4, LLM call: analyzes the results, selects flight FL-123.
  5. Span 5, Tool call: book_flight(flight_id="FL-123") → ERROR: "Seat not available".
  6. Span 6, Agent: returns the error to the user.

Each box would show timing and status, and could be clicked to see its logs.

▶️ Click through the trace (each span opens to show its log)

Span 1 · Agent · receives query · 0.00 s ✓

Input: "Book a flight to Paris and summarize the itinerary." · user_id u_42

Span 2 · LLM call · plan steps · 1.10 s ✓

Prompt: "List the steps to handle: Book a flight to Paris…" → "1. Search flights 2. Book the best one 3. Summarize"

from langsmith.wrappers import wrap_openai
from openai import OpenAI

client = wrap_openai(OpenAI())


def ask_llm(prompt: str) -> str:
    reply = client.chat.completions.create(model="gpt-6-luna", reasoning_effort="none",
                                           messages=[{"role": "user", "content": prompt}])
    return reply.choices[0].message.content


@traceable(run_type="tool")
def search_flights(destination: str) -> list:
    return [{"id": "FL-123", "to": destination, "price_inr": 52000},
            {"id": "FL-456", "to": destination, "price_inr": 61000}]


@traceable(run_type="tool")
def book_flight(flight_id: str) -> dict:
    return {"status": "failed", "error": "Seat not available"}    # the airline's real answer today


@traceable(name="booking_agent")
def booking_agent(user_query: str) -> str:
    plan = ask_llm(f"List the steps to handle: {user_query}")                       # span 2
    flights = search_flights("Paris")                                                # span 3
    choice = ask_llm(f"Pick the cheapest flight id from {flights}. Reply with the id only.")  # span 4
    result = book_flight(choice.strip())                                             # span 5
    return ask_llm(f"The user wants to book a flight. The booking API returned "     # span 6

Slide 13

Debugging in action: the booking agent that lies

Everything looks healthy, yet customers are being misled.

▢ What the slide says

  • The problem: users report the travel agent sometimes claims to book flights, but no booking is made.
  • The symptom: everything seems fine. The LLM API is up. No critical errors in the server logs.
  • The question: "Why is the agent confirming false bookings?"

💡 In simple words

This is the classic AI bug: nothing crashes. The servers are up, the code returns normally, and still the result is wrong. Monitoring alone can't see it, because every check it knows about is green. This is exactly the kind of question observability exists for.

🍛 Analogy

A travel agent at a desk calls the airline, hears "sorry, no seats", hangs up, and tells you with a big smile "you're booked!" The phone line worked, the agent was polite, and you still have no ticket.

🌍 Real world

In July 2025, SaaStr's founder reported that Replit's AI coding agent deleted his production database during a code freeze and then misreported what had happened, at first saying a rollback was impossible (it turned out it wasn't). Agents saying "done" when the real outcome differs is a known failure mode. Traces are how you catch it.

Slide 15

Drilling down with logs to understand "why"

Click the last LLM call in the trace and read exactly what it was given.

▢ What the slide says

The prompt sent to the LLM
"The user wants to book a flight. The booking API returned 'Seat not available'. What should I say?"
The LLM's completion
"I've booked your flight to Paris! Your confirmation number is [hallucinated number]."

Root cause: the agent has no error-handling logic. It blindly passes tool errors to the LLM, which can hallucinate a positive response.

💡 In simple words

The model was asked an open question ("what should I say?") with a confusing error buried inside, while the conversation was all about booking. Models are trained to be helpful, so it produced the helpful-sounding answer and even invented a confirmation number. The bug isn't in the model; it's in how our code used the model.

Slide 16

Implementing the fix

Handle failures in code, with a fixed, honest message.

▢ What the slide says

The fix: add a conditional check in the agent's logic. If tool_call.status == "failed", use a pre-defined error-handling prompt: "Tell the user the booking failed because the seat was unavailable and suggest they try another flight." Do NOT pass the raw error to the LLM and hope for the best.

Result: the success_rate metric recovers, and user trust is restored.

⌨️ Try it in code: the fixed handler

r16_fixed_booking.pyRan it ✓ real output below
# The fix: check the tool's status in CODE. Never hand a raw failure to the LLM and hope.
def respond_to_booking(result: dict, flight_id: str) -> str:
    if result["status"] == "failed":
        # Pre-defined, honest message (no LLM, so nothing to hallucinate)
        return (f"Sorry, I couldn't book {flight_id}: {result['error'].lower()}. "
                "Would you like me to try another flight?")
    return f"Your flight {flight_id} is booked. Confirmation: {result['confirmation']}."


print(respond_to_booking({"status": "failed", "error": "Seat not available"}, "FL-123"))
print(respond_to_booking({"status": "ok", "confirmation": "PNR7XK2"}, "FL-456"))
Output (real run)
Sorry, I couldn't book FL-123: seat not available. Would you like me to try another flight?
Your flight FL-456 is booked. Confirmation: PNR7XK2.

For failures we don't even need the LLM: a fixed message can't hallucinate. If you want a friendlier wording, give the LLM the specific instruction from the slide ("tell the user the booking failed…"), never an open "what should I say?".

⚠️ Make the failure visible too

Also make the tool report failure properly: raise an error or mark the span as failed. Then the book_flight span turns red in traces, and the tool_usage.error_rate metric counts it. The original bug was invisible partly because the tool "succeeded" while returning a failure.

🌍 The full loop

Metrics showed a problem → traces found the bad cases → logs showed the exact prompt → code fix → metrics confirm recovery. That loop is what "observability" means in practice.

# DIY tracing with OpenTelemetry (the open standard most observability tools understand).
#   pip install opentelemetry-sdk
import sqlite3
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor


def one_line(span):   # print each span as one readable line instead of a big JSON blob
    ms = (span.end_time - span.start_time) / 1e6
    return f"{span.name:<16} {ms:6.2f} ms  {dict(span.attributes)}\n"


provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter(formatter=one_line)))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("support-bot")

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id INTEGER, status TEXT)")
db.execute("INSERT INTO orders VALUES (1234, 'out for delivery')")

with tracer.start_as_current_span("handle_question") as root:            # the whole request
    root.set_attribute("user.id", "u_42")
    with tracer.start_as_current_span("search_orders") as span:          # step 1: database
        status = db.execute("SELECT status FROM orders WHERE id = 1234").fetchone()[0]
        span.set_attribute("order.status", status)
    with tracer.start_as_current_span("format_reply") as span:           # step 2: build the answer
        reply = f"Your order #1234 is {status}."
        span.set_attribute("reply.length", len(reply))
        # in a real app the LLM call would be one more span right here

print(reply)
# Spans print as they FINISH: the two children first, then the parent that contains them.

Monitoring
Fixed checks and alerts for problems you already know about.
Observability
Recording enough detail to investigate problems you didn't predict.
Non-deterministic
The same input can give different outputs.

Metrics, Events, Logs, Traces.
Metric
A number tracked over time (latency, cost, success rate).
Event
A named, meaningful moment ("escalated_to_human").

A permanent, time-stamped record of exactly what happened.

Adding code that records metrics, events, logs and spans.

The model states something false as if it were true.

Check yourself (click to reveal)

1. Your dashboard is all green, but users say the bot gives wrong answers. Which pillar do you open first?

Traces (filtered to the complaining users or bad ratings), then the logs inside them. Metrics can only say that something is off.

2. Is "conversation.escalated_to_human" a metric, event, log or trace?

An event: a named, meaningful moment. Counting these events over time gives you a metric (escalation rate).

3. Why did book_flight show a green ✓ in the buggy trace?

It returned a "failed" dictionary instead of raising an error, so the tracing tool saw a normal return. Make tools report failures properly.

4. You can't reproduce a bad answer locally. Why, and what saves you?

Non-determinism: the model may answer differently each time. The saved trace and logs of the real request show exactly what happened.

5. Name two things you should NOT store in logs.

Any two of: API keys and passwords, raw personal data (phone numbers, emails, ID numbers), payment details. Mask them first.
