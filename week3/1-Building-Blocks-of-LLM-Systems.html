1.1 A new way of thinking: from "always the same" to "probably right"

Almost all the software you have written so far is deterministic. That is a fancy word for a simple idea: the same input always gives the same output. If add(2, 2) returns 4 today, it will return 4 tomorrow and a million times after that. A unit test that passes once will pass forever.

Large Language Models (LLMs) break this rule. They are probabilistic: give the same input twice and you may get two different answers. Usually both are fine. Sometimes one is wrong. Our job as engineers is to build a system around the model that turns this "probably right" behaviour into something users can depend on. That is what this whole series is about.

Same input, different outputs
Traditional software (deterministic)
Input: 2 + 2
Always 4 ✅

A calculator, a bank balance check, a sorting function.

LLM (probabilistic)
Input: "Write a tagline for a chai shop"
"Sip the moment.""Your daily dose of warmth.""Best coffee in town!" 🤔

Each run can differ, and one run can even be wrong.

So what exactly is an LLM?

A Large Language Model is an AI model that has read an enormous amount of text and code (books, websites, documentation, code repositories) and learned the patterns of language from it. Because of that, it can write, summarise, translate, answer questions, reason through problems and write code. Popular examples are GPT (by OpenAI), Claude (by Anthropic), Gemini (by Google), Llama (by Meta), DeepSeek and Grok. Each has its own strengths, such as reasoning, creativity, speed or price.

You talk to an LLM by sending it text called a prompt. It replies with text. Good prompts include clear instructions and guardrails (rules about what not to do) so the reply is what you expect.

🔍 Worked example: your first LLM call

Here is the smallest useful program. We send one prompt and print the answer.

from openai import OpenAI
client = OpenAI()   # reads your OPENAI_API_KEY from the environment

reply = client.chat.completions.create(
    model="gpt-6.1-terra",
    messages=[{"role": "user", "content": "Write a 5-word tagline for a chai shop."}],
)
print(reply.choices[0].message.content)

Output (run 1): Sip slowly. Smile widely. Repeat.
Output (run 2): Fresh chai, warm conversations daily.

Same code, same prompt, two different answers. That is the probabilistic nature in action.

🧠 Think of it like…A calculator is like a government form: fixed rules, fixed result. An LLM is like a very well-read friend. Ask them the same question twice and they will phrase the answer differently, and once in a while they will confidently say something wrong. You would not fire such a useful friend; you would build habits around them: give them the right notes, double-check important facts, and keep a backup plan. That is exactly what LLM system design is.
🌍 Real-world exampleWhen you chat with a food-delivery app's support bot and it says "Your refund of ₹249 has been processed", that answer did not come from the LLM's memory. The system looked up your order in a database, gave those facts to the LLM, and asked it to write a friendly reply. The LLM is only one part of a bigger system. You will see this pattern again and again.

🧩 Tokens: the Lego bricks of text

An LLM does not read words the way you do. It reads tokens: small chunks of text, often a whole short word, sometimes part of a long word, sometimes a single punctuation mark. Splitting text into tokens is called tokenization. Each token is then turned into a number (its token ID), because computers only work with numbers.

🔍 Worked example: how a sentence becomes tokens
TextTokens (roughly)Token IDs (illustrative)
The cat sat on the mat.The cat sat on the mat .[791, 8415, 7731, 389, 279, 5634, 13]
unbelievableun believ able[359, 32927, 481]
BengaluruBeng al uru[33, 1286, 5797]

Notice three things: (1) common words are usually one token; (2) long or rare words get split into pieces; (3) the space before a word is often part of the token. A handy rule of thumb for English: 1 token ≈ 4 characters ≈ ¾ of a word. So 1,000 words ≈ 1,300 tokens. Languages like Hindi or Tamil usually need more tokens for the same sentence, which makes them a bit slower and costlier to process.

🎮 Try it: tokenize your own sentence

Type anything. This is a simplified tokenizer for learning. Real tokenizers (called BPE, Byte-Pair Encoding) use a learned vocabulary, but the idea is the same.

Why should a system designer care about tokens? Because tokens decide three very practical things: how fast the answer comes, how much you pay, and how much you can send at once.

⏱ Speed (latency)
The model reads all your input tokens together, in parallel, which is fast. But it writes its output one token at a time, because each new token depends on the ones before it. Generating 500 tokens takes much longer than reading 500 tokens. Want faster answers? Ask for shorter answers.
💸 Cost
LLM companies charge per million tokens, with output tokens usually costing several times more than input tokens. Sending a 2,000-token prompt just to answer "yes or no" is like hiring a taxi to cross the road. Keep prompts lean, and reuse (cache) anything you send repeatedly.
📏 Size limit
Every model has a maximum number of tokens it can handle at once, called its context window (for example 128K or 400K tokens). You cannot paste a user's entire year of chat history into every request, so you need strategies like the two in the demo below.
🧠 Think of it like…In an exam you read the whole question paper in a minute (input, parallel), but you write the answer word by word (output, one at a time). That is why a short answer finishes the exam faster. And like an auto-rickshaw that charges per kilometre, an LLM charges per token. A long detour costs real money. 🛺
🔍 Worked example: what does a support bot cost per month?

Say your app's support bot handles 10,000 chats a day. Each chat sends about 1,500 input tokens (instructions + history + question) and gets back 300 output tokens. Assume an illustrative price of $1 per million input tokens and $4 per million output tokens (real prices vary by model).

StepCalculationResult
Input tokens per day10,000 × 1,50015 million
Output tokens per day10,000 × 3003 million

Monthly cost$27 × 30≈ $810 / month

Now imagine someone adds a 3,000-token "company policy" document to every prompt. Input jumps to 4,500 tokens per chat and the monthly bill nearly triples on the input side. This is why engineers watch tokens closely.

Two ways to handle a long conversation

When a conversation gets very long, older turns are summarised ("User is planning a Manali trip for 4 people in December, budget ₹60K, wants a hotel near Mall Road") so the model still "remembers" the important parts without paying for every old message again.

📍 Embeddings: a GPS address for meaning

Tokens tell the model what text it has. Embeddings capture what the text means. An embedding is a list of numbers (called a vector) that represents the meaning of a piece of text, an image or code. The magic property: texts with similar meaning get vectors that are close to each other, even if they share no words at all.

This is very different from normal search. A normal search (like a dictionary lookup or SQL WHERE name = 'x') needs an exact match. With embeddings we can find the nearest neighbours: things that are conceptually related. Search "how to combine numbers" and you can find a function called sum().

Similar meanings live close together
"combine numbers" shares no words with "add" or "sum", yet its meaning lands in the maths neighbourhood.
🔍 Worked example: measuring "closeness" with cosine similarity

Real embeddings have hundreds or thousands of numbers. Let's use tiny 3-number vectors so we can do the maths by hand. Imagine each number measures one "feature": [is it food?, is it sweet?, is it a vehicle?]

WordVector
gulab jamun[0.9, 0.9, 0.0]
rasgulla[0.9, 0.8, 0.1]
scooter[0.0, 0.1, 0.9]

Cosine similarity measures the angle between two vectors. 1 means "pointing the same way" (same meaning), 0 means "unrelated". The formula is: multiply matching numbers and add them up (the dot product), then divide by the lengths of both vectors.

gulab jamun vs rasgulla: dot = 0.9×0.9 + 0.9×0.8 + 0×0.1 = 1.53. Lengths ≈ 1.273 and 1.208. Similarity = 1.53 ÷ (1.273 × 1.208) ≈ 0.99 → almost the same meaning ✅
gulab jamun vs scooter: dot = 0 + 0.09 + 0 = 0.09. Similarity ≈ 0.09 ÷ (1.273 × 0.906) ≈ 0.08 → unrelated ❌

A vector database does exactly this, just with 1,536 numbers per vector and millions of vectors, using clever shortcuts to stay fast.

🔍 Worked example: getting a real embedding 
emb = client.embeddings.create(
    model="text-embedding-3-small",
    input="How do I reset my UPI PIN?",
)
vector = emb.data[0].embedding
print(len(vector))      # how many numbers?
print(vector[:5])       # first five numbers

Output:

1536
[0.0183, -0.0421, 0.0067, 0.0294, -0.0110]

Each sentence becomes 1,536 numbers. You will never read these numbers yourself. You store them and let the database compare them.

🧠 Think of it like…Every word has an address in a "city of meaning". Samosa, kachori and pakora all live on the same street (Snacks Lane). Password, login and OTP live in a different colony (Security Nagar). When someone asks "what goes well with evening chai?", the system walks to Snacks Lane, even though the word "samosa" never appeared in the question. 🏘️
🌍 Real-world example"Customers who viewed this also viewed…" on shopping sites, "songs like this" on music apps, and searching your phone's photo gallery for "beach" all use embeddings. None of those photos are labelled "beach"; the meaning is in the vectors.

How many numbers should a vector have? More numbers (say 3,072 instead of 1,536) can capture finer shades of meaning, but they also take more storage and make search slower. The rule: pick the smallest size that meets your accuracy needs.

🚀 Going deeper: storage mathsEach number is usually stored as a 4-byte float. One 1,536-number vector = 1,536 × 4 ≈ 6 KB. Ten million document chunks ≈ 61 GB of raw vectors, before any index overhead. Double the dimensions and you double that. So "how many dimensions?" is really a question about RAM, cost and speed, not only accuracy.

🏫 Pre-training and 🎓 fine-tuning: how the brain is built

Pre-training = going to school
The first and most expensive stage. The model reads a massive snapshot of the internet: books, articles, websites, code. It is not trained for any one job. Instead it learns the basics of language and the world:
  • how grammar works
  • what words mean
  • how words and ideas connect
  • common facts about the world
  • the usual patterns of sentences
This costs tens of millions of dollars and months of computing, so only a few companies do it.
Fine-tuning = specialist coaching
Take the pre-trained model and train it a little more on a small, focused dataset so it becomes an expert in one area: your company's jargon, a particular writing style, or rules of a field like medicine or law.

Fine-tuning is thousands of times cheaper and faster than pre-training from scratch, because the model already knows the language; you are only adjusting it slightly.

2. Your special dataFocused datasete.g. 2,000 example support replies
both go into
3. Training runSmall adjustmentsupdates the model's weights slightly
4. ResultFine-tuned specialistspeaks in your style
A general doctor + cardiology training = a cardiologist.
🔍 Worked example: what fine-tuning data actually looks like

Fine-tuning data is just many examples of "when the user says this, reply like that". Each line is one example in JSON:

{"messages": [
  {"role": "system", "content": "You are BankBuddy. Be polite, brief, never promise timelines."},
  {"role": "user", "content": "my card got blocked why"},
  {"role": "assistant", "content": "Sorry about that! Cards are usually blocked after 3 wrong PIN attempts. You can unblock it in the app under Cards → Manage."}
]}

Give the model a few thousand of these and it learns BankBuddy's tone and format.

⚠️ Watch out: fine-tuning is not the best way to teach new factsBeginners often think "my model doesn't know our 2026 price list, so let's fine-tune it". Fine-tuning can add knowledge, but facts change often and the model may still mix up old and new. For fresh or changing facts, it is more reliable to fetch them at question time and give them to the model (this is called RAG, section 1.6). Use fine-tuning for style, format, tone and jargon.
Easy rule: Facts → RAG. Behaviour → fine-tuning.

1.4 Prompts: how we talk to the model

A prompt is everything you send to the model: the instruction, question, background text and examples. The quality of the answer depends heavily on the quality of the prompt. A simple prompt is just a question ("What is compound interest?"). A well-built prompt has four parts:

Anatomy of a structured prompt
1. PersonaWHO should the model be?
"You are a friendly personal-finance teacher."
2. ContextWHY / background
"The user is a 22-year-old who just got their first salary. Focus on safe options."
3. InstructionWHAT to do
"Explain compound interest using a ₹5,000 monthly SIP example."
4. FormatHOW the answer should look
"Reply as JSON with a 'summary' and exactly 3 'tips'."
PartWhat it doesExample
InstructionThe actual command"Summarize the following meeting notes…"
ContextBackground the model needs to do the task well"…These are notes from a sprint planning meeting. Focus only on action items and owners."
PersonaWho the model should act as; this changes tone and depth"You are a senior engineering manager writing for new joiners."

🔍 Worked example: the four parts in real code

In code, the persona and rules usually go in the system message (instructions from you, the developer), and the user's request goes in the user message.

reply = client.chat.completions.create(
    model="gpt-6.1-terra",
    messages=[
        {"role": "system", "content":
            "You are a friendly personal-finance teacher. "          # persona
            "The user just got their first salary; suggest only safe options. "  # context
            "Reply ONLY as JSON: {\"summary\": str, \"tips\": [3 strings]}"},  # format
        {"role": "user", "content":
            "Explain compound interest with a ₹5,000 monthly SIP example."},  # instruction
    ],
)
print(reply.choices[0].message.content)

Output:

{"summary": "Compound interest means you earn returns on your returns. If you invest ₹5,000 every month at 12% a year, after 10 years you will have put in ₹6 lakh but could have about ₹11.6 lakh.",
 "tips": ["Start early: time matters more than amount.",
          "Don't stop the SIP when markets fall.",
          "Increase the SIP amount when your salary rises."]}

Because we asked for JSON, our app can read tips directly and show them as a neat list. No messy text parsing.

🧠 Think of it like…Ordering on a food app with "anything is fine" gets you anything. Ordering with "I'm vegetarian (context), I want something North Indian (persona of the cuisine), one paneer dish (instruction), half portion, less spicy, no onion (format)" gets you exactly what you want. 🍲

🧠 The context window: the model's short-term memory

The context window is the maximum number of tokens the model can "see" in one go. Think of it as its working memory. Everything you send AND everything it writes back must fit inside this window. That includes:

  • your system instructions (persona, rules, format)
  • the conversation history (earlier questions and answers)
  • any documents or data you attach
  • the user's latest question
  • the model's reply (yes, the answer uses up the window too)

The model has no memory between requests. Every single call, you must send everything it needs to know again. If the conversation grows beyond the window, the oldest parts are simply cut off, and the model "forgets" them.

🤔 Reasoning: how the model "thinks"

Reasoning means taking information, working through it logically, and reaching a new conclusion. In an LLM, reasoning is an emergent ability: nobody programmed it directly. The model is trained only to predict the most likely next token, but after seeing billions of examples of explanations, proofs and step-by-step solutions, it learned to imitate how people reason.

One powerful trick is chain-of-thought: the model writes out its thinking step by step before giving the final answer. Modern "reasoning models" do this automatically and can also decide to use tools (like web search) in the middle of thinking.

🔍 Worked example: a model planning before it answers

Prompt: "Plan a 2-day Jaipur trip for a family of 4 under ₹20,000."

Thought: The user wants a budget plan. I should break it into travel, stay, food and sightseeing. Thought: I don't know current hotel prices. I should search instead of guessing. Action: web_search("family hotels Jaipur price per night") Observation: Mid-range family rooms cost about ₹2,500–3,500 per night. Thought: 2 nights ≈ ₹6,000. That leaves ₹14,000 for food, local travel and tickets. Thought: Day 1 Amber Fort + Hawa Mahal; Day 2 City Palace + Johari Bazaar. Final answer: (a day-by-day plan with a cost table)

Look at what happened: the model planned, noticed it lacked information, chose a tool, used the result, and continued. This "think → act → observe" pattern is the seed of AI agents, which we cover in section 1.8. 🌱

🛠 Five prompting techniques that work (bad vs good)

Prompt engineering means adjusting your prompt (instructions, examples, constraints) until the model reliably gives what you need. Here are five techniques you will use every day.

1. Give context: share the surrounding information

❌ Weak
Why is my code failing?
✅ Strong
Here is the error: "KeyError: 'price' at line 32 in cart.py". Here is the function that reads the order JSON (pasted below). Here is one sample order JSON (pasted below). Using only this, explain why 'price' is missing and suggest a fix.

The model cannot see your screen. Without the error, the code and the data, it can only guess.

2. Assign a role: tell the model who to be

❌ Weak
Review this login function.
✅ Strong
You are a senior security engineer reviewing code before release. Review this login function for a junior developer. Focus on SQL injection, password storage and missing input validation. List each risk with a one-line fix.

3. Show examples ("few-shot" prompting)

❌ Weak
Extract the order details from this WhatsApp message.
✅ Strong
Extract order details as JSON. Examples: Message: "bhaiya 2 kg aloo aur 1 dozen eggs bhej do" Output: {"items":[{"name":"potato","qty":"2 kg"},{"name":"eggs","qty":"12"}]} Message: "send 500g paneer pls" Output: {"items":[{"name":"paneer","qty":"500 g"}]} Message: "1 litre milk and 2 bread" Output:

Two or three examples teach the exact format far better than a paragraph of explanation. That's "few-shot". With zero examples it's called "zero-shot".

4. Add guardrails: say clearly what NOT to do

❌ Weak
Write a script to delete old files in my Downloads folder.
✅ Strong
Write a Python script that finds files older than 30 days in ~/Downloads. RULES: - Do NOT delete anything by default. - First print a "DRY RUN" list of files that would be deleted. - Delete only if the user types YES to confirm.

5. Ask for step-by-step thinking (chain-of-thought)

❌ Weak
How many unique customers ordered last week?
✅ Strong
Find the number of unique customers in these order logs. Think step by step: 1. Find where the customer ID appears in each line. 2. Extract every customer ID into a list. 3. Remove duplicates. 4. Count what's left. Show each step, then give the final number.
🎯 Interview tip"I treat prompts like code: they live in version control as templates, they ask for structured output (a JSON schema), they include explicit guardrails, and every prompt change is tested against a fixed set of example questions before it ships."

1.5 How AI understands code

Let's apply these ideas to a real use case: AI coding assistants (tools like GitHub Copilot or Cursor). Understanding the meaning of code is not enough here. The tool must also understand the code's structure (what is inside what) and relationships (what calls what). Two ideas help with that: syntax trees (ASTs) and knowledge graphs. First, a quick look at vector search.

🔎 Vector search: finding code by meaning

Vector search finds information by meaning instead of exact keywords. When a developer asks a question, the system finds the most relevant pieces of code to send to the LLM as context. Here's the flow:

  1. Ahead of time: every function in the codebase is turned into an embedding and stored in a vector database (for example pgvector, an add-on for PostgreSQL, or Pinecone).
  2. At question time: the developer's question is turned into an embedding using the same embedding model.
  3. The database compares the question vector with all stored vectors using cosine similarity or the dot product (both measure closeness).
  4. The closest matches ("top-k", e.g. the best 5) are returned.
  5. Those code pieces are added to the prompt so the LLM can answer using your code.
🔍 Worked example

Developer asks: "Where do we check if an email address is valid?"

Function in codebaseSimilarity to the question
def is_valid_email(addr): … (uses a regex)0.89 ✅ top match
def send_welcome_mail(user): …0.61
def calculate_gst(amount): …0.12

Notice the word "check" never appears in is_valid_email, but the meaning matches.

🚀 Going deeper: cosine vs dot productCosine similarity = (A · B) ÷ (|A| × |B|). It only cares about direction, not length. If all vectors are first "normalised" to length 1, the denominator becomes 1, so cosine similarity and the plain dot product give the same ranking. That's why many systems normalise once and then use the cheaper dot product.

✍️ Text autocomplete vs code completion

Text autocomplete (like your phone keyboard) only looks at the last few words and guesses the next one. It doesn't really understand meaning or structure. Code completion is harder: the suggestion must be valid syntax and must fit where you are in the code: inside which class, which function, with which variables available.

🌳 Abstract Syntax Trees (ASTs): the skeleton of code

Embeddings give us the meaning of code. An Abstract Syntax Tree (AST) gives us its structure. An AST is a tree that shows how every part of the code sits inside another part: a project contains files, a file contains classes, a class contains methods, a method contains statements. Compilers and IDEs build ASTs all the time to highlight errors, rename variables safely and refactor code.

🔍 Worked example: see a real AST with Python's built-in ast module 
import ast
code = """
class Cart:
    def add(self, item):
        self.items.append(item)

    def total(self):
        return sum(i.price for i in self.items)
"""
tree = ast.parse(code)
for node in ast.walk(tree):
    if isinstance(node, (ast.ClassDef, ast.FunctionDef)):
        print(type(node).__name__, node.name,
              "lines", node.lineno, "to", node.end_lineno)
Output: 
ClassDef Cart lines 2 to 7
FunctionDef add lines 3 to 4
FunctionDef total lines 6 to 7
As a tree: 
ClassDef (Cart)
├── FunctionDef (add)
│   ├── args: self, item
│   └── Call: self.items.append(item)
└── FunctionDef (total)
    ├── args: self
    └── Return: sum(...)

Why does an AI tool care? Because of chunking. Before code can be embedded, it must be cut into pieces (chunks). If you cut blindly every 500 characters, you might slice a function in half, and each half makes no sense alone. With an AST, you cut along natural boundaries: one whole function = one chunk, or one whole class = one chunk.

❌ Fixed-size chunks
Chunk 1: "...def total(self): return sum(i.pri" Chunk 2: "ce for i in self.items) def apply_coupon(..."
A function split in two. Neither chunk is useful on its own.
✅ AST-based chunks
Chunk 1: def add(self, item): … (complete) Chunk 2: def total(self): … (complete) Chunk 3: def apply_coupon(self, code): … (complete)
Each chunk is a complete, meaningful unit.

In a large project the AST extends upward too: folders are parents, files are their children, classes inside files, methods inside classes. Here's an example food-delivery app:

  • File level: each file has its own AST with imports, classes, functions and global code.
  • Class / function level: classes contain methods; functions contain statements and expressions.
🧠 Think of it like…An AST is a book's table of contents. Instead of tearing random 500-word strips out of a book, you take "Chapter 3, Section 2" as one piece. The meaning stays intact. ✂️📘

🕸 Knowledge graphs: who is connected to whom

A knowledge graph stores information as nodes (things) and edges (relationships between things). On Instagram, nodes could be users, posts and hashtags, and edges could be follows, liked and tagged in. A graph easily answers questions like "which of my friends liked this post?" or "which hashtags are often used together?".

For code, nodes are projects, folders, files, classes and functions, and edges are relationships like contains, calls and imports. The graph can answer questions embeddings cannot, such as "which functions call calculate_gst()?".

You have to follow the relationships: uncle → brother of groom's father → whose wife's sister is → … That's a graph. Embeddings answer "what looks alike?"; graphs answer "what is connected?". 👨‍👩‍👧

⚖️ Choosing a model: there is no "one model to rule them all"

Every model is a trade-off between four things. You pick based on what your product needs most.

DimensionThe question to askExample need
📏 Context windowHow much text must the model read at once?Summarising a 300-page contract needs a very large window.
⏱ LatencyHow fast must the answer appear?Code suggestions while typing must appear in under 0.2 seconds.
🔐 Security & privacyCan the data leave our servers?Hospital records may require a self-hosted model.
💸 CostHow much can we spend per request?A free app with 10 million users needs a very cheap model.

🎲 Temperature: the creativity knob

We said LLMs are probabilistic. Here is where that randomness comes from, and how to control it. When the model picks the next token, it first gives every possible token a score. Those scores are converted into probabilities, and then one token is sampled (picked randomly, weighted by probability). Temperature controls how "sharp" or "flat" those probabilities are.

❄️ Low temperature (0 – 0.2)
The most likely token almost always wins. Output is consistent and focused. Use for code generation, extracting data, classification, JSON output: anywhere you want the same answer every time.
🔥 High temperature (0.7 – 1.0)
Less likely tokens get a real chance. Output is varied and creative. Use for brainstorming, marketing copy, stories, or generating varied practice questions.
🎮 Try it: "The chai was ___" — move the temperature slider

Bars show the probability of each next word. Press "Pick a word" a few times at low and high temperature and see how often the result changes.

Behind the scenes: probability of word i = escorei/T ÷ (sum over all words of escore/T). Dividing scores by a small T exaggerates the gaps, so the top word dominates. A large T shrinks the gaps, so all words become more equally likely. (The scores here are a toy example.)

🔍 Worked example: same prompt, two temperatures 
for t in [0, 1.0]:
    for run in range(2):
        r = client.chat.completions.create(model="gpt-6.1-terra", temperature=t,
              messages=[{"role": "user", "content": "Name a monsoon snack in 2 words."}])
        print(t, r.choices[0].message.content)

Output:

0    Onion pakoda
0    Onion pakoda
1.0  Masala corn
1.0  Bread pakora

What this means for system design:

  • Testing: you cannot write assert reply == "Onion pakoda" for LLM output. Tests must accept variation (for example, check that the reply is valid JSON, or have another model grade it), or force temperature to 0 for regression tests.
  • Retries: if the model returns broken JSON at temperature 0, retrying with the exact same request will likely fail in exactly the same way. A slightly higher temperature on retry gives it a chance to produce something different (and correct).
⚠️ Watch outEven at temperature 0, outputs are not guaranteed to be 100% identical every time (tiny numeric differences on GPUs, batching, or model updates on the provider's side). So build tests that check meaning and structure, not exact strings.
🧠 Think of it like…Low temperature is your mother's dal recipe: tastes exactly the same every day. High temperature is an experimental chef who might add mango to it today. 🥭 When you're making a bank statement, call your mother. When you need new dish ideas, call the chef.

1.6 RAG: giving the model the right facts at the right time

Here is a common problem. A user asks your app's help bot: "My refund hasn't come yet, what should I do?" Your help centre has an article titled "Money not credited after cancellation". The words are different, but the meaning is the same. How do we find that article and use it to answer? The answer is RAG: Retrieval-Augmented Generation.

  • Retrieval: find the relevant information (from documents, a database, an API…)
  • Augmented: add that information into the prompt
  • Generation: let the LLM write the answer using that information

RAG has a few steps. The first three prepare your knowledge; the last ones happen every time a user asks something.

🧹 Step 1: Clean the data

Before you cut documents into chunks and embed them, clean them properly. This is more than removing extra spaces.

De-noising
Remove HTML tags, repeated headers and footers, cookie banners and navigation links. They add tokens but no meaning, and they "dilute" the useful text.
PII scrubbing
Remove personally identifiable information (PII) like phone numbers, emails, Aadhaar or PAN numbers and API keys before the data is sent to any external model.
Normalisation
Make formats consistent: one date format, one currency style, standard characters. "05/11/26", "Nov 5, 2026" and "2026-11-05" should all become one form.
🔍 Worked example: before and after cleaning
Before
<div class="nav">Home | Help | Login</div> <h2>Refund not received?</h2> Call Priya at 98450 12345 or mail priya@shop.in. Refunds take 5-7 days from 05/11/26. © 2026 Shop Pvt Ltd. All rights reserved.
After
Refund not received? Call [PHONE] or mail [EMAIL]. Refunds take 5-7 days from 2026-11-05.

🔢 Step 2: Turn knowledge into vectors

Split the cleaned documents (help articles, past resolved tickets) into chunks and convert each chunk into an embedding using an embedding model such as text-embedding-3-small. Store each chunk's text, its vector and some labels (called metadata: source, date, category) in a vector database.

🔍 Step 3: Search by meaning

When the user asks a question, embed the question too, and ask the vector database for the closest chunks. Comparing against millions of vectors one by one would be slow, so databases use ANN (Approximate Nearest Neighbour) algorithms, such as HNSW, that find "very close" results extremely fast without checking every single vector.

🧠 Think of it like…ANN search is like finding a book in a well-organised library. You don't check all 1 lakh books one by one. You go to the right floor → the right section → the right shelf, and look at a few dozen books. You might occasionally miss the perfect book on the next shelf (that's the "approximate" part), but you find a great one in seconds.

🔍 Worked example: what the final prompt actually looks like
SYSTEM: You are ShopKart's help assistant. Answer ONLY using the context below. If the answer is not in the context, say "Let me connect you to an agent." CONTEXT: [1] Refunds for cancelled orders reach the original payment method in 5-7 working days. [2] UPI refunds are usually faster: 1-3 working days. Model's answer: "UPI refunds usually take 1–3 working days, so yours should arrive within a day. If it's still not there after 7 working days, you can raise a ticket from Orders → Help."

The model didn't need to "know" ShopKart's policy. We handed it the answer, and it explained it nicely.

🔍 Worked example: a minimal RAG in about 20 lines 
import numpy as np
from openai import OpenAI
client = OpenAI()

docs = ["Refunds for cancelled orders take 5-7 working days.",
        "UPI refunds are usually faster: 1-3 working days.",
        "Delivery partners can't accept cash above ₹2,000."]

def embed(texts):
    out = client.embeddings.create(model="text-embedding-3-small", input=texts)
    return np.array([d.embedding for d in out.data])

doc_vecs = embed(docs)                                 # 1. index once
question = "I paid by UPI, when will my refund come?"
q_vec = embed([question])[0]                           # 2. embed the question
scores = doc_vecs @ q_vec                              # 3. similarity (vectors are normalised)
top = [docs[i] for i in scores.argsort()[::-1][:2]]   # 4. best 2 chunks
print("Retrieved:", top)

answer = client.chat.completions.create(model="gpt-6.1-terra", messages=[
    {"role": "system", "content": "Answer only from this context:\n" + "\n".join(top)},
    {"role": "user", "content": question}])           # 5. augment + generate
print(answer.choices[0].message.content)

Output:

Retrieved: ['UPI refunds are usually faster: 1-3 working days.', 'Refunds for cancelled orders take 5-7 working days.']
Since you paid by UPI, your refund should usually arrive within 1-3 working days.

Notice the cash-delivery chunk was not retrieved: its meaning is far from the question.

RAG is the most important technique for higher accuracy and fewer made-up answers, because the model's answer is grounded in real, verified information from your own sources.

🧠 Think of it like…RAG turns a closed-book exam into an open-book exam 📖. Without RAG, the student writes from memory and may confidently write something wrong. With RAG, they open the textbook to the right page first, then write.

😬 Why basic RAG is not always enough

Problem 1: "Similar" is not the same as "relevant"
Vector search is great at finding similar text, but similar is not always useful. If your help centre has five versions of the refund policy (2022, 2023, 2024…), all five look almost identical, so all five come back. The model gets repetitive, confusing context and may quote the outdated one.
Problem 2: Bad chunking hides the answer
Documents have structure: title → section → sub-section. A question may match the document's title strongly, so the system returns the general introduction, while the actual answer sits five sections deeper and scores low on its own. The connection between "this section" and "that document" is lost.
The buried-answer problem
Question: "How do I change the API timeout?"
strong match on the title ✅
weak match, missed ❌
One document: "API General Settings"

What the LLM receivesonly the overview — the real answer never arrives 😢

🕸 Why knowledge graphs help retrieval

To fix these limits, we add a knowledge graph, stored in a graph database such as Neo4j or Amazon Neptune. Instead of matching similar words, it records relationships explicitly:

Section 5          -[part_of]->      "API General Settings"
Ticket #402        -[resolved_by]->  Commit a1b2c3
Commit a1b2c3      -[written_by]->   Ananya

Now retrieval can follow a path through these links to reach a precise answer, even across several hops.

🚀 GraphRAG: RAG + knowledge graphs

Combining a knowledge graph with an LLM is called GraphRAG. The system follows chains of relationships to collect connected facts, then gives them to the LLM. It shines with structured, domain-specific data where questions involve "who / why / what caused what".

GraphRAG answering a multi-step question
Question:"Who fixed the payment-timeout bug mentioned in the Checkout Guide?"
Path through the graph
1. Find the starting node: Checkout Guide
2. Follow "has_section" → Section 4: Payment errors
3. Follow "mentions" → Ticket #402 (payment timeout)
4. Follow "resolved_by" → Commit a1b2c3
5. Follow "written_by" → Ananya
Answer: Ananya fixed it in commit a1b2c3
🎯 Interview tip"Vector search tells me what is similar; a graph tells me what is connected. For multi-hop questions like root cause or 'who changed this', I'd use hybrid retrieval: vector search to find the starting point, then graph traversal to follow the links."

1.7 Context engineering: packing the perfect suitcase

Here is a mindset shift that experienced AI engineers share: building with LLMs is mostly a data-pipeline problem, not a prompt-writing problem. The clever wording of a prompt matters far less than which information you put in front of the model at the moment it answers.

Your knowledge lives in long-term memory (a vector database with millions of chunks). The model can only see its short-term memory (the context window, a few thousand to a few hundred thousand tokens). Context engineering is the practice of designing, building and managing everything the model sees before it answers: the instructions, the right facts, the tools, and the rules.

The funnel: from millions of tokens to the few that matter

What is "re-ranking"?Vector search is fast but rough: it might return 50 "kind of related" chunks. A re-ranker is a second, more careful model that reads the question and each of those 50 chunks together and scores how well each one actually answers the question. We keep only the top 5. Fast-and-rough first, slow-and-careful second.

The four jobs of context engineering

1. Assemble information dynamically
Build the context fresh for every turn:
  • System instructions: role and behaviour ("You are a helpful support agent")
  • Conversation history (memory): so the chat feels continuous
  • External knowledge (RAG): up-to-date facts from your database or the web
2. Manage the window
  • Prioritise: what matters most for this step?
  • Compress: summarise or filter big data into fewer tokens
3. Orchestrate tools
Connect external tools and APIs (Application Programming Interfaces). The model needs clear descriptions to decide when to use a tool, how to call it, and how to blend the result into its answer.
4. Keep it consistent and reliable
Control what the model sees in a systematic way so that answers stay accurate, consistent and within policy across different users and sessions.

1.8 AI agents: from answering to doing

In a simple AI app, the LLM is called once (or a few times in a fixed order) and the code decides every step. That works well for routine tasks. But some goals are open-ended: "find out why last night's deployment failed and open a fix". Nobody can write the steps in advance. That's where agents come in.

An AI agent is a system where an AI model reasons, plans and takes a series of actions on its own to reach a goal. The key difference: the path is decided at run time by the model, not hard-coded by you. You give the goal; the agent figures out the steps. It works in a loop often called ReAct (Reason + Act):

The agent loop (repeat until the goal is done)
🗺 1. Planbreak the goal into steps
🛠 2. Actpick a tool: search, run code, query a DB, read a file
🤔 4. Reasoncompare goal + plan + new info → next step, or "done"
👀 3. Observeadd the tool's result to the context
Goal: "Is my Chennai → Bengaluru train tomorrow running on time? If it's late by more than an hour, tell my family on WhatsApp."
🧠 Think of it like…A plain LLM is like asking a friend a question and getting an answer. An agent is like a personal assistant you tell "plan our Kerala trip". They check flights (act), see they're expensive (observe), think a train might be better (reason), change the plan (plan), and keep going until the booking is done. ✈️🚆
🚀 Going deeper: agents need seatbeltsAgents can get stuck in loops, burn money calling the model again and again, or call the wrong tool. Good designs always include: a maximum number of steps and a token budget, only the tools this task needs (with the smallest permissions), and human approval before any high-impact action like sending money or deleting data. Chapter 2 covers this as "excessive agency".

1.9 Modalities: more than just text

People understand the world through sight, sound and touch, not only text. Modern AI is similar. Each type of data is called a modality, and models that handle several at once are called multimodal.

📝 Text
Written language: translation, summaries, chatbots.
🖼 Images
Recognising objects, reading a photo of a bill, checking a damaged-product photo for a refund.
🎧 Audio
Speech to text, voice assistants, call-centre analytics, music generation.
🎬 Video
Moving images plus audio: summarising a lecture recording, content moderation.
🧊 Spatial / 3D
Understanding depth and 3D space: self-driving cars, robots, AR apps.
🏗 System-design impact
Images and video use far more tokens than text, so they cost more and are slower. Plan upload size limits, compress media, and process big files in the background.

1.10 Where does your data live? Data residency and compliance

Speed and cost aren't the only concerns. Big companies, banks and hospitals also ask: where is our data stored and processed, and who can see it? This is called data residency, and it is often the first filter when choosing how to run an LLM. In India, for example, payment data must be stored in the country, and the Digital Personal Data Protection (DPDP) Act sets rules for handling personal data.

Three ways to run an LLM: more control means more work
🌐 Public API
e.g. calling OpenAI or Anthropic directly over the internet. Easiest to start. But your data leaves your private network (your VPC, Virtual Private Cloud). For health records (PHI), card data (PCI) or other personal data (PII), this is often not allowed unless the provider signs a zero-retention agreement (they promise not to store your data).
☁️ Private cloud
e.g. Amazon Bedrock or Azure OpenAI inside your cloud account. Data stays inside your cloud boundary and region. You still depend on the cloud provider's availability and model list.
🏠 Self-hosted open model
e.g. running Llama 3.1 or Mistral on your own GPUs. Full control: data never leaves. Needed for strict or offline ("air-gapped") environments. The price: you manage GPUs, scaling, updates and on-call.

1.11 Measuring performance: how good and how fast?

A simple engineering rule: you can't improve what you don't measure. For AI, "smart" and "fast" are different things, so we measure them separately.

🎓 Quality benchmarking
How smart and accurate is the model for my task? Does it summarise our tickets well? Does it pick the right category? You run it on a fixed set of test examples and score the results.
⚡ Speed benchmarking
How fast and efficient is it? How long until the first word appears, how many tokens per second, how many users at once? This answers the business question: how fast and how expensive is it to run?

Building your own quality benchmark in 4 steps

Public leaderboards tell you which model is good at general tests. But you care about your task. So build a custom benchmark:

  1. Define the goal. What exactly must the model do well? "Summarise customer support tickets accurately, with the right sentiment and topic."
  2. Create a "golden set". Hand-write 50–100 high-quality examples, each with an input and the ideal output.
    Input: "This is the 3rd time I'm writing! I was charged twice for order #1234 and nobody replies!!" Ideal output: {"summary": "Customer charged twice for order #1234, no response to earlier messages.", "sentiment": "negative", "topic": "billing"}
  3. Run the models. Run every model you want to compare (say gpt-6.1-terra vs a self-hosted Llama 3.1 8B) on all inputs in the golden set.
  4. Evaluate. Two options: human evaluation (an expert scores each answer 1–5; the most reliable, but slow) or LLM-as-a-judge (a strong model grades the answers; fast and scalable). A judge prompt might be:
    You are an expert reviewer. Here is an INPUT, the IDEAL answer, and a MODEL answer. Score the MODEL answer from 1 to 5 for accuracy compared to the IDEAL. Reply as JSON: {"score": n, "reason": "..."}
    Example judge output: {"score": 4, "reason": "Correct issue and sentiment; missed that earlier messages went unanswered."}

🔍 Worked example: estimating total latencyA simple formula: Total latency ≈ TTFT + (output tokens ÷ TPS).
If TTFT = 0.5 s, the answer is 300 tokens, and the model produces 60 tokens per second: 0.5 + 300 ÷ 60 = 0.5 + 5 = 5.5 seconds.
Ask for a 100-token answer instead: 0.5 + 100 ÷ 60 ≈ 2.2 seconds. Shorter output is the biggest speed lever you have, which is exactly the token lesson from section 1.3.

1.12 When things go wrong: the three classic failures

🤥 Hallucination
The model confidently makes up something false, because it sounds statistically plausible. Example: inventing a refund policy, a court case, or a Python function that doesn't exist.
Fix: ground it with real data (RAG), ask it to say "I don't know" when unsure, and verify important outputs.
📅 Knowledge cut-off
A model's knowledge is frozen at the time its training data was collected. Ask about last week's news or today's prices and it simply doesn't know (or worse, guesses).
Fix: provide fresh information at question time via RAG, tools or web search.
⚖️ Bias
The hardest one. Models learn from huge amounts of human writing, and human writing contains biases (about gender, region, caste, language…).
Manage it: filter training data, add guardrails in prompts, test with diverse examples, and collect human feedback.
🧠 Think of it like…Hallucination is like that uncle who never says "I don't know" when you ask for directions: "Haan haan, go straight, then second left!" 😅 Confident, and wrong. RAG is handing him Google Maps before he answers.

1.13 Summary: LLMs are not magic

LLMs are probabilistic engines with hard limits. Every design decision you make trades off three things:

The quality–cost–latency triangle: you can usually pick two
DimensionMainly decided by
💸 CostHow many input tokens you send + how big the model is
⏱ LatencyHow many output tokens you ask for + time spent retrieving data
🎯 QualityWhat you put in the context window + how strong the model's reasoning is

The real skill of AI engineering is not writing magic prompts; it is managing these constraints. The rest of this series is about patterns for exactly that: RAG to work around limited context, caching for speed, routing for cost, and much more. Now that you know the atoms, let's start building molecules. 🧱

✅ Key takeaways
  • LLMs are probabilistic; we build systems around them to make them dependable.
  • Tokens drive speed, cost and limits. Output tokens are slow and expensive; keep answers short.
  • Embeddings turn meaning into numbers so we can search by meaning.
  • Facts → RAG. Style and behaviour → fine-tuning.
  • Good prompts have persona, context, instruction and format, plus guardrails and examples.
  • ASTs give code structure; knowledge graphs give relationships; vectors give similarity.
  • Context engineering = choosing what goes into the limited context window.
  • Agents loop through plan → act → observe → reason, and need limits and approvals.
  • Measure both quality (golden sets, judges) and speed (TTFT, TPS, total latency).

📝 Quick quiz (click to reveal the answer)

Q1. Why is generating output tokens slower than reading input tokens?Input tokens are processed together in parallel. Output tokens are generated one at a time, because each new token depends on all the previous ones. So to reduce latency, limit the output length.
Q2. What's the difference between the sliding-window and summarization strategies?Sliding window simply drops the oldest messages (free, but the model forgets them). Summarization compresses old messages into a short summary (keeps the gist, but costs one extra LLM call).
Q3. Two sentences share no words at all. Can their embeddings still be close?Yes. Embeddings capture meaning, not exact words. "How do I get my money back?" and "refund process" will be close together.
Q4. Your bot doesn't know this month's prices. Fine-tune or RAG?RAG. Prices change often; fetch them at question time. Fine-tuning is better for teaching style, tone and format.
Q5. Why might a retry at temperature 0 be pointless?At temperature 0 the model gives (nearly) the same output for the same input. If the first output was broken JSON, the retry will likely be broken in the same way. A slightly higher temperature gives a chance of a different, correct output.
Q6. Name two reasons basic RAG can fail.(1) Similar is not always relevant: many near-duplicate chunks crowd the context. (2) Poor chunking: the question matches a document's title, but the real answer is buried deep in a section that wasn't retrieved.
Q7. When would you use GraphRAG instead of plain vector search?When the question is about relationships across several steps ("who fixed the bug mentioned in this guide?", root-cause questions), especially with structured, connected data.
Q8. What are the three data-cleaning steps before embedding?De-noising (remove HTML and boilerplate), PII scrubbing (remove phone numbers, emails, IDs, keys before data goes to an external API), and normalisation (consistent dates, currency and characters).
Q9. TTFT is 0.4 s, the answer is 240 tokens, and TPS is 80. Roughly how long is the total latency?0.4 + 240 ÷ 80 = 0.4 + 3 = 3.4 seconds.
Q10. Why do agents need a maximum step count?Without it, an agent can loop forever, burning tokens and money, or keep calling tools wrongly. A step limit (and token budget) is a safety stop.

📖 Glossary

TermMeaning in one line
LLMLarge Language Model: an AI trained on huge text to read and write language.
PromptThe text you send to the model.
TokenA small piece of text (≈ 4 characters) that the model reads and writes.
Context windowThe most tokens a model can handle in one request (input + output).
Embedding / vectorA list of numbers that represents meaning.
Vector databaseA database that stores vectors and finds the closest ones fast.
Cosine similarityA score from −1 to 1 of how closely two vectors point in the same direction.
ANN / HNSWFast "approximately nearest" search methods for vectors.
Pre-training / fine-tuningGeneral learning from huge data / extra focused learning on small data.
RAGRetrieve facts, add them to the prompt, then generate the answer.
Re-rankingA second, careful scoring step that keeps only the best retrieved chunks.
ASTAbstract Syntax Tree: the nested structure of code.
Knowledge graphData stored as things (nodes) and relationships (edges).
TemperatureA setting that controls how random the model's word choices are.
HallucinationA confident but false answer.
Agent / ReActA model that loops through reasoning and tool actions to reach a goal.
TTFT / TPSTime to first token / tokens per second.
PIIPersonally identifiable information: phone, email, ID numbers, etc.
