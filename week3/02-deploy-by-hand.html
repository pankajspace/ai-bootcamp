    The plan at a glance

    The eleven steps fall into five phases. Opening a new shop is a fair picture of it.

    PrepareSteps 1–2. Check your identity and rent the storage room for your images.
    PackSteps 3–4. Package the app into images, ship them, lock the keys in the safe.
    BuildStep 5. One command builds the network, disk, servers and front door.
    Open upSteps 6–9. Check everything is running, then use it.
    CloseSteps 10–11. Pause it to save money, or remove it completely.

    Step 5 does the heavy lifting and takes about seven minutes. Everything else is quick.

    Teaching tip

    In a live class, start Step 5 and then walk through the architecture diagram and the “one request, end to end” stepper from Part 1 while CloudFormation builds. The waiting time becomes the best explanation time of the session.

    1. Prepare your terminal

    echo 'setopt interactivecomments' >> ~/.zshrc
echo 'export AWS_PAGER=""' >> ~/.zshrc
setopt interactivecomments
export AWS_PAGER=""
    setopt interactivecomments
    Makes zsh (the Mac's default shell) treat # as the start of a comment, as bash does. Without it, pasting any block that has a # note in it fails with odd errors such as zsh: unknown sort specifier or command not found: #.
    AWS_PAGER=""
    Prints AWS output straight to the screen. Otherwise long JSON opens in a viewer that waits until you press q.
    >> ~/.zshrc
    Adds the line to the file every new terminal reads at start-up, so you never type it again. The last two lines apply it to the terminal you have open now.

    On bash (Linux, WSL, Git Bash)

    Comments already work. Run only echo 'export AWS_PAGER=""' >> ~/.bashrc, and wherever this page says ~/.zshrc, use ~/.bashrc.

    2. Connect the AWS CLI to your account

    Pick the option that matches the login you have. Option A if you sign in through an AWS access portal (a page listing your AWS accounts, each with a role such as AdministratorAccess and an Access keys link). Option B if you have an IAM user and an access key.

    Option A: SSO login (access portal)

    First collect two values. In the access portal, click Access keys next to your role, and copy the SSO start URL and SSO region from the AWS IAM Identity Center credentials section. Then run:

    aws configure sso

    Answer its questions like this:

    SSO session name
    scaler (any short name works)
    SSO start URL
    Paste it from the portal. It looks like https://d-xxxxxxxxxx.awsapps.com/start.
    SSO region
    Paste it from the portal, for example us-west-2. This is only where your login lives. It does not decide where you deploy.
    SSO registration scopes
    Press Enter to accept the default.
    A browser opens
    Sign in if asked, then click Allow. Come back to the terminal.
    Account and role
    Picked automatically if you have only one. Otherwise choose the account and role meant for this lab.
    CLI default client Region
    us-east-1. It must match REGION in the variables below.
    CLI default output format
    json
    CLI profile name
    scaler. This is the name the next block uses.

    Make that profile the default for every terminal, then check it:

    echo 'export AWS_PROFILE=scaler' >> ~/.zshrc
export AWS_PROFILE=scaler
aws sts get-caller-identity

    What you should see

    A JSON block with your 12-digit "Account" and an Arn like arn:aws:sts::123456789012:assumed-role/AWSReservedSSO_YourRole_1a2b3c…/you@company.com.

    Common mistake

    Old access keys left in the shell override the profile, so commands go to the wrong account. If get-caller-identity shows an account you did not expect, run unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN and try again.

    An SSO login lasts a few hours. When a command says Token has expired or The SSO session associated with this profile has expired, run aws sso login. The first block in Set your variables does this for you when it is needed.

    Option B: IAM access key

    aws configure

    It asks four questions:

    Access Key ID
    The username half of your CLI login. From IAM, your user, Security credentials, Create access key.
    Secret Access Key
    The password half. Shown only once when you create it. Treat it like a bank PIN: never paste it into chat, code or screenshots.
    Default region
    us-east-1. Mumbai (ap-south-1) also works and is closer to India; prices differ slightly.
    Default output format
    json

    3. Create the two service-linked roles

    aws iam create-service-linked-role --aws-service-name ecs.amazonaws.com
aws iam create-service-linked-role --aws-service-name elasticloadbalancing.amazonaws.com

    A service-linked role is a permission that an AWS service needs to act inside your account; ECS uses it to attach network cards to your tasks, the load balancer uses it to register targets. Brand-new accounts sometimes do not have them yet, and the first deployment fails in a confusing way.

    What you should see

    Either a block of JSON describing the new role, or An error occurred (InvalidInput) … Service role name AWSServiceRoleForECS has been taken in this account. Both are fine. Ignore the word error: “taken” just means the role already exists. This is normal on shared or company accounts.

    If you get AccessDenied instead, your role may not be allowed to create IAM roles. Check whether they already exist:

    aws iam get-role --role-name AWSServiceRoleForECS --query Role.RoleName
aws iam get-role --role-name AWSServiceRoleForElasticLoadBalancing --query Role.RoleName

    Two role names printed means you are fine. NoSuchEntity means you need to ask your AWS administrator to create that role.

    Set your variables

    Every command below uses a few shell variables. A variable is a sticky note the terminal remembers: you write REGION=us-east-1 once, and every later $REGION is replaced with us-east-1. The notes disappear when you close the terminal, so run these four blocks at the start of every new terminal session, from the project folder. Paste each block on its own, in order.

    Block 1. Log in again if your SSO login has expired. Does nothing when you are still logged in.

    aws sts get-caller-identity >/dev/null 2>&1 || aws sso login

    Block 2. The variables.

    VERSION=v1
REGION=us-east-1
OPENAI_MODEL=gpt-4o-mini
[ -f ~/.inventory-api-key ] || (umask 077; openssl rand -hex 24 > ~/.inventory-api-key)
API_KEY=$(cat ~/.inventory-api-key)
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
ECR=$ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com
STACK=inventory-stack-$VERSION
CLUSTER=inventory-$VERSION

    Block 3. Your OpenAI key. Paste this line alone and press Enter, then paste the key and press Enter. Nothing shows on screen.

    read -rs OPENAI_API_KEY

    Block 4. Check everything is filled in.

    echo "openai: ${#OPENAI_API_KEY} chars | api: ${#API_KEY} chars | $OPENAI_MODEL | $ECR | $STACK | $CLUSTER"

    What you should see

    openai: 164 chars | api: 48 chars | gpt-4o-mini | 123456789012.dkr.ecr.us-east-1.amazonaws.com | inventory-stack-v1 | inventory-v1, with your own account number. The OpenAI count varies by key type; anything well over 50 is fine. If openai shows 0, redo Block 3. If the registry starts with .dkr or is empty, run Block 1 and then Block 2 again.

    VERSION
    Goes into every resource name, so v1 and v2 can live side by side. Lowercase letters, digits and dashes, at most 12 characters. Increase it for each new deployment.
    REGION
    Where everything is built. us-east-1 here; Mumbai (ap-south-1) also works. Keep it the same as the CLI default region you chose above.
    OPENAI_MODEL
    gpt-4o-mini is the cheapest model with tool calling; gpt-4.1-mini gives better answers.
    API_KEY
    The shared password between frontend and backend. The [ -f … ] || line creates a random one in ~/.inventory-api-key the first time only, readable by you alone. Every later session reads the same file, so the key never changes.
    ACCOUNT_ID
    Your 12-digit account number, fetched automatically. $( … ) means “run this command and use its output here”.
    ECR
    The address of your private image store, built from your account and region.
    read -rs
    Asks for the key without showing it (-s), so it never lands on screen or in your shell history. It must be pasted alone: in a multi-line paste, read takes the next pasted line as the key.

    Common mistake

    Using a different API_KEY in a later session. Step 4 stores it in AWS, but a running container keeps the value it started with. If you later restart only the frontend, it gets the new key while the backend still has the old one, and every chat fails with Backend error 403. Keep ~/.inventory-api-key and do not delete it. If you already deployed with a key you typed yourself, write that one into the file first: echo 'your-old-key' > ~/.inventory-api-key.

    Common mistake

    When one line of a pasted block fails, zsh skips the rest of that paste, so later variables stay empty. Fix the error, then paste the block again. Block 4 shows you straight away if anything is missing.

    The eleven steps

    1

    Check who you are logged in as

    Make sure the CLI is talking to the account you think it is.

    aws sts get-caller-identity
echo "Account: $ACCOUNT_ID   Region: $REGION   Registry: $ECR"
    sts get-caller-identity
    STS is AWS's identity desk. This call asks “who am I?” and works with any login, even one with no other permissions, so it is the safest first check.
    "Account"
    The 12-digit number of the account every following command will change.
    "Arn"
    Your full AWS name. For an SSO login, read it in three parts: assumed-role means you are temporarily wearing a role; AWSReservedSSO_InstructorsAdministratorAccess_… is the role SSO made for your access (here, administrator); the last part is who is wearing it, usually your email.
    echo "…$ACCOUNT_ID…"
    Prints the variables back to you, so you can see they are filled in before anything is built with them.

    What you should see

    A small JSON block with "Account": "123456789012" and an Arn ending in your user name (access key) or in assumed-role/AWSReservedSSO_…/your-email (SSO login), then the echo line with your registry address filled in. If Registry shows .dkr.ecr.us-east-1… with no number at the front, the variables block failed: run it again.

    Why this step exists

    Many people have a work account and a personal account configured. Deploying a class demo into your company's production account is an expensive way to learn this lesson.

    2

    Create the image repositories

    Rent two shelves in ECR, your private image store (ECR in Part 1). First time only.

    aws ecr describe-repositories --repository-names inventory-backend --region $REGION >/dev/null 2>&1 \
  || aws ecr create-repository --repository-name inventory-backend --region $REGION

aws ecr describe-repositories --repository-names inventory-frontend --region $REGION >/dev/null 2>&1 \
  || aws ecr create-repository --repository-name inventory-frontend --region $REGION
    describe-repositories
    Asks “does this repository exist?”
    create-repository
    Creates an empty, private folder for one image. Every tag you push later (v1, v2…) is one more version inside it. Only your account can read it.
    --region $REGION
    Says which AWS location to work in. Every command on this page passes it, so nothing lands in a different region by accident.
    >/dev/null 2>&1
    Throws away that command's output and errors; we only care whether it succeeded.
    ||
    “Or else”: run the create command only if the check failed.
    \ at line end
    The command continues on the next line.

    Together this makes the step idempotent: safe to run any number of times. Like pressing a lift button twice, the second press changes nothing.

    What you should see

    First run: JSON describing each new repository, including a repositoryUri. Later runs: no output at all, which means they already exist.

    3

    Build the images and push them to ECR

    Pack the frontend and backend into container images, then ship them to your private store.

    aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $ECR

# Build from the project root: the backend Dockerfile copies db/schema.sql
docker build --platform linux/amd64 -f backend/Dockerfile -t $ECR/inventory-backend:$VERSION .
docker build --platform linux/amd64 -f frontend/Dockerfile -t $ECR/inventory-frontend:$VERSION .

docker push $ECR/inventory-backend:$VERSION
docker push $ECR/inventory-frontend:$VERSION
    get-login-password | docker login
    AWS prints a temporary password (valid 12 hours) and the pipe | hands it straight to Docker, so it never appears on screen.
    --username AWS --password-stdin $ECR
    For ECR the user name is always the literal word AWS. --password-stdin reads the password from the pipe instead of the command line, so it is not saved in your history. $ECR says which registry this pass is for.
    docker build
    Follows the Dockerfile line by line: start from Python 3.11, copy the code, pip install the libraries. Each line becomes a layer; the build log shows them as [1/6] to [6/6]. Unchanged layers are reused next time, which is why rebuilds are fast.
    --platform linux/amd64
    Build for x86 processors, which our Fargate tasks use. Essential on Apple Silicon Macs (why).
    -f backend/Dockerfile
    Which recipe to follow.
    -t …:v1
    The name and tag to stick on the image.
    . (the final dot)
    The build context: the folder Docker may copy files from. It must be the project root, because the backend needs db/schema.sql from outside the backend folder.
    docker push
    Uploads the image to ECR one layer at a time. Each Pushed line is one layer; a layer ECR already has shows Layer already exists and is skipped. The final digest: sha256:… is the image's fingerprint: the same digest always means exactly the same image.
    Reading an image name, piece by piece

    123456789012.dkr.ecr.us-east-1.amazonaws.com/inventory-backend:v1 is like a full postal address:

    • 123456789012: your account (the building)
    • dkr.ecr.us-east-1.amazonaws.com: ECR in your region (the city's post office)
    • inventory-backend: the repository (the flat)
    • v1: the tag (which parcel in that flat)

    What you should see

    Login Succeeded, then build output ending in lines like naming to …/inventory-backend:v1. The first build takes 2–5 minutes because it downloads Python and the libraries; rebuilds are faster thanks to Docker's layer cache. Each push ends with v1: digest: sha256:… size: ….

    If it fails

    Cannot connect to the Docker daemon: start Docker Desktop. no basic auth credentials on push: the 12-hour login expired, re-run the first line. repository … does not exist: Step 2 ran in a different region; check echo $REGION.

    4

    Store the two secrets in Parameter Store

    Put the OpenAI key and the internal API key in AWS's safe, so containers can receive them without the keys ever being written into code or configuration (SSM in Part 1).

    First, confirm the API key you are about to store is the one saved in ~/.inventory-api-key:

    [ "$(cat ~/.inventory-api-key)" = "$API_KEY" ] && echo "API key saved and matches"

    If it does not print API key saved and matches, run Block 2 of Set your variables again. Then store both secrets:

    aws ssm put-parameter --name /inventory/openai-api-key --type SecureString --value "$OPENAI_API_KEY" --overwrite --region $REGION
aws ssm put-parameter --name /inventory/api-key --type SecureString --value "$API_KEY" --overwrite --region $REGION
    ssm put-parameter
    Saves one value in Parameter Store, part of AWS Systems Manager (SSM). The value goes from your terminal straight to AWS; nothing is written into the project files or the images.
    --name /inventory/…
    Names look like folder paths, so related secrets group together and permissions can cover a whole folder.
    --type SecureString
    Encrypt the value with KMS. A plain String would be readable by anyone who can view parameters.
    "$OPENAI_API_KEY"
    The quotes protect values containing special characters.
    --overwrite
    Replace the value if it already exists. This is how you rotate a key later: run the same command with the new value.

    What you should see

    {"Version": 1, "Tier": "Standard"} for each. The version number goes up every time you overwrite. Standard-tier parameters are free.

    5

    Deploy the stack: network, disk, servers and front door

    Hand the blueprint (infra/inventory-stack.yaml) to CloudFormation and let it build the about 35 resources in the right order.

    aws cloudformation deploy \
  --region $REGION \
  --stack-name $STACK \
  --template-file infra/inventory-stack.yaml \
  --capabilities CAPABILITY_IAM \
  --disable-rollback \
  --no-fail-on-empty-changeset \
  --parameter-overrides \
    Version=$VERSION \
    BackendImage=$ECR/inventory-backend:$VERSION \
    FrontendImage=$ECR/inventory-frontend:$VERSION \
    OpenAIModel=$OPENAI_MODEL \
    OpenAIKeyParameterName=/inventory/openai-api-key \
    ApiKeyParameterName=/inventory/api-key
    cloudformation deploy
    Creates the stack the first time and updates it on later runs. You never decide between “create” and “update”: CloudFormation compares the blueprint with what exists and does only the difference.
    --stack-name
    The name for this whole bundle of resources: inventory-stack-v1.
    --template-file
    The blueprint to build from.
    --capabilities CAPABILITY_IAM
    An “I agree” checkbox. The template creates IAM roles, and AWS wants your explicit consent before any stack creates permissions.
    --disable-rollback
    Normally a failed build is torn down automatically. We keep the half-built resources so you can read the error and the logs instead of watching the evidence disappear.
    --no-fail-on-empty-changeset
    Running the command again with nothing changed is treated as success, not an error.
    --parameter-overrides
    Fills in the blanks of the template: which version, which images, which model, where the secrets live.
    The six blanks, one by one
    Version
    Added to every resource name, so v1 and v2 never clash.
    BackendImage, FrontendImage
    The full ECR addresses from Step 3. ECS pulls exactly these images when it starts a container.
    OpenAIModel
    Passed to the backend as a setting, so you can switch models by redeploying, without rebuilding the image.
    OpenAIKeyParameterName, ApiKeyParameterName
    Only the names of the secrets from Step 4, never the values. ECS fetches the values from Parameter Store when a container starts, so the keys never appear in CloudFormation, the console or the logs.

    What CloudFormation does during those minutes

    deploy first creates a change set, a list of everything it is about to do (like a builder's quote), then executes it. Resources that depend on each other are built in order; independent ones are built in parallel. Roughly:

    1. Network (under a minute): VPC, two subnets, internet gateway, route table, four security groups.
    2. Disk (1–2 minutes): EFS file system, a mount target in each subnet, the access point.
    3. Plumbing (1–2 minutes, in parallel): IAM roles, log groups, the ECS cluster, the private DNS namespace.
    4. Front door (2–3 minutes): the load balancer, its target group and listener.
    5. Backend service (about 2 minutes): ECS starts the task, mounts EFS, injects secrets, runs init_db.py, and waits for the health check to pass.
    6. Frontend service (about 2 minutes): starts after the backend, then registers with the load balancer.
    Watch it being built, from a second terminal

    Run the variables block in the new terminal first, then repeat this command every half minute:

    aws cloudformation describe-stack-events --stack-name $STACK --region $REGION --max-items 12 \
  --query "StackEvents[].[Timestamp,LogicalResourceId,ResourceStatus]" --output table

    Or open the AWS console, CloudFormation, Stacks, inventory-stack-v1, Events tab. The newest events are at the top.

    What you should see

    Waiting for changeset to be created.. (CloudFormation is writing its quote), then Waiting for stack create/update to complete (it is building), and after 6–8 minutes Successfully created/updated stack - inventory-stack-v1 (every resource is built and both services passed their health checks).

    If it fails

    The command prints Failed to create/update the stack. Use the four-question method in Troubleshooting: the first FAILED event tells you which resource broke and why. Fix the cause and run Step 5 again. If CloudFormation refuses to update a failed stack, delete it (Step 11) and redeploy.

    6

    Check that both services are running

    Confirm ECS is keeping one healthy copy of each, and read the backend's start-up log.

    aws ecs describe-services --cluster $CLUSTER --services inventory-backend inventory-frontend --region $REGION \
  --query "services[].{name:serviceName,desired:desiredCount,running:runningCount,status:status}" --output table

# Backend start-up log
aws logs tail /ecs/inventory-$VERSION/backend --region $REGION --since 15m

    The --query option is a filter (in a language called JMESPath) that picks just the fields you care about out of a very large JSON answer. Without it, describe-services prints hundreds of lines.

    desired vs running
    desired is how many copies you asked ECS to keep alive; running is how many are up right now. When they match, ECS is happy. If running stays at 0, a container keeps crashing: read the log.
    --output table
    Prints the result as a small table instead of JSON, easier to read at a glance.
    logs tail … --since 15m
    Shows what the backend printed in the last 15 minutes, the same lines you would see in your terminal when running it locally. Add --follow to keep watching live; press Ctrl+C to stop.

    What you should see

    A table where both services show desired 1, running 1, status ACTIVE. In the log: Database initialized and seeded at: /app/data/inventory.db and Uvicorn running on http://0.0.0.0:8000.

    7

    Get the backend's internal address

    Read the backend URL from the stack's outputs, and understand why you cannot open it.

    aws cloudformation describe-stacks --stack-name $STACK --region $REGION \
  --query "Stacks[0].Outputs[?OutputKey=='BackendInternalURL'].OutputValue" --output text

    Stack outputs are the builder's handover sheet: the useful addresses and names CloudFormation created, so you do not have to hunt for them in the console.

    What you should see

    http://backend.inventory-v1.local:8000. This name exists only inside the VPC, and the backend accepts traffic only from the frontend. From your laptop it will not resolve, and that is the security design working. Step 8 shows how to test it from the inside.

    8

    Test the backend from inside (optional)

    Open a shell inside the running frontend container and call the backend the way the frontend does.

    ECS Exec is like SSH into a container, but without opening any port: the connection is relayed through AWS Systems Manager, and permission comes from the task role. It needs the Session Manager plugin on your laptop.

    TASK_ARN=$(aws ecs list-tasks --cluster $CLUSTER --service-name inventory-frontend --region $REGION --query "taskArns[0]" --output text)

aws ecs execute-command --cluster $CLUSTER --task $TASK_ARN --container frontend --interactive --command "/bin/sh" --region $REGION

    You are now inside the container. BACKEND_URL and API_KEY are already set there as environment variables:

    # 1. Is the backend alive?
python -c "import os,urllib.request; print(urllib.request.urlopen(os.environ['BACKEND_URL']+'/health').read())"

# 2. Ask the agent a question, exactly like the chat page does
python -c "import os,requests; r=requests.post(os.environ['BACKEND_URL']+'/chat', json={'query':'Should I reorder SKU001?','sku_id':'SKU001'}, headers={'X-API-Key':os.environ['API_KEY']}, timeout=90); print(r.status_code, r.text)"

exit

    What you should see

    b'{"status":"ok"}', then 200 {"session_id":"…","response":"…"} with the agent's answer. A 502 with AuthenticationError means the OpenAI key is wrong (see Troubleshooting).

    If it fails

    SessionManagerPlugin is not found: install the plugin. TargetNotConnectedException: the task started less than a minute or two ago and the exec agent is not ready yet; wait and retry.

    9

    Open the app in your browser

    Get the public URL and use the agent.

    URL=$(aws cloudformation describe-stacks --stack-name $STACK --region $REGION \
  --query "Stacks[0].Outputs[?OutputKey=='FrontendURL'].OutputValue" --output text)
echo $URL

    It prints something like http://inventory-v1-alb-123456789.us-east-1.elb.amazonaws.com. Open it, and note it is http, not https.

    Outputs[?OutputKey=='FrontendURL']
    From the stack's handover sheet, pick the one line called FrontendURL.
    --output text
    Plain text without quotes, so it can be saved straight into the URL variable.

    If the browser says “This site can't be reached” or ERR_CONNECTION_TIMED_OUT

    Usually the browser quietly tried https, which this app does not serve, and waited until it gave up. Ask the load balancer directly, without a browser:

    curl -s -o /dev/null -w "HTTP %{http_code}\n" --max-time 15 "$URL" || echo "no answer (timeout)"

    HTTP 200 means AWS is fine. Open the address in an Incognito window and type http:// in front, or use Safari (open -a Safari "$URL" on a Mac). If Chrome still times out, turn off Always use secure connections in Chrome's Settings, Privacy and security, Security. If curl also times out, your network (office Wi-Fi, VPN or proxy) is blocking it: try a phone hotspot.

    A five-minute test script

    1. Type SKU001 in the SKU box and click Lookup SKU. You should see 100 units, 10 a day, 7 days, 20 safety stock. This proves frontend → backend → database works without OpenAI.
    2. Ask Should I reorder SKU001? Expect “not yet, about 1 day”. This proves the OpenAI key and both tools.
    3. Ask How much should I order for SKU002? Expect 55 units.
    4. Ask Inventory is 50, demand is 8 a day, lead time is 5 days. What do I do? The agent should skip the database and use only the calculator.

    What you should see

    The first page load after deployment can take up to a minute while the load balancer's health checks pass; a 503 during that time is normal. Answers take a few seconds, mostly waiting for OpenAI.

    Experiment: prove the database survives a restart

    This is the classroom moment that makes EFS click. Change a product, kill the backend, and check the change is still there.

    # a) Change SKU001's stock to 50, from inside the frontend container
TASK_ARN=$(aws ecs list-tasks --cluster $CLUSTER --service-name inventory-frontend --region $REGION --query "taskArns[0]" --output text)
aws ecs execute-command --cluster $CLUSTER --task $TASK_ARN --container frontend --interactive --command "/bin/sh" --region $REGION
python -c "import os,requests; print(requests.post(os.environ['BACKEND_URL']+'/inventory', json={'sku_id':'SKU001','name':'Widget A','current_inventory':50,'avg_demand':10,'lead_time':7,'safety_stock':20}, headers={'X-API-Key':os.environ['API_KEY']}).json())"
exit

# b) Replace the backend task with a brand-new one, and wait until it is healthy
aws ecs update-service --cluster $CLUSTER --service inventory-backend --force-new-deployment --region $REGION
aws ecs wait services-stable --cluster $CLUSTER --services inventory-backend --region $REGION

    Now click Lookup SKU for SKU001 again. It shows 50, not 100: the old container is gone, the new one mounted the same EFS drive, and init_db.py left your edit alone because the sample data is only inserted when missing. Ask Should I reorder SKU001? and the answer changes to “yes, reorder 110 units” (reorder point 90 + one more lead time of 70 − the 50 on hand).

    10

    Pause the containers to save money (optional)

    Stop paying for the containers while nobody is using the app, without deleting anything.

    # Pause: zero running copies
aws ecs update-service --cluster $CLUSTER --service inventory-frontend --desired-count 0 --region $REGION
aws ecs update-service --cluster $CLUSTER --service inventory-backend --desired-count 0 --region $REGION

# Resume: backend first, then frontend (1-2 minutes; the database on EFS is kept)
aws ecs update-service --cluster $CLUSTER --service inventory-backend --desired-count 1 --region $REGION
aws ecs update-service --cluster $CLUSTER --service inventory-frontend --desired-count 1 --region $REGION
aws ecs wait services-stable --cluster $CLUSTER --services inventory-backend inventory-frontend --region $REGION

    --desired-count tells the service how many copies to keep running (the shift manager's rule from Part 1). Zero means none.

    Remember the rented car

    Pausing switches the engine off, but you still pay for the parking spot: the load balancer, its two public addresses and the DNS zone, roughly $1 a day. Unlike Azure Container Apps, ECS will not wake up by itself when someone visits; you run the resume commands. For a demo that is finished, delete the stack instead (Step 11).

    11

    Delete this deployment

    Remove every resource the stack created, with one command.

    aws cloudformation delete-stack --stack-name $STACK --region $REGION
aws cloudformation wait stack-delete-complete --stack-name $STACK --region $REGION   # 5-8 minutes
echo "Deleted $STACK"

    The wait command simply blocks until AWS reports the deletion finished, so you know when it is safe to walk away. CloudFormation deletes in the reverse order it built: services first, then the load balancer, disk, roles and finally the network.

    What gets deleted

    Both services and tasks, the load balancer, the EFS drive including inventory.db, the VPC, subnets, security groups, IAM roles, log groups and the private DNS zone. The ECR images and SSM secrets stay (they are shared between versions), so the next deployment is faster. To remove those too, see Full cleanup.

    If it fails

    If wait reports DELETE_FAILED, AWS was still releasing network cards or a DNS record. Wait two minutes and run the same delete-stack again; it finishes the second time.

    The whole lab in one breath

    You logged in, packed the app into two boxes (images), shipped them to your warehouse (ECR), locked the keys in a safe (Parameter Store), and handed the blueprint to a builder (CloudFormation). The builder made a private network with a front door (load balancer), two workers (frontend and backend containers) and a filing cabinet that survives restarts (EFS). Then you opened the front door in a browser, and finally pulled the building down so the bill stops.

    Updating a running deployment

    You will change code far more often than you build new infrastructure. Pick the smallest update that does the job.

    Changed only the frontend code

    docker build --platform linux/amd64 -f frontend/Dockerfile -t $ECR/inventory-frontend:$VERSION .
docker push $ECR/inventory-frontend:$VERSION
aws ecs update-service --cluster $CLUSTER --service inventory-frontend --force-new-deployment --region $REGION

    Changed only the backend code (the database is kept)

    docker build --platform linux/amd64 -f backend/Dockerfile -t $ECR/inventory-backend:$VERSION .
docker push $ECR/inventory-backend:$VERSION
aws ecs update-service --cluster $CLUSTER --service inventory-backend --force-new-deployment --region $REGION

    --force-new-deployment tells ECS to start fresh tasks, which pull the image again. It is a rolling update: the new task starts, passes its health check, and only then is the old one stopped. Users see no downtime. Watch it with:

    aws ecs describe-services --cluster $CLUSTER --services inventory-backend --region $REGION \
  --query "services[0].events[:5].message" --output table

    Changed a setting (model, CPU, memory)

    Re-run Step 5 with the new value, for example OpenAIModel=gpt-4.1-mini. CloudFormation compares the new blueprint with what exists and changes only the difference: here, a new task definition revision for the backend and a rolling update. Nothing else is touched.

    A whole new version alongside the old one

    Set VERSION=v2, re-run the variables block, then Steps 3, 5, 6 and 9. Version 1 keeps serving at its own URL while you test version 2. When you are happy, delete v1:

    aws cloudformation delete-stack --stack-name inventory-stack-v1 --region $REGION

    A limitation worth noticing

    When you push a new image with the same tag (v1), the old image loses its label. If the new code is broken there is no easy “go back to yesterday's v1”. Part 3 fixes this by tagging every image with the git commit it was built from, so every version stays addressable.

    Full cleanup: remove everything

    Use this at the end of a course, or whenever you want your AWS bill for this project to be zero.

    A. Delete every version's stack

    STACKS=$(aws cloudformation list-stacks --region $REGION \
  --query "StackSummaries[?starts_with(StackName,'inventory-stack-') && StackStatus!='DELETE_COMPLETE'].StackName" --output text)
echo "Deleting: $STACKS"

for S in $STACKS; do aws cloudformation delete-stack --stack-name $S --region $REGION; done
for S in $STACKS; do aws cloudformation wait stack-delete-complete --stack-name $S --region $REGION; done

    The first command collects the names of every stack starting with inventory-stack- that is not already deleted. The two loops delete them all, then wait for each.

    B. Delete the shared images and secrets

    aws ecr delete-repository --repository-name inventory-backend --force --region $REGION
aws ecr delete-repository --repository-name inventory-frontend --force --region $REGION
aws ssm delete-parameter --name /inventory/openai-api-key --region $REGION
aws ssm delete-parameter --name /inventory/api-key --region $REGION

    --force deletes a repository even though it still contains images.

    C. Prove nothing is left

    Every one of these should print an empty list ([]) or an empty table.

    aws cloudformation list-stacks --region $REGION --query "StackSummaries[?starts_with(StackName,'inventory-stack-') && StackStatus!='DELETE_COMPLETE'].[StackName,StackStatus]" --output table
aws ecr describe-repositories --region $REGION --query "repositories[?starts_with(repositoryName,'inventory-')].repositoryName"
aws ssm get-parameters-by-path --path /inventory --region $REGION --query "Parameters[].Name"
aws efs describe-file-systems --region $REGION --query "FileSystems[?Name && starts_with(Name,'inventory-')].FileSystemId"
aws elbv2 describe-load-balancers --region $REGION --query "LoadBalancers[?starts_with(LoadBalancerName,'inventory-')].LoadBalancerName"
aws ec2 describe-vpcs --region $REGION --filters "Name=tag:Name,Values=inventory-*" --query "Vpcs[].VpcId"
aws logs describe-log-groups --region $REGION --log-group-name-prefix /ecs/inventory --query "logGroups[].logGroupName"
aws ecs list-clusters --region $REGION --query "clusterArns[?contains(@,'inventory-')]"

    What legitimately remains

    The two service-linked roles (AWSServiceRoleForECS, AWSServiceRoleForElasticLoadBalancing), your IAM user or SSO profile, and ~/.inventory-api-key on your laptop. All are free. If you created an access key only for this course, deactivate it in IAM. Check Billing, Cost Explorer the next day: charges for this project should have stopped.

    Teaching tip

    End the class by having every learner run section C and show the empty output. “I'm sure I deleted it” is not the same as proof, and that habit will save them money for the rest of their careers.

    Troubleshooting

    A method that works for any failure

    Investigate from the outside in, like a doctor going from symptoms to test results. Ask four questions in order and stop when you find the answer:

    1. Did CloudFormation fail to build something? Look at the failed stack events.
    2. Is the ECS service unhappy? Read the service's recent events.
    3. Did a task start and then stop? Read its stop reason.
    4. Did my code crash? Read the container's log.
    # 1. Which resource failed, and why
aws cloudformation describe-stack-events --stack-name $STACK --region $REGION \
  --query "StackEvents[?contains(ResourceStatus,'FAILED')].[LogicalResourceId,ResourceStatusReason]" --output table

# 2. What the service has been doing
aws ecs describe-services --cluster $CLUSTER --services inventory-backend --region $REGION \
  --query "services[0].events[:10].message" --output table

# 3. Why tasks stopped (ECS remembers stopped tasks for about an hour)
T=$(aws ecs list-tasks --cluster $CLUSTER --desired-status STOPPED --region $REGION --query "taskArns" --output text)
[ -n "$T" ] && aws ecs describe-tasks --cluster $CLUSTER --region $REGION --tasks $T \
  --query "tasks[].{stopped:stoppedReason,container:containers[0].reason}" --output table || echo "no stopped tasks"

# 4. What the code printed
aws logs tail /ecs/inventory-$VERSION/backend --region $REGION --since 30m
aws logs tail /ecs/inventory-$VERSION/frontend --region $REGION --since 30m
