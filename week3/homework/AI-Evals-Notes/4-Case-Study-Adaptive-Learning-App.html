🎒 Starter kit: 16 ideas you need for this chapter

1. LLM & prompt
An LLM (Large Language Model) is a big AI model like GPT, Claude or Gemini that reads and writes text. The instruction you give it is the prompt. LLM calls are slow (seconds) and cost money.
🧠 A brilliant friend who charges a fee per question and takes a moment to think.
2. Hallucination
LLMs sometimes state wrong things confidently. In a learning app, teaching wrong grammar destroys trust, which is why human experts review content in this design.
🧠 The uncle who says "go straight" even when he doesn't know the way.
3. DAU, RPS, P99
DAU = daily active users. RPS = requests per second. P99 < 500 ms = 99 of every 100 requests finish within half a second. Servers are sized for peak RPS.
🧠 Railways plan counters for the festival rush, not a quiet day.
4. API gateway
The front door for every request: checks identity and permissions, then routes it to the right service.
🧠 Your society's security guard.
5. Sync vs async, "202 Accepted"
Sync: the user waits for the answer. Async: work happens in the background; the server instantly replies 202 Accepted with a job_id, and the user checks status later (polling).
🧠 Chai stall (sync) vs dry cleaner's token slip (async).
6. Message queue & workers
A queue (SQS, Kafka) is a line of jobs. Producers add jobs; workers pick them up at their own pace. In a spike, the line grows but nothing crashes (backpressure).
🧠 A bank's token system: counters call the next token when ready.
7. Cache & Redis
Redis is a super-fast in-memory store (milliseconds). Keep ready-made results there. Hit = found; miss = fetch from the source. TTL = expiry.
🧠 Daily tea leaves on the kitchen shelf, not in the storeroom.
8. Redis list & LPOP
A Redis list is an ordered line of items. LPOP takes the first item out and removes it in one atomic step, so no one else can grab the same item at the same moment.
🧠 A candy dispenser: the top candy comes out, and it can't come out twice. 🍬
9. SQL (PostgreSQL) vs NoSQL (DynamoDB / Cassandra)
PostgreSQL: tables, relationships, flexible queries; scale reads with read replicas. DynamoDB / Cassandra: built for huge numbers of writes per second and scale out horizontally.
🧠 A well-organised office register (SQL) vs a station with hundreds of ticket counters (NoSQL).
10. Partition key & sort key
In DynamoDB, the partition key (e.g. user_id) decides which "cupboard" the data goes into; the sort key orders items inside that cupboard (e.g. by session).
🧠 One cupboard per person; files inside sorted by date.
11. Embedding & pgvector
An embedding is the meaning of text as a list of numbers (e.g. 768). Similar meanings → nearby vectors. pgvector is a PostgreSQL add-on that stores them and finds "similar" items.
🧠 A GPS address for the meaning of each question.
12. Retry, backoff, circuit breaker
Retry with exponential backoff: on failure, wait and retry, waiting longer each time. Circuit breaker: if a provider keeps failing, stop calling it for a while (open), try one test request later (half-open), go back to normal if it works (closed).
🧠 The MCB switch at home. ⚡
13. Human-in-the-loop (HITL)
Before AI-made content goes live, a human expert checks it: accept, edit or reject.
🧠 A reporter writes; the editor approves before printing. 📰
14. Cron job / nightly job
A task that runs automatically at a fixed time, e.g. every night at 2 am.
🧠 The milkman who arrives at 5 am every day without being called. 🥛
15. Data lake, Parquet, streams
A data lake is cheap cloud storage (like Amazon S3) holding all historical data for analysis. Parquet is a compressed file format that's fast to analyse. DynamoDB Streams is a live feed of every change in a table.
🧠 Old belongings go to the storeroom: not used daily, but not thrown away.
16. Function calling, CEFR levels, distractors
Function calling: instead of judging itself, the LLM asks a tool (like an answer checker) for an exact result. CEFR A1–C2 are standard language levels (A1 = beginner … C2 = near-native). Distractors are the wrong-but-believable options in a multiple-choice question.
🧠 A teacher grades with the answer key, not by mood.

Chapter 4 · Case Study: Designing an Adaptive Learning AppLLM-generated lessons + personalised curation for every learner

4.1 Introduction: the future of learning is personal

A great learning app moves at each learner's own pace. It spends less time on what you already know and more on lessons that are challenging but not discouraging, which is the sweet spot for staying motivated. It also needs fresh lessons regularly, as it learns from usage and feedback what works.

LLMs can transform this in two ways:

🏭 1. Creating new exercises
Generate thousands of new practice questions quickly, across many languages and levels.
🎯 2. Personalising the path
Pick the perfect next question for each learner, based on their history.

We'll design the core AI features of a Duolingo-style app: personalised lesson progression and interactive exercises. Out of scope: detailed scoring systems (XP, leagues). They matter for the product, but we'll keep our focus on the AI architecture.

4.2 Functional requirements: what must it DO?

🏭 Lesson generation
Create complete exercises and lessons for every language and level, so there's always a fresh, relevant stream of content.
🎯 Adaptive curation
Look at a learner's past answers and pick the perfect next question: not too hard, not too easy.

4.4 Back-of-envelope numbers

Assume 50 million daily active users. The app teaches 50 languages; the most popular have about 250 lessons each, less common ones up to 70. Each lesson has up to 10 questions.

🔍 Worked example: from users to requests per second
  1. Questions served per day: 50M users × 3 lessons × 10 questions = 1.5 billion questions/day.
  2. Per second: 1.5 billion ÷ 86,400 seconds in a day ≈ 17,400 questions per second.
  3. API calls per question: at least 3: GET the question, POST the answer, GET the feedback. So 17,400 × 3 ≈ 52,000 RPS on average.
  4. Peak (×5): traffic isn't flat; evenings and overlapping time zones bring spikes. 52K × 5 ≈ 260,000 RPS.
  5. Extra features: conversation practice (+20%) and real-time analytics (+15%): 260K × 1.35 ≈ ~350,000 RPS at peak.
  6. How many are writes? Roughly 1 in 3 calls (submitting answers, saving progress) writes data: 260K ÷ 3 ≈ ~90,000 writes per second at peak. This number will drive our database choice.

🚀 Going deeper: why the LLM can't sit on the live pathIf every question needed an LLM call, that's 17,000+ LLM calls per second, each taking 1–5 seconds: tens of thousands of calls in flight at any moment and an enormous bill. But if one LLM call picks a playlist of 20–30 questions, we need 20–30× fewer calls, and they can happen in the background. That single idea shapes this entire design.

🔍 Worked example: generating questions with a clear prompt

A good generation prompt is precise about the count, the level, the theme, the answer format and the output shape:

Create 10 fill-in-the-blank questions for Spanish learners at level A2 to practise the simple future tense. Theme: food. For each question give exactly one correct answer and three believable wrong options (distractors). Tag each question with its grammar point. Return only a JSON object: {"questions": [...]}
from pydantic import BaseModel

class Question(BaseModel):          # the exact shape of one question
    sentence: str
    answer: str
    distractors: list[str]
    grammar_tag: str
    level: str
    topic: str

class QuestionSet(BaseModel):
    questions: list[Question]

r = client.chat.completions.parse(
    model="gpt-6.1-terra",
    response_format=QuestionSet,          # Structured Outputs: every question has exactly these fields
    messages=[{"role": "system", "content": "You are an expert Spanish teacher writing exercises."},
              {"role": "user", "content": prompt}])
questions = r.choices[0].message.parsed.questions     # already Python objects, no json.loads
print(questions[0].model_dump())

Output (first question):

{"sentence": "Mañana yo ___ paella con mi familia.",
 "answer": "comeré",
 "distractors": ["comí", "como", "comía"],
 "grammar_tag": "future_simple", "level": "A2", "topic": "food"}

("Tomorrow I ___ paella with my family." The answer, comeré, means "I will eat"; the distractors are past and present forms.)

⚠️ Watch out: say exactly what you meanIf a prompt says "create 10 lessons" when you want 10 questions, the model may produce 10 full lessons. Use precise words and give the exact JSON shape you expect.
🙋 Human review
Experts check every question: grammar, difficulty, format and platform standards. They fix small issues and then accept or reject.
🏦 Going live (ingestion)
A scheduled nightly job picks up newly accepted questions, runs automatic checks (valid JSON, answer is among the options, no duplicates…), and inserts them into the main question bank. The bank is the single source of truth for all approved, live content in every language.

⚡ System II: the online tutor

1. Request & gateway
The learner's app asks for a lesson (POST /api/v1/lesson-sessions). The gateway checks identity and routes it to the lesson curator service.
2. Lesson curator service
The real-time brain: fetches the learner's next lesson from the approved bank, based on their level, understanding and progress, and keeps adapting as they improve.
3. Learner context
A user context service keeps each learner's progress: completed lessons, scores per skill, known vocabulary, strengths and recent mistakes.
4. Prepare in advance
We cannot run a slow, expensive LLM call for every learner in real time. So the online path uses proactive curation: the next lessons are chosen before the learner asks.

Why prepare in advance? If we waited until a learner finished a question and only then asked an LLM "what's the best next question?", they would stare at a spinner for seconds every time. Instead, we do that thinking ahead of time, in the background, in batches, and keep the results ready in a fast cache. That gives us two paths: warm (results ready) and cold (nothing ready yet).

⚡ Event trigger
When a learner completes a lesson (or does anything that shows they're active), a tiny message such as {"userId": "user_123"} is put on a dedicated low-priority queue called refill_check_queue.
🧮 Buffer check
A background worker reads the queue and checks how many lessons are left in that learner's Redis playlist. If it's running low (say fewer than 5), it starts a refill.
📦 Gather context
The worker collects the learner's recent progress, the history of their last 50 lessons, and a pool of a few hundred unseen questions from the bank at the right level, bundles it all into one message, and puts it on an SQS queue.
🧠 LLM sequencing
Orchestrator workers take these jobs at a controlled pace (so neither the LLM nor our services are overwhelmed). Prompt: "Based on this learner's history, choose and order the best 20–30 questions from this candidate pool." The resulting question IDs are pushed onto the learner's Redis playlist.
🔍 Worked example: the playlist in Redis, command by command

Each element of the list is one lesson: a group of question IDs.

# the background job adds 3 lessons to the end of user_123's playlist
> RPUSH playlist:user_123 "q_88,q_91,q_17,q_42,q_63" "q_12,q_19,q_77,q_80,q_05" "q_31,q_33,q_09,q_51,q_70"
(integer) 3

# learner taps Start → take the FIRST lesson and remove it, in one atomic step
> LPOP playlist:user_123
"q_88,q_91,q_17,q_42,q_63"

> LLEN playlist:user_123          # how many lessons are left?
(integer) 2

# ...two more lessons later...
> LPOP playlist:user_123
(nil)                             # empty → this is the cold path

Why LPOP and not "read, then delete"? Because LPOP does both in one atomic step. If the learner opens the app on their phone and tablet at the same moment, each device gets a different lesson; the same lesson can never be served twice. The small buffer of ready lessons also hides any short delays in the background refill.

🎬 The full curation flow (press Play)
Two triggers, one purposeRefills are started by events (a lesson completed → refill immediately) and also by a safety scan every 5 minutes that catches any learner whose event was missed. The new plan is saved twice: in the database (durable, survives crashes) and in Redis (fast to serve).

Async refill
1. Cache miss
The learner asks for a lesson; Redis LPOP returns nil (nothing there).
2. Synchronous fallback
Don't make them wait for the background job. Build just this one lesson right now with a fast rule-based query that skips the LLM: match the learner's language and level, and exclude questions they've seen recently. Not perfectly personalised, but fast and reliable.
3. Serve and trigger

🔍 Worked example: the rule-based query 
-- One lesson for a Spanish A2 learner, skipping recently seen questions
SELECT id FROM question_bank
WHERE language = 'Spanish'
  AND difficulty_level = 'A2'
  AND id NOT IN (:recently_seen_ids)     -- from the learner's last 20 lessons
ORDER BY random()
LIMIT 10;

Output: 10 question IDs, returned in a few milliseconds. No LLM, no waiting.

✅ Why this design works
  1. Decoupling: the personalisation engine is separated from what learners click, so the LLM sees steady, predictable load instead of sudden bursts.
  2. Buffering: keeping 20–30 lessons ready means short hiccups in the background pipeline are invisible to learners.
  3. Graceful degradation: if the LLM providers are down or slow, don't send work to the orchestrator; use the rule-based selection (same level, not seen in the last 20 lessons). Lessons keep flowing, just a little less personalised.

🚀 Going deeper
  • Duplicate refills: several "refill check" messages for the same learner can arrive together. Use a per-learner lock (for example Redis SET refill:user_123 1 NX EX 60, which only succeeds if no lock exists) so only one LLM job runs per learner.
  • Stale playlists: if a learner jumps a level, the ready playlist may now be too easy. Give playlists a version or expiry, or clear them when a skill level changes.
  • Memory estimate: 50M learners × 30 IDs × ~36 bytes ≈ 54 GB of raw data, before Redis overhead. That needs a sharded Redis cluster; keeping playlists only for recently active learners (with a TTL) shrinks it a lot.
  • Cost win: one LLM call sequences 20–30 lessons, so it's 20–30× cheaper than calling per question.

🧠 The orchestrator, up close

The orchestrator builds detailed prompts, decides which LLM should serve each request (based on availability, response time and whether the use case needs accuracy or speed), and runs a safety and validation check on every reply before passing it back to the calling service.

🛡 The resilience layer

The orchestrator depends on outside APIs, which can fail in four typical ways:

📶 Network blips
Brief glitches, failed secure handshakes, momentary packet loss.
🚦 Rate limits (429)
The provider is busy, or we've used our quota.
💥 Outages (5xx)
Major failure at the provider: errors or full downtime.
🐢 Timeouts
The model takes longer than we can wait.
🔁 Automatic retries
On a temporary error (like 429 or 503), retry automatically.
Purpose: fix short glitches without a human or a model switch.
Exponential backoff: wait longer between each attempt, so we don't pile more load onto a struggling provider (a "retry storm").
Limit: usually 3 attempts. If all fail, the problem isn't temporary, and the circuit breaker takes over.
⚡ Circuit breaker
Stops sending requests to a provider that is clearly and repeatedly failing.
↪️ Rerouting
When: the breaker is open, or the primary still times out after retries.
What: switch to a backup provider (e.g. primary OpenAI → backup Anthropic or Google).
Tiered fallback: first a strong backup, then a cheaper, simpler one (graceful degradation).
Keep the context: translate the prompt, context and history correctly into the backup provider's API format.
Breaker stateWhenWhat the orchestrator does
🟢 Closed (normal)Everything is healthyAll requests go to the primary provider
🔴 Open (failing)A failure threshold is crossed (e.g. 5 server errors in a row, or a 20% error rate within 60 seconds)Stop sending traffic immediately; fail fast or reroute. No time or tokens wasted on doomed requests, and the failing provider gets breathing room.
🟡 Half-open (testing)After a cooldown (e.g. 30 seconds)Send one test request. Success → closed. Failure → open again.
🎮 Try it: the circuit breaker (trips after 5 failures in a row)
🧠 Think of it like…Retry = a call doesn't connect, so you wait a bit and redial (waiting longer each time). Circuit breaker = after hearing "the number you are calling is switched off" 5 times, you stop trying for 30 seconds and call a different friend instead (backup provider). 📞

✅ The safety & validation layer · 🗄 the data lake

✅ Safety & validation
Every LLM reply is checked for structure (is it valid JSON with the right fields?), parsing and content (is it appropriate and within guidelines?). Bad replies are discarded and logged, and the results feed a feedback loop to improve prompts.
🗄 Data lake for learning
To keep improving, every service sends events (lesson started, answer submitted, mistake made) to a central event streaming platform, which lands them in a data lake on cloud object storage, in a modern open table format so big analysis jobs run reliably. Analysts and models learn from this to improve content and personalisation.

def validate_playlist(reply_text, candidate_ids):
    data = json.loads(reply_text)                      # 1. must be valid JSON (else retry/reroute)

    assert 20 <= len(ids) <= 30                       # 2. right size
    assert set(ids) <= set(candidate_ids)             # 3. NO invented IDs allowed!
    assert len(ids) == len(set(ids))                  # 4. no duplicates

⏳ Asynchronous processing for content generation

When an admin asks for hundreds of questions, a normal blocking request would freeze their screen and almost certainly time out. Instead, we decouple the request from the work with a message queue:

1. Submit the job
The admin asks for 100 questions; the portal calls the API.
2. Accept and split
The lesson generation service validates the request, saves a job record with a unique job_id, and replies 202 Accepted immediately. Workers handle up to 10 questions at a time, so the 100-question job is split into 10 messages (this is called fan-out) on generation_jobs_queue.
3. The queue as a buffer
The queue decouples the service from the workers, absorbs spikes (backpressure), and keeps messages safe if a worker crashes, so no request is lost.
4. Generation workers
Workers inside the orchestrator take messages, call the LLM to write questions, and put the results on generation_results_queue.
5. Save to staging
A database worker takes results and inserts them into questions_staging. When all 10 child batches are done, the parent job is marked COMPLETED with a results URL.
6. The admin checks in
The admin's screen stays usable and polls the status endpoint (GET …/question-generation-jobs/{job_id}) to show "Processing…" then "Completed".

Hybrid rule: for tiny requests (5 questions or fewer), skip all this and answer synchronously. The queue's overhead isn't worth it, and the admin wants instant results.

🧠 Think of it like…For 1,000 rotis at a wedding, you don't hire one cook. You hire 10 cooks (workers) and give each 100 (fan-out). The manager (generation service) ticks a register as each cook finishes, and only when all 10 say "done" does he announce "food is ready!" (COMPLETED). 🫓
🚀 Going deeper: what can go wrong with queues
  • Duplicate delivery: SQS may deliver the same message twice ("at-least-once"). Workers must be idempotent: if batch 7 was already processed, skip it. Otherwise you get 110 questions instead of 100.
  • Poison messages: a batch that fails every time should go to a dead-letter queue (DLQ) for inspection, and the job should be marked PARTIAL or FAILED instead of retrying forever.
  • Counting completions: increment "batches done" atomically (a database transaction or conditional update), so two workers finishing at once can't both write "10/10" wrongly.
  • Semantic de-duplication: use pgvector to flag new questions that are near-identical to ones already in the bank.

📈 Scaling

Two sides to scale: the services (compute) and the data (storage and throughput).

🧱 Scaling services
Scale horizontally: run more copies. The curation service auto-scales on incoming API traffic. The orchestrator workers auto-scale on two signals: the number of messages waiting in the queue, and CPU use. More waiting messages → more workers.
🗄 Scaling data
Question bank (PostgreSQL): read-heavy, so cache each question by ID and add read replicas.
Progress (DynamoDB): scales horizontally for heavy writes; reads are spiky when learners fetch their next exercise.
Playlists (Redis): a Redis cluster. Even if the whole cluster is lost, no learner loses progress or history (that's in DynamoDB); the pipeline simply rebuilds playlists. Worst case: lessons are a bit slower and less personalised for a while (cold path).
🔗 Scaling our dependence on LLM providers (the orchestrator's job)
Multiple providers
Integrate several LLM providers so there's no single point of failure; breakers, retries and rerouting keep traffic flowing.
Tiered models
Route by urgency and complexity: simple curation → small, cheap model; reserve top-tier models for premium conversation features.
Breakers everywhere
Wrap every provider in its own circuit breaker. On a latency spike or error burst, trip it and reroute to a fast backup model, or to a non-AI response (rule-based selection).

🧮 Exact grading with function calling

LLMs are probabilistic and can stumble on precise checks. Asking an LLM "is this answer correct?" will occasionally get a wrong verdict, and marking a correct answer wrong is a terrible experience for a learner. Instead, use function calling: the LLM is given a tool like check_answer(question_id, user_answer). The tool runs ordinary, deterministic code (string comparison, or maths in a sandbox for numeric answers) and returns a plain true/false. The LLM then uses that fact to write a friendly, encouraging message. Result: exact grading plus the warm, conversational tone of AI.

🎮 Try it: the tool decides, the LLM only explains
She ___ to the store yesterday.
🔍 Worked example: grading with a tool call 
ANSWER_KEY = {"q_12483240": "went"}

def check_answer(question_id, user_answer):                 # deterministic: no AI involved
    correct = ANSWER_KEY[question_id]
    return {"is_correct": user_answer.strip().lower() == correct, "correct": correct}

TUTOR = "You are a friendly English tutor. Give one short line of feedback."
tools = [{"type": "function",                      # Responses API: name/parameters sit directly here
    "name": "check_answer",
    "description": "Check a learner's answer against the answer key. Always use this; never judge yourself.",
    "parameters": {"type": "object", "properties": {
        "question_id": {"type": "string"}, "user_answer": {"type": "string"}},
        "required": ["question_id", "user_answer"]}}]

r = client.responses.create(                         # tool calling on gpt-6.1-terra needs the Responses API
    model="gpt-6.1-terra", instructions=TUTOR, tools=tools,
    input="Question q_12483240: 'She ___ to the store yesterday.' My answer: go")
call = next(item for item in r.output if item.type == "function_call")   # the model asked for the tool
result = check_answer(**json.loads(call.arguments))
print("Tool result:", result)

final = client.responses.create(
    model="gpt-6.1-terra", instructions=TUTOR, tools=tools,
    previous_response_id=r.id,                       # continue the same conversation
    input=[{"type": "function_call_output", "call_id": call.call_id, "output": json.dumps(result)}])
print(final.output_text)

Output:

Tool result: {'is_correct': False, 'correct': 'went'}
Almost! Because of "yesterday" we need the past tense: "She went to the store yesterday." 😊
Code note (GPT-6 API)On gpt-6.1-terra, tool calling only works through the Responses API, so this example uses client.responses.create: tools are listed with name and parameters directly (no nested "function" key), the tool request arrives as an item of type function_call in r.output, and we send the tool's result back as a function_call_output linked to the earlier turn with previous_response_id. The question-generation example earlier uses Structured Outputs (.parse with a Pydantic class) so every generated question is guaranteed to have the right fields.
⚠️ Where this works, and where it doesn'tDeterministic checking is perfect wherever there is one exact right answer: multiple choice, fill-in-the-blank, numeric answers. For open answers like free-text translation ("the cat sleeps on the bed" has many correct versions), you need LLM-based grading with a clear rubric, and "100% exact" is no longer guaranteed.
🧠 Think of it like…The teacher (LLM) says kindly, "Great effort, just one small mistake!", but the marks come from the answer key (the tool), never from her mood. ✔️

4.9 Testing

🏋️ Load testing
Goal: prove auto-scaling really works. Use a tool like k6 or JMeter to simulate thousands of learners starting lessons at once, and ramp up (10K → 50K → 100K virtual users) to find the breaking point, measure wait times and tune auto-scaling rules.
🎯 AI quality regression
LLM behaviour can "drift" when prompts or models change. Keep a dataset of hundreds of typical inputs with ideal outputs (questions to generate, playlists to sequence, feedback to write), and run it on every prompt tweak or model upgrade to confirm answers stay accurate, safe and in the right tone.

🐒 Chaos testing: break things on purpose

While the system is under load, deliberately inject failures (this practice is called chaos engineering) to check that the safety nets really work:

ExperimentWhat we expect
Kill a random curation-service instanceNothing breaks: the service is stateless, so other instances keep serving and the load balancer routes around it.

Make the LLM provider slow or return errorsThe circuit breaker trips and traffic fails over to a backup model or rule-based selection.

4.11 Summary

LLMs are powerful for learning platforms in both directions: creating content and personalising it. On the creation side, LLMs speed up lesson writing while experts review and refine to guarantee quality. On the personalisation side, learners get lessons that match their pace and style.

The common thread in both flows is retrieval and context injection: fetching the learner's history to personalise the next lesson, or grounding a generated exercise in the approved curriculum. You'll see the same pattern in AI-powered e-commerce search, where the system adapts to a shopper's intent and behaviour the way this app adapts to a learner.

🚀 Trade-offs worth saying out loud
  • Freshness vs latency: playlists are prepared in advance, so a mistake the learner made a minute ago isn't reflected immediately. Event-driven refills and a small buffer shrink this gap.
  • Personalisation vs cost: a bigger buffer means fewer LLM calls but a higher risk of stale playlists; a smaller one is fresher but costs more.
  • Human review throughput: experts guarantee quality but can become a bottleneck. Batch approvals, AI pre-scoring, and deep review only for low-confidence items help.
  • Graceful degradation: LLM down → rule-based; Redis down → cold path; even with both down, learners keep getting lessons.

  • Test by breaking things, and alert on cache hit rate and queue depth first.

Q1. Why not have the LLM create lessons live for each learner?Safety and quality risk (errors, inappropriate content), plus latency and cost: at ~350K RPS, an LLM call per request is impossible. So content is generated offline and reviewed by humans, and the online path only selects from approved content.
Q2. What's the difference between the warm and cold paths?Warm: the learner's Redis playlist has ready lessons → atomic LPOP → served instantly. Cold: LPOP returns nil (new or returning learner) → skip the LLM, run a rule-based query (same level and language, excluding recently seen) → serve one lesson and trigger an async refill.
Q3. Why must LPOP be atomic?It takes and removes the item in one step, so the same lesson can never be served twice, even if the learner opens the app on two devices at the same moment.
Q4. When and how does a playlist get refilled?When a lesson is completed (or another activity happens), {userId} goes onto refill_check_queue. A worker checks the buffer (fewer than 5 left?), gathers context (last 50 lessons + a few hundred unseen candidates), and sends it via SQS to the orchestrator, which asks the LLM to choose and order 20–30 lessons and pushes them to Redis. A 5-minute scan catches anything missed.
Q5. How is a 100-question admin request processed?A job record is created (PENDING) and 202 Accepted + job_id is returned. The job fans out into 10 messages of 10 on generation_jobs_queue; workers call the LLM and publish to generation_results_queue; a DB worker inserts into questions_staging; when all 10 batches finish, the job becomes COMPLETED with a results URL. The admin polls meanwhile. For 5 or fewer questions, it's synchronous.
Q6. Name the three circuit-breaker states and the thresholds used here.Closed (normal); open (after 5 consecutive server errors or a 20% error rate within 60 s: stop traffic and reroute); half-open (after 30 s, send one test request: success → closed, failure → open).
Q7. Why not keep all lesson history in DynamoDB forever?An endlessly growing log in a premium database is a money trap. Keep 90 days hot (with TTL) for fast checks; stream every change via DynamoDB Streams → Kinesis Firehose → Parquet files on S3 for cheap long-term storage and training.
Q8. What happens if the whole Redis cluster is lost?No learner loses progress or history (that's in DynamoDB). Learners are served via the cold path while the pipeline rebuilds playlists; lessons are slightly slower and less personalised for a while.
Q9. Why use function calling for grading?LLMs are probabilistic and can misjudge exact answers. A deterministic tool returns true/false from the answer key; the LLM only writes friendly feedback. That gives exact grading for questions with one correct answer.
Q10. Which two alerts matter most, and why?Queue depth (workers can't keep up → scale out) and cache hit rate (more learners falling to the slower, less personalised cold path).
Q11. What are the three model-router rules?Simple grammar check → small in-house model; complex conversation → strong mid-tier model; premium deep explanation → top-tier model.
Q12. The LLM returns a playlist containing a question ID that wasn't in the candidate pool. What should happen?The validation layer rejects it: every returned ID must come from the candidates provided. Then retry, reroute, or fall back to rule-based selection.
