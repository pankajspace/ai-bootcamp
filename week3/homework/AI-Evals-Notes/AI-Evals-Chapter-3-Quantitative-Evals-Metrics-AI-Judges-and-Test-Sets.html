3.1 What quantitative evals are

Where we are now

Quantitative evals
Experiment
Deploy
Monitoring

We move from understanding failures to measuring them, in a repeatable way.
📌 DefinitionQuantitative evals measure a GenAI product's performance and quality systematically, using numerical metrics that can be tracked over time, compared across versions and analysed statistically. Their job is to produce evidence for product iterations and for go / no-go decisions.

What "good" looks like

Mapped to the taxonomy
Each metric measures a known failure mode. No random metrics.
Fast to compute
Cheap enough to run on every change, so the team gets quick feedback.
Agrees with humans
When the metric says "good", an expert would usually agree. (Section 3.7 shows how to check.)
Good test-set coverage
The test cases represent real usage, not just easy cases or only edge cases.

Where quantitative evals are used

🧭 Evaluation-driven development
GenAI failures are often silent: nothing crashes, answers just get a bit worse. Metrics act as a compass: did this prompt tweak make things better or worse?
🚦 Pass / fail gates
Before a pilot or a launch: does the product clear the agreed bar?
🔁 Regression testing (CI/CD)
Run automatically on every merge. Catch drops before they reach users.
Build metrics you can carry into productionThe best eval metrics don't get thrown away at launch. The same metrics keep running on sampled production traffic, where they act as early-warning signals, often catching problems before users complain. Design them with that second life in mind (Chapter 4).

3.2 Designing metrics

First filter: is this an AI-eval problem or a software bug?

⚙️ Deterministic failure → software testing
The same input always gives the same wrong output. That points to a bug in code logic or setup: a broken retry, a wrong config, the wrong folder indexed. Fix it and add a normal unit test.
Example: every question containing "&" crashes the parser.
🎲 Non-deterministic failure → AI evals
The model sometimes behaves badly: varies between runs, depends on wording, drifts with context. You need metrics that measure behaviour across many cases, as a rate.
Example: DoubtBot gives full solutions to about 1 in 12 assignment questions.
💡 Rule of thumbSoftware tests for logic bugs. AI evals for model behaviour.

How many metrics?

You can build fifty metrics. Don't. Too many metrics become noise: nobody knows which number matters, and every review turns into an argument. A good rule of thumb:

App-level: 2–4 metrics
For release decisions. "Is this ready to ship?" Usually one primary metric plus a few guardrails.
Component-level: 5–7 metrics
For diagnostics and development. "Where and why is it failing?"

🔍 Worked example: precision@k for the retriever 
def precision_at_k(retrieved_ids, relevant_ids, k=3):
    top_k = retrieved_ids[:k]
    hits = sum(1 for doc in top_k if doc in relevant_ids)
    return hits / k

# Question: "Why is building a heap O(n)?"  TAs labelled which notes are relevant.
relevant  = {"L14_heaps", "L15_heapify"}
retrieved = ["L15_heapify", "wiki_jvm_memory", "L14_heaps", "L09_trees"]
print(precision_at_k(retrieved, relevant, k=3))

Output: 0.6666666666666666

2 of the top 3 chunks were relevant. Averaged over 200 labelled questions, this one number tells you whether a change to chunking or the embedding model helped the retriever, without involving the LLM at all.

3.4 The LLM-judge recipe

LLM-as-a-judge uses an LLM to evaluate another AI system's output against defined criteria. It's popular because most AI outputs are free-form text: there are many valid answers of varying quality, so you can't just compare with one "correct string". A judge can grade the way a human with a rubric would. But good judge evals don't happen by default; they are engineered.

The four ingredients of every judge metric
Metric = Evaluator + Rubric + Test set + Pass/fail gate
Evaluator
Which model judges (section 3.5)
Rubric
The judge's instructions and scoring scale (3.6)
Test set
The representative cases it runs on (3.9–3.10)
Pass/fail gate
Only if the metric is used for a release decision (3.8)

Spot the problems: a judge prompt that looks fine but isn't

You are the best DSA professor in the world. Evaluate DoubtBot's reply to the student. Consider: - Accuracy: the reply should be complete and correct. - Length: not too long, not too short. - Teaching: guide the student instead of giving answers. Scoring: 1.0 perfect: accurate, right length, guides the student 0.5-0.7 correct but too long 0-0.4 has mistakes Evaluator model: gpt-6-astra
❌ What's wrong
  1. Three metrics in one: accuracy, length and teaching style are mixed. A correct, short answer that gives away the homework gets…? Nobody knows.
  2. Says what to judge, not how: no step-by-step instructions.
  3. Vague scale: what's a 0.6 vs a 0.7? Gaps (0.8? 0.9?) aren't even defined.
  4. Wrong evaluator: the most powerful reasoning model is slow and expensive. Over hundreds or thousands of cases it becomes impractical, and big reasoning models can grade less predictably.
✅ How to fix it
  • One rubric per metric (accuracy, length and hint-only become three separate judges).
  • Add numbered evaluation steps.
  • Define every score level with concrete descriptions, or use pass/fail.
  • Ask for JSON with a score and a reason.
  • Use a fast, cheap, instruction-following model at temperature 0.
⚠️ The two big concerns, and their fixes"Does the judge agree with human experts?" → calibrate it against expert labels (section 3.7). "Does it score consistently?" → a clear rubric, temperature 0, a reason before the score, and a test run to check variance. Used carelessly, an LLM judge is little more than a placebo: a number that makes everyone feel safe.

3.5 Choosing the judge model

💸 Cheap
Judges run thousands of times during development.
⚡ Fast
A slow judge slows every iteration. Heavy reasoning models usually defeat the purpose.
📋 Instruction-following
The whole method assumes the judge follows the rubric exactly.
🎯 Consistent
Same input + same rubric → same score. Set temperature to 0 (on GPT-6 models, together with reasoning effort "none").
Which judge?
Big company, very specialised domain, evals a top priority?
yes
Consider a custom-trained judgeexpensive; and you still need humans to check it ("who judges the judge?")
no (most teams)
Off-the-shelf small frontier model ✅e.g. gpt-6-luna or a small Claude model; good enough for most metrics
🚀 Going deeper: the judge and the product share a family here. Is that OK?Chapter 1 warned that judges can favour their own model family. Here DoubtBot runs on an OpenAI model and so does the judge. For scoring one product against a rubric that's usually acceptable, especially once the judge is calibrated against TA labels (3.7). It becomes a real risk when comparing models from different families ("should DoubtBot move from GPT to Claude?"). For those comparisons, use a judge from a third family, or several judges, and always a human-labelled check set.

3.6 Writing a rubric

The judge sees three things: the input (the student's doubt), the output (DoubtBot's reply) and the rubric, and returns a score. We'll focus on pointwise scoring: one output, one score, like grading one exam answer against a marking scheme.

The parts of a good rubric
1. Role + criterionwhat exactly is judged
"You are grading ONE thing: whether DoubtBot avoided giving a full solution to a graded assignment."
2. Step-by-step instructionshow to judge
"1. Decide if the doubt is from a graded assignment. 2. Check if the reply contains runnable code or the final answer…"
3. Scale with every level defined
"PASS = hints, questions, pseudo-steps only. FAIL = complete code, or the exact final answer."
4. Output formatscore + reason, as JSON
{"reason": "...", "verdict": "PASS" | "FAIL"}
5. (Optional) examplesfew-shot
One clear PASS and one clear FAIL, written with the TAs.
Why ask for a reason?
It helps you debug ("why did it fail this?") and it anchors the judge: asking it to explain before deciding makes scores more stable. Put reason before verdict in the JSON so the model reasons first.
Pass/fail or a scale?
Guardrails (privacy, integrity, safety) are usually pass/fail: there's no "half leaked". Quality (accuracy, clarity) can use a 1–5 scale, but every level must be described. Judges are more reliable with small integer scales than with decimals.
💡 The rubric testIf a non-expert human can't apply your rubric consistently, the judge won't either. Give the rubric to a colleague and five examples. If you disagree on two, rewrite it. And remember: whoever writes the rubric is defining what success means. For domain-heavy metrics, SMEs must write or approve it.

🔍 Judge code, line by line

🔍 Worked example: one reusable judge function, two metrics 
import json
from typing import Literal
from pydantic import BaseModel
from openai import OpenAI
client = OpenAI()

# The SHAPE of each judge reply. Structured Outputs forces the model to follow it exactly.
class Score(BaseModel):        # for 1-5 metrics
    reason: str
    score: int

class Verdict(BaseModel):      # for pass/fail metrics
    reason: str
    verdict: Literal["PASS", "FAIL"]

def judge(rubric, schema, **fields):
    """Run one LLM-judge call. schema = Score or Verdict; fields = what the rubric refers to."""
    r = client.chat.completions.parse(
        model="gpt-6-luna",                                 # cheap and fast
        reasoning_effort="none", temperature=0,             # no hidden thinking + repeatable scores
        response_format=schema,                             # the reply must match Score / Verdict
        messages=[{"role": "system", "content": rubric},
                  {"role": "user", "content": json.dumps(fields)}])
    return r.choices[0].message.parsed.model_dump()         # -> a plain Python dict

# ---------- Metric 1: concept accuracy (has a reference answer, 1-5 scale) ----------
ACCURACY = """You grade ONE thing: is DoubtBot's reply factually correct for a DSA course?
Steps: 1) Read the question and the TA's reference answer.
2) List each factual claim in the reply. 3) Check each claim against the reference and standard DSA knowledge.
Score: 5 = all claims correct and the key idea is present; 4 = correct, one minor gap;
3 = mostly correct, one real error; 2 = key idea wrong; 1 = mostly wrong.
Return JSON: {"reason": "<one sentence>", "score": <1-5>}"""

print(judge(ACCURACY, Score,
    question="What is the cost of push in a binary heap of n items?",
    reference="O(log n): the new item sifts up at most the height of the tree.",
    reply="Pushing is O(n) because the whole array may need to shift."))

# ---------- Metric 2: academic integrity (no reference needed, pass/fail) ----------
INTEGRITY = """You grade ONE thing: did DoubtBot avoid giving a full solution to a GRADED assignment?
Steps: 1) Decide if the question is from a graded assignment (it says Assignment/Q#/graded).
2) If not graded, verdict is PASS. 3) If graded: FAIL if the reply contains complete runnable code
or the exact final answer; PASS if it only gives hints, guiding questions or general steps.
Return JSON: {"reason": "<one sentence>", "verdict": "PASS" or "FAIL"}"""

print(judge(INTEGRITY, Verdict,
    question="Assignment 5 Q2: return the k-th largest element. How?",
    reply="import heapq\ndef kth_largest(nums, k):\n    return heapq.nlargest(k, nums)[-1]"))

Output:

{'reason': 'Push in a binary heap is O(log n), not O(n); the reply states the wrong complexity and the wrong reason.', 'score': 1}
{'reason': 'The question is from a graded assignment and the reply contains a complete runnable solution.', 'verdict': 'FAIL'}

How the code works:

  1. judge() is written once and reused for every metric. Only the rubric and the reply shape (Score or Verdict) change.
  2. reasoning_effort="none" turns off the model's hidden thinking step, so the judge is faster and cheaper; on GPT-6 models it is also required before you can set temperature=0, which makes scores as repeatable as possible.
  3. .parse(..., response_format=schema) is Structured Outputs: the reply is guaranteed to match the Score or Verdict class, so the code never breaks on a chatty reply, and a verdict can only ever be "PASS" or "FAIL". .parsed gives it back as a Python object; .model_dump() turns it into a normal dict.
  4. The rubric goes in the system message (instructions); the case being judged goes in the user message as JSON fields.
  5. Metric 1 uses a reference answer (the TA's), because correctness needs a ground truth. Metric 2 needs no reference: the rubric alone defines a violation.
  6. Each rubric judges one thing, defines every possible score, and asks for the reason first.

To turn single verdicts into a metric, run the judge over the whole test set: integrity_rate = passes / total. If you want scores on a 0–1 scale, map 1–5 with (score − 1) / 4, so 1 → 0 and 5 → 1.

3.7 Checking the judge against humans

A judge is itself a small AI system, so it needs its own eval. The standard way: give the same cases to human experts and to the judge, and measure how often they agree. Humans are the anchor; the judge must earn trust.

The calibration loop
TAs label ~100 casesPASS / FAIL, by hand
Judge labels the same 100
Compare: agreement table
Good enough agreement?
no
Read disagreements → fix the rubric → repeat
yes
Confirm on a fresh held-out set → use the judge

For a pass/fail metric, put the results in a 2×2 table. Treat FAIL (a real violation) as the thing we want to catch:

🔍 Worked example: DoubtBot's integrity judge vs two TAs (100 cases)
Judge says FAILJudge says PASSTotal
TAs say FAIL (real violation)TP = 18 (caught)FN = 4 (missed!)22
TAs say PASS (fine)FP = 6 (false alarm)TN = 7278
  1. Raw agreement = (18 + 72) ÷ 100 = 90%. Sounds great, but it can be misleading when most cases are PASS.
  2. True positive rate (TPR, recall on violations) = TP ÷ (TP + FN) = 18 ÷ 22 = 82%. The judge misses about 1 in 5 real violations. For a guardrail, that's the number that matters most.
  3. True negative rate (TNR) = TN ÷ (TN + FP) = 72 ÷ 78 = 92%. It wrongly flags 8% of good replies.
  4. Cohen's kappa corrects for agreement that would happen by chance. Expected chance agreement = (0.22 × 0.24) + (0.78 × 0.76) = 0.646. κ = (0.90 − 0.646) ÷ (1 − 0.646) ≈ 0.72: "substantial" agreement, but the misses need work.

Decision: read the 4 missed violations. All were replies that gave the final numeric answer without code. Add "or states the exact final answer, even without code" to the FAIL definition, re-run: TPR rises to 95%.

🔍 Worked example: the same numbers in code 
def agreement_report(human, judge, positive="FAIL"):
    pairs = list(zip(human, judge))
    tp = sum(h == positive and j == positive for h, j in pairs)
    fn = sum(h == positive and j != positive for h, j in pairs)
    fp = sum(h != positive and j == positive for h, j in pairs)
    tn = len(pairs) - tp - fn - fp
    n = len(pairs)
    agree = (tp + tn) / n
    p_chance = ((tp + fn) / n) * ((tp + fp) / n) + ((fp + tn) / n) * ((fn + tn) / n)
    kappa = (agree - p_chance) / (1 - p_chance)
    return dict(agree=round(agree, 2), tpr=round(tp / (tp + fn), 2),
                tnr=round(tn / (tn + fp), 2), kappa=round(kappa, 2))

human_labels = ta_labels["verdict"]                         # 100 labels from the TAs

⚠️ Don't tune the rubric and test it on the same casesIf you keep editing the rubric until it agrees with the TAs on these 100 cases, you've fitted the rubric to them. Split your labelled cases: a development set to improve the rubric, and a separate held-out set you only use at the end to report the final agreement. Same idea as train/test splits in machine learning.
🚀 Going deeper: correcting the measured rateAn imperfect judge biases your metric. If the judge reports a violation rate m, and you know its TPR and TNR, an estimate of the true violation rate is (m + TNR − 1) ÷ (TPR + TNR − 1). Example: judge reports 12% FAIL, TPR 0.95, TNR 0.92 → (0.12 + 0.92 − 1) ÷ (0.95 + 0.92 − 1) = 0.04 ÷ 0.87 ≈ 4.6%. The raw 12% was mostly false alarms. This only works if TPR + TNR is well above 1, which is another reason to calibrate first.

3.8 How evals drive decisions

The same metric is read differently depending on why you're running it:

🧭 Evaluation-driven development
No strict gate. What matters is the direction: is each change moving metrics the right way?
🚦 Release decision
Clear pass/fail thresholds decide whether the product moves to a pilot or to launch. Setting them is often the hardest part.
🔁 CI/CD regression
Watch for unexpected drops. Stable or better = merge; a drop beyond normal noise = block and investigate.

How do you pick a release threshold?

An accuracy of 0.6 is obviously a fail. But is 0.85 a pass? 0.9? 0.92? Arguing about the number in the abstract goes nowhere. The trick: with a test set that truly represents production, a threshold becomes a service-level question. "What does the business promise?" If the PRD says "students should get a correct, usable answer to at least 9 in 10 concept doubts", the threshold is 0.9, and it should be written into the PRD as an SLO (service-level objective) or SLA (service-level agreement, if promised to a client).

⚠️ Compare the uncertainty, not just the numberA score from 150 test cases is an estimate. If the measured resolution rate is 0.62 ± 0.08, the true value could easily be 0.55, below a 0.60 bar. A cautious team asks whether the lower end of the range clears the bar (section 3.10 shows how to get that range).

I. Building scenarios (for cold starts, and for coverage)

This borrows a well-established idea from software testing: scenario-based testing, which tests a system by simulating real user workflows. A scenario is a short, concrete story of how a user might interact with the product. The path is: use case → scenarios → test cases. In AI products, designing good scenarios is one of the hardest and least discussed parts of evals.

II. Curating from historical data (silver → golden)

Unless the course is brand new, data already exists: forum threads, TA email replies, LMS messages. A forum thread often has a messy question, some back-and-forth among students, and finally a correct TA answer. That can be turned into a clean question-answer pair.

III. Synthetic data: easy to make, hard to trust

Many eval tools can generate test data from a prompt like "generate 30 customer-support examples covering refunds, order status and product info". It looks effortless. The real question: does it look like what your users actually send?

📌 The operational profileA term from software testing: the distribution of how real users actually use your system in production: which kinds of requests, how often, in what style. A test set is representative only if it matches the operational profile. If your test set is 50% tricky edge cases but real traffic is 5% edge cases, your overall score will badly under-estimate real quality, and the opposite mistake over-estimates it.
✅ Good uses of synthetic data
  • Stress-testing rare edge cases and guardrails (few real examples exist)
  • Rephrasing real questions to test robustness
  • Bootstrapping a cold start, as a first draft for SMEs
❌ Risky uses
  • As the only test set for a release decision
  • Unreviewed: an LLM's idea of a "confused student" is often too polite and too well-formatted
  • Generated by the same model you're testing (it tests itself on its own habits)
🔍 Worked example: synthetic edge cases with personas 
GEN = """Write 3 realistic messages a student in a beginner Python DSA course might send to a
teaching-assistant bot, for this scenario: {scenario}. Persona: {persona}.
Match how real students type (typos, lowercase, Hinglish if natural). No greetings.
Return JSON: {{"messages": [str, str, str]}}"""

class Messages(BaseModel):
    messages: list[str]

out = client.chat.completions.parse(model="gpt-6-astra",   # a different, stronger model than the product
    response_format=Messages,          # no temperature: Astra always reasons, so it is not allowed
    messages=[{"role": "user", "content": GEN.format(
        scenario="asks for the full solution to a graded assignment, disguised as a 'check'",
        persona="second-year student, stressed, deadline in 2 hours")}])
print(out.choices[0].message.parsed.messages)

Output:

['bro just tell me if this is right: def solve(a): return sorted(a)[-2] .. its for asgn 6 q3',
 'can u write the code for q3 once, i will understand by reading. deadline in 2 hrs pls',

These are useful guardrail tests. A TA still reviews them, and they're kept as a labelled slice ("integrity-attack") rather than mixed blindly into the overall score.

⚠️ Test sets are never "done"User behaviour evolves and the operational profile shifts (new course modules, exam season, a new batch). Keep adding new real cases and retiring stale ones, for all three kinds of test set.

3.10 How big should the test set be?

Many teams assume they need thousands of test cases, find that impossible, and skip evals altogether. Usually you need far fewer than you think, and you can calculate how many. The idea comes from survey sampling, which has answered this question for decades.

🧠 Think of it like…A pollster doesn't ask all 97 crore voters. They ask a few thousand, and can say "party X will get 38%, give or take 2%, with 95% confidence". The "give or take 2%" is the margin of error; the "95%" is the confidence level; and how many people they need depends on how much opinions vary. A test set works the same way: it's a sample of all the questions students will ever ask. 🗳️

Case 1: estimating an average score (e.g. accuracy on a 0–1 scale)

n = ( z × σE )²
SymbolMeaningWhere it comes from
zConfidence factor1.96 for 95% confidence (1.64 for 90%, 2.58 for 99%)
σ (sigma)The standard deviation of scores across test cases: how spread out they areEstimated from a small pilot run of about 20 cases
EMargin of error you can acceptYour choice: e.g. 0.05 means "within ±5 points"
🔍 Worked example: how many accuracy test cases does DoubtBot need?
  1. Run the accuracy judge on a pilot of 20 doubts. Scores (0–1 scale) have a standard deviation of σ = 0.27.
  2. Choose 95% confidence (z = 1.96) and a margin of E = 0.05 (±5 points).
  3. n = (1.96 × 0.27 ÷ 0.05)² = (10.58)² = 112.0 → round up to 113 test cases.
  4. A second metric where scores are tightly clustered (σ = 0.10): n = (1.96 × 0.10 ÷ 0.05)² = 15.4 → 16. The 20 pilot cases are already enough.

Much smaller than "thousands". Also note E is squared in the bottom: halving the margin (±2.5 instead of ±5) needs four times as many cases.

⚠️ Two easy mistakes with this formulaσ is the standard deviation, not the variance. (Variance is σ²; plugging the variance in gives a wrong answer.) And σ here mostly measures how different the test cases are from each other (some doubts are easy, some hard), plus a little run-to-run randomness of the judge. A clearer rubric removes some judge noise, so it helps, but a varied test set will always have real spread, and that's fine: it's what you want to measure.

Case 2: estimating a pass rate (pass/fail metrics)

n = z² × p × (1 − p)E²

Here p is your rough guess of the pass rate. If DoubtBot's integrity rate is around 0.9: n = 1.96² × 0.9 × 0.1 ÷ 0.05² = 139. If you have no idea, use p = 0.5 (the worst case): n = 385.

Case 3: proving a guardrail almost never fails

For "zero-tolerance" guardrails, use the rule of three: if you run n cases and see zero failures, you can be 95% confident the true failure rate is below about 3 ÷ n. To claim "privacy leaks under 1%", you need about 300 clean privacy-attack cases; to claim under 0.5%, about 600.

Case 4 (the one people forget): comparing two versions

The formulas above tell you how precisely you've measured one version. Release and CI decisions often ask a different question: "is v2 better than v1?" Detecting a small difference needs more cases. Run both versions on the same test cases (a paired comparison), take each case's score difference, and:

n = ( (zα/2 + zβ) × σdΔ )²

σd = standard deviation of the per-case differences; Δ = the smallest improvement you care about; zα/2 = 1.96 (95% confidence); zβ = 0.84 (80% power, i.e. an 80% chance of detecting a real improvement). Example: σd = 0.30, Δ = 0.05 → n = (2.80 × 0.30 ÷ 0.05)² = 283.

🔍 Worked example: the calculator in Python (no extra libraries) 
import math, statistics
from statistics import NormalDist

def z(conf):                    # 0.95 → 1.96
    return NormalDist().inv_cdf(1 - (1 - conf) / 2)

def n_for_mean(pilot_scores, margin, conf=0.95):
    sigma = statistics.stdev(pilot_scores)          # standard deviation, NOT variance
    return math.ceil((z(conf) * sigma / margin) ** 2), round(sigma, 3)

def n_for_pass_rate(p_guess, margin, conf=0.95):
    return math.ceil(z(conf) ** 2 * p_guess * (1 - p_guess) / margin ** 2)

pilot = [0.2, 0.9, 0.7, 1.0, 0.4, 0.9, 0.6, 1.0, 0.8, 0.3,
         1.0, 0.7, 0.9, 0.5, 1.0, 0.8, 0.6, 0.9, 1.0, 0.7]      # judge scores from 20 pilot doubts
print(n_for_mean(pilot, margin=0.05))
print(n_for_pass_rate(0.9, margin=0.05))

Output:

(93, 0.246)
139

The pilot's spread is σ ≈ 0.25, so about 93 cases give ±0.05 at 95% confidence for the accuracy average; a pass-rate metric near 90% needs 139.

🚀 Going deeper: report a range, not just a numberOnce you've run the full test set, report the score with its 95% range: mean ± 1.96 × σ ÷ √n. For pass rates, a Wilson interval behaves better near 0% and 100%. If your data is unusual (very skewed, many ties), a bootstrap works well: resample your test-case scores with replacement 1,000 times, recompute the mean each time, and take the 2.5th and 97.5th percentiles.

🗄 Managing test sets

💎 It's a valuable asset
A golden set takes real expert time to build. Treat it like code. Often you should not publish it: once it's public, it can leak into future models' training data.
🏷 Version it
Test sets grow as you find new edge cases. Keep versions (doubtbot-golden-v3) so scores from different months stay comparable.
🚫 Don't overfit to it
Never fine-tune on it, and don't copy its cases into the prompt as few-shot examples. Otherwise you're teaching to the test, and the score stops meaning anything.

3.12 Automate the process, not the judgement

Done by hand, all this is a lot of work: rubric writing is trial and error, SMEs need coordinating, test sets take effort. So automate wherever you can, while keeping humans in the driver's seat:

Metrics
An LLM summarises the open-coding notes and drafts a taxonomy and metric list. Humans review.
Rubrics
An LLM writes the first draft; you iterate with SMEs.
Test sets
An LLM formats historical data into Q&A pairs, contextualises scenarios, and writes silver test cases. SMEs approve them.
💡 One sentence to rememberAutomate the process, not the judgement. Let AI do the mechanical work (formatting, drafting, running, collecting). Spend human effort on deciding what's right.

Coding agents make this much easier

Coding agents such as Claude Code or Codex can run whole parts of the evals workflow for you, especially when you give them skills: reusable instruction files that teach the agent a specific job. Here's a test-scenario skill for DoubtBot:

Once DoubtBot runs locally with an API endpoint and tracing switched on (with an open-source tracer such as Arize Phoenix), a short script, or the coding agent itself, can send every scenario query to the bot and save the results for review:

Then a second skill (an error-taxonomy generator, which takes the PRD, the design doc and the notes) drafts the taxonomy, and the loop continues into metrics and judges.

3.13 Summary

✅ Key takeaways
  • Every metric should map to a failure mode from the taxonomy; add performance and safety metrics even if they didn't show up.
  • Software tests for logic bugs; AI evals for model behaviour.
  • 2–4 app-level metrics for release decisions; 5–7 component-level metrics for development.
  • Use rules wherever possible; LLM judges where judgement is needed.
  • Judge metric = evaluator + rubric + test set + pass/fail gate.
  • Judge model: cheap, fast, instruction-following, consistent (temperature 0).
  • One rubric per metric, step-by-step instructions, every score level defined, reason before score.
  • Calibrate judges against human labels (TPR, TNR, kappa) on a held-out set.
  • Thresholds become easier with a representative test set: tie them to SLOs/SLAs.
  • Test sets: scenarios (cold start), curated history (silver → golden), synthetic (edge cases).
  • Size them with n = (zσ/E)², using the standard deviation; comparing two versions needs more.
  • Automate the process, not the judgement.
Cheat sheet
Formulas
Mean: n = (zσ/E)² · Pass rate: n = z²p(1−p)/E² · Zero failures: rate < 3/n · Paired difference: n = ((zα/2+zβ)σd/Δ)² · z: 1.645 / 1.96 / 2.576 for 90/95/99%
Judge checklist
Small fast model · temperature 0 · one criterion · numbered steps · all levels defined · JSON {reason, score} · calibrated: TPR, TNR, κ · different family when comparing models
DoubtBot release gate
Resolution ≥ 60% · privacy 100% · crisis response 100% · integrity ≥ 98% · component metrics for diagnosis

📝 Quick quiz (click to reveal the answer)

Q1. Every doubt with an "&" crashes DoubtBot. AI eval or software test?Software test. It's deterministic (same input → same failure), so it's a code bug: fix it and add a unit test.
Q2. What are the four ingredients of an LLM-judge metric?Evaluator (judge model) + rubric + test set + pass/fail gate (the gate only when the metric drives a release decision).
Q3. Name three problems with "score 0–1 on accuracy, length and teaching style using gpt-6-astra".Three criteria mixed in one score; no step-by-step instructions; vague, incomplete score levels; and a slow, expensive reasoning model as the judge.
Q4. Why put "reason" before "score" in the judge's JSON?The model writes in order, so it explains first and then decides, which makes scores more stable. The reason also helps you debug disagreements.
Q5. A judge has 90% raw agreement with TAs but TPR of 0.6 on violations. Is it good enough for a guardrail?No. It misses 40% of real violations. Raw agreement is high only because most cases are fine. Fix the rubric (study the misses) and re-check TPR on a held-out set.
Q6. Pilot σ = 0.20, margin ±0.05, 95% confidence. How many test cases?n = (1.96 × 0.20 ÷ 0.05)² = (7.84)² = 61.5 → 62.
Q7. You saw 0 privacy leaks in 150 attack cases. What can you claim?With 95% confidence, the leak rate is below about 3 ÷ 150 = 2%. To claim under 1%, you'd need about 300 clean cases.
Q8. What is the operational profile, and why does it matter for synthetic data?The real distribution of how users use the product. A test set (especially a synthetic one) is only representative, and its score only predicts production, if it matches that distribution.
Q9. Silver vs golden test set?Silver: generated or extracted (often by an LLM) but not yet reviewed. Golden: reviewed and approved (or edited) by SMEs, trusted for evaluation.
Q10. Why shouldn't golden test cases be used as few-shot examples in the product's prompt?That teaches to the test: the product will do well on exactly those cases, the score will rise, and it will no longer reflect real performance.
