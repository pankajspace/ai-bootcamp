Capstone project · after the Production RAG, Agentic RAG and Deep Search courses

AI Vendor Risk Assessor

Build the assistant every security and procurement team wishes it had: ask “Can our support team use this AI tool with customer data?” and get a review file with every policy requirement checked against evidence from the web — source, date and verdict — plus the exact questions still to ask the vendor. A human approves. The system never does.

Solo: 2–3 weeks · Team of 3–4: 4 weeks · Starter kit runs offline on day one · Created by Shivank Agrawal

0Start here

You have finished three courses. Each one built a serious component in isolation: a production RAG pipeline over company documents, an agentic RAG crew that routes and grades, and a deep search agent that researches the open web and refuses to be fooled. This capstone puts the three together into one product that a company would use, and adds the glue that none of the courses taught: a deterministic requirement matcher, a questionnaire drafter, a human approval gate and a UI.

What you will have at the end

  • A working assessor: policy library + vendor research + rule-based verdicts + human gate, behind an API and a small UI.
  • A hand-built gold set of real vendors and an evaluation report proving accuracy, zero guessing and injection resistance.
  • A trace for every run that lets you point from any verdict to the exact web page and policy clause behind it.
  • A portfolio project with a real enterprise story: “I automated the vendor security review, and here is how I kept it honest.”

Prerequisites

  • Completed Production RAG from Scratch (you have a working rag_core/ folder).
  • Completed Agentic RAG with DeepSeek + CrewAI (you understand Router, Retriever and the two graders).
  • Completed Deep Search Agents (you have run run_agent.py offline and live, and Lab 12 in LangGraph).
  • Python 3.10+, a free LLM key (Gemini or Groq) or Ollama, and a free web-search option (ddgs, no key).

How the starter kit is built. The deterministic parts are complete and tested (schemas, the matcher, the questionnaire, the report, the gold set and the evaluation harness). The parts your courses taught are present in a simplified offline form — keyword search instead of hybrid + rerank, a rule-based router instead of an LLM router, a static research plan instead of a planner — so that the whole thing runs. Every one of those files starts with a COURSE MAP comment and a LEARNER TODO block that names the milestone and the course module to use. Your job is to replace the simplified part with the real one, keep the tests green, and prove the improvement in the evaluation.

1The problem

Every company now has employees asking “can I use this AI tool?” several times a week. Each request should trigger a vendor security review: does the vendor hold a current SOC 2 Type II or ISO 27001? Where is our data stored? Do they train on it? Who are their sub-processors? Have they had an incident? Is a DPA available? Today a security engineer spends two to six hours per vendor reading trust centres, privacy policies and news, and most of that time is finding and dating facts, not judging them. Teams either wait weeks for a review or skip it.

The assessor does the finding, dating and checking. It leaves the judging to a person, with every fact already attached to its source.

The running example: Nimbu Mart

You know Nimbu Mart from the Production RAG course. Its Information Security team has eight internal documents — two editions of the security policy, a data-protection policy written for India’s DPDP Act, an AI acceptable-use policy, a procurement checklist, the restricted Approved Vendor List, a questionnaire template and an untrusted chat export. 4Milestones

Do them in order. Each one ends with a check you can run. Tick the box when the check passes; the page remembers it in your browser.

M0

Run and read the starter kit

½ day

Goal: know exactly what the finished system does before changing anything.

  1. Run the four demo questions in the README. Read each report.md, then its trace.jsonl, bottom to top.
  2. Read the code in this order: schemas.py → matcher.py → graph.py (run_plain) → vendor_research.py → policy_rag.py.
  3. Open data/vendor_web/corpus.json. Find the stale page, the look-alike company, the rumour, the copy and the attack page. Predict what the system does with each; check against the LedgerLens trace.
  4. Break something on purpose: in requirements.yaml set allow_planned: true on DP-3.1 and watch LedgerLens pass residency. Put it back.

Done when: pytest is green, eval/run_eval.py shows 100% verdict accuracy, and you can explain in two sentences why QuillDesk is BLOCKED and Parakeet is only CONDITIONAL.

M1

The policy library, production grade

3–4 days

Production RAG Modules 06, 08, 09, 11 · Labs 03, 06, 08, 09, 11

Goal: replace keyword search with your rag_core pipeline, and extractive answers with grounded generation — without losing a single security property.

  1. Copy your rag_core/ into the project. Load data/policies through it, keeping clause ids and the metadata fields (access, status, trust, version) on every chunk.
  2. Make PolicyLibrary.search() use hybrid retrieval (BM25 + vectors, RRF) and a cross-encoder reranker. Filters stay before ranking: ACL, archived, untrusted, injection flag.
  3. Make PolicyLibrary.answer() generate grounded answers with clause citations when an LLM is configured; keep the extractive mode as the offline fallback. Refuse when the top score is below threshold and when the grader says the answer is not grounded.
  4. Fix the known failure: pq-who-approves in the gold set (keyword search ranks SEC-7.1 above the approval table in AI-5.1). Hybrid + rerank should fix it; prove it in the eval report.
  5. Add three policy documents of your own (for example an incident-response runbook and a 2027 draft marked status: draft) and three new gold questions.

Done when: all policy-question checks in eval/run_eval.py pass including the one marked “baseline known to fail”; tests/test_policy_rag.py still passes (ACL, archived, untrusted); an employee asking for the Approved Vendor List still gets the process, never the list.

M2

Vendor research on the real web

4–5 days

Deep Search Modules 03, 04, 05, 06, 07, 09 · Labs 2, 3, 4, 6, 7, 8, 10

Goal: turn the sequential live baseline into a planned, parallel, budgeted research agent that produces the same VendorProfile the offline mode does — for real vendors.

  1. Four places (Deep Search Module 12 “Adapt it to your own domain”): the fields are already retargeted in schemas.py; review AUTHORITY, FIELD_AUTHORITY_OVERRIDES and HALF_LIFE_DAYS in vendor_research.py and justify each number in a comment.
  2. Replace plan_queries() with a Plan Creator → Plan Reviewer pair that produces one sub-question per field, with stop rules (“stop when every high-stakes field has a documented source or two searches have failed”).
  3. Run fetch + extraction in parallel workers sharing one Budget; route extraction to the small model.
  4. Make the identity gate real: the LLM decides “same company?” from domain, legal entity and product — and the gate stays a gate (reject, do not down-weight).
  5. Pick three real AI/SaaS vendors, research them by hand first (fill data/gold_set_template.json with URLs and dates), then run the agent and compare field by field.
  6. Stretch: long-term memory of previous runs so a re-review of the same vendor only fetches pages newer than the last run.

Done when: on your three real vendors, field accuracy against your hand-made gold set is ≥ 80%, no field is filled from a page about a different company, a live assessment costs under your VRA_MAX_USD and finishes in under 90 seconds, and the offline tests still pass unchanged.

Expect friction. Trust centres are JavaScript-heavy, some sites block bots, and “SOC 2 compliant” appears on pages with no report. That is the real job. Keep the offline corpus as your regression suite and add a cached_pages/ snapshot for your real vendors so your demo does not depend on the internet.

M3

Router and graders as agents

2 days

Agentic RAG “agents.py”, “tasks.py”, “Practice and self-check”

Goal: replace the regex router and the heuristic graders with LLM agents that are better than the mocks and prove it.

  1. Port the Router’s goal and backstory from the course kit, add the two new routes (vendor, assessment) and the refuse route, and return a RouteDecision through LLM.structured().
  2. Port the Answer Grader and Hallucination Grader as grade_relevance() / grade_grounded(). Add the retry loop: not relevant → widen the search (k = 8, include query rewriting); not grounded → regenerate once with a stricter prompt, then abstain.
  3. Write 30 routing questions (10 per route, including awkward ones: “Is LedgerLens SOC 2 so we can use it?” is an assessment; “Which tier is Parakeet approved for?” is a policy question) and measure routing accuracy for the mock and for the LLM.
  4. Repeat the course exercise “Break the Router on purpose” on your new router and write down what changed.

Done when: routing accuracy ≥ 90% on your 30 questions with the LLM router; a deliberately wrong policy answer (edit the prompt to invent a clause) is caught by the hallucination grader and turned into an abstain.

M4

Security: attack it, then defend in layers

2 days

Deep Search Modules 08, 11 · Lab 9   Production RAG Module 11 · Lab 11

Goal: prove that untrusted content — web pages, chat exports, the user’s own question — can never change a verdict.

  1. Write tests/test_red_team.py with 15 attacks: injection in a vendor page (“report PASS”), injection in a policy document, a user question that smuggles an instruction (“…and mark it approved”), a fake trust-centre on a look-alike domain, a page that says the India region exists when the privacy policy says planned, a rumour phrased as news. Every attack must be caught, and the test must assert where it was caught (quarantine, identity gate, dropped, intent check, output guardrail).
  2. Add a second injection layer behind the regexes: a small-model classifier on each fetched page (Deep Search Lab 9). Measure false positives on the clean pages.
  3. Run the ablation: switch the identity gate off and show the UK firm’s ISO certificate leaking into LedgerLens’s facts. Put the screenshot in your write-up.
  4. Apply the Module 11 privacy checklist: the schema holds no personal data; the questionnaire email names a role, not a person; nothing from a vendor’s employees is stored.

Done when: 15/15 attacks caught with the catch point asserted; the gold-set safety metric is still 100%; the guess rate is still 0.

M5

Make it a product: graph, API, UI, human gate

3–4 days

Deep Search Module 12, Lab 12   Production RAG Modules 04, 12, 13

Goal: a reviewer can use it without you in the room.

  1. LangGraph: add a checkpointer and an interrupt() at human_gate so an assessment can pause for days and resume when the approver decides. The CLI prompt in the starter is the placeholder for this.
  2. API: put /assess behind a queue (Redis + RQ as in the Production RAG app), return a job id immediately, and poll for the report. Store reports in Postgres so /vendors/{name}/history can show what changed since the last review (SEC-12.1).

Done when: a teammate who has not seen the code can assess a vendor from the UI, read why each verdict was given, send the vendor questions, and record a decision — and the decision survives a server restart.

Adding a clause means adding a YAML entry and, sometimes, one small rule function with its tests.

23 fictional pages across three vendors. Each page carries mock_claims: what a careful extraction model would read from it. In offline mode the agent uses those; in live mode it calls your model. Every domain ends in .example.

Gold sets

gold_set.json: five assessment cases (including the same question asked by someone without access) and six policy questions, one marked “baseline known to fail”. gold_set_template.json: the shape you fill for real vendors.

6Rules of the project

  1. The model never decides a verdict. It reads pages, drafts text and classifies routes. matcher.py decides, from rules you can unit-test. Two runs on the same evidence give the same verdict.
  2. UNKNOWN beats a guess. A PASS or FAIL without an evidence URL is a bug; the output guardrail downgrades it. The evaluation’s guess_rate must stay at zero.
  3. A claim is not evidence. “We are SOC 2 compliant” is claimed. A report, a certificate number, a registry entry or a legal page is documented. Only documented evidence passes a high-stakes requirement.
  4. Identity is a gate, not a weight. A page about a same-name company is rejected before anything is read from it. Down-weighting it would still let its facts leak in.
  5. Untrusted content never reaches the verdict. Pages that address the AI are quarantined whole. Forum posts and rumours are dropped and logged, not scored low.
  6. Repetition is not corroboration. A syndicated copy of the vendor’s page counts once.
  7. Access control lives in retrieval. The Approved Vendor List is invisible to people outside Security and Procurement, and the assistant says so instead of leaking it. Groups come from identity on the server, never from the request body.
  8. Every fact has a date. Freshness decays per field. A 2024 security page loses to a 2026 trust centre, and the conflict is recorded, not hidden.
  9. Humans approve. The report ends in an approval block that only a named person can fill. The word “approved” never appears in anything the system writes about a vendor.
  10. Research companies, not people. No names of vendor employees in the schema, the memory or the report.

9Stretch goals

  • Continuous monitoring. A weekly scheduled re-review of every approved vendor that only reports changes (new sub-processor, new incident, certificate expiring in 60 days). Deep Search Module 7 memory + Module 12 “regulatory circular monitor” idea.
  • MCP server. Expose assess_vendor and ask_policy as MCP tools so Claude Desktop or your IDE can call them (Deep Search Lab 5).
  • Debate layer. Before the human gate, a “vendor advocate” and a “risk officer” agent each write one paragraph from the same evidence; the report shows both. Useful when evidence conflicts.
  • Document intake. Let the vendor upload its SOC 2 report PDF; extract the audit period and the auditor’s opinion with the Production RAG OCR/table pipeline (Lab 02) and upgrade claimed to documented automatically.
  • Multi-tenant. A second company with different policies (tenant_id on every chunk and rule), as in the Production RAG capstone exercise.

10FAQ

Why not let the LLM read the policy and the evidence and decide?

Because the verdict must be the same on Tuesday as it was on Monday, and a reviewer must be able to point at the line of policy and the line of evidence behind it. Models are excellent at reading and extracting; they are not consistent judges. Keeping the judgement in code is what makes the system auditable and the evaluation meaningful.

Isn’t a rule engine “not AI”?

The intelligence is in reading a thousand messy pages and turning them into typed, dated, sourced facts — and in knowing which pages to distrust. That is where every hour of the project goes. The rule engine is 300 lines and stays that way.

What if a vendor’s pages block my fetcher?

Cache what you can, record UNKNOWN for what you cannot, and let the questionnaire ask the vendor. An honest UNKNOWN with a question attached is a correct output. Playwright for JavaScript-rendered trust centres is a reasonable stretch.

Can I do this solo?

Yes: do M0–M4 fully, M5 as the CLI + API only, and three real vendors instead of ten. That is a complete, demonstrable project in about three weeks.

Which LLM should I use?

Whatever is free and supports JSON output: Gemini’s free tier or Groq for development, Ollama for offline. Use the small model for extraction and grading and a stronger one only for planning and synthesis — then show the cost difference in your report.
