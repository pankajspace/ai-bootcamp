📘 Concept: context window and tokens

A model does not read words; it reads tokens, small chunks of text roughly three-quarters of a word long. Everything in a chat, your messages, Codex's replies, every file it opened, every command output, is converted into tokens and sent to the model again with each new turn. The total amount it can hold at once is the context window. When a chat grows long, three things happen: each turn costs more (you pay for all those tokens again), the model gets slower, and it starts to lose track of early details because the window is crowded. A fresh chat per task keeps the window small, focused and cheap. Codex still knows the project, because AGENTS.md and the files are always there.

📘 Concept: plan mode

Plan mode is a built-in Codex mode where the agent is only allowed to think and write, not to edit files or run commands. You describe a task, it reads the codebase and comes back with a step-by-step plan for your approval. The intention is good: define the feature before building it. The weakness is that it mostly plans from its own assumptions; it asks you few or no questions, so the gaps in your request stay gaps in the plan. For a well-understood task it is fine. For a new feature with real design decisions (who are the users? how is money stored? what happens when two people bid at once?) I want a tool that interrogates me first. That is what grilling does, and it is why plan mode stays off for the rest of this course.

Look at the message box, then turn plan mode back off: click the Plan chip that appeared under the message box, or type /plan again and pick the “turn off” option.

📘 Concept: grilling (interview before building)

Grilling flips the usual order. Instead of you writing a long prompt and hoping you covered everything, the agent interviews you: it reads the code, works out what is undecided, and asks numbered questions in rounds, each with options A / B / C and a recommended answer. You answer, it asks the next round, and when nothing is left open it writes the agreed design down and proposes slices to build. The value is that every design decision is made deliberately, by you, before a single line of code exists. Without this, the model makes those decisions silently, you discover them only when the code is wrong, and you pay twice to fix them. Grilling costs tokens up front and saves many more later.

What the three skills do:

  • Grilling is the interview itself: numbered questions in rounds until you and Codex agree on one design. Every question comes with options and a recommended answer. The full instructions Codex follows are in ~/.agents/skills/grilling/SKILL.md; open it in VS Code when you have a minute, it is just a Markdown file telling the model how to behave.
  • Grill Me is a shortcut that starts Grilling with a short preamble.
  • Grill with Docs runs Grilling together with the domain-modeling skill, which writes the decisions down as documentation (CONTEXT.md, docs/adr/…) inside the part's folder. Its instructions are in ~/.agents/skills/grill-with-docs/SKILL.md. This is the one we use.
📘 Concept: ADR (architecture decision record)

An ADR is a short text file that records one decision: what we decided, what the options were, and why we chose this one. For example: “Money is stored as integer cents in USD. Options: floating point dollars, decimal type, integer cents. Chosen: integer cents, because floating point rounds and the app is USD only.” Teams keep ADRs in a docs/adr/ folder so that six months later nobody has to guess why the code looks the way it does. For us they have a second use: Codex reads them in future chats, so the decisions you make today keep steering it in guides 9 and 10 without you repeating yourself.

Delete /grill from the box when you have seen the list. If the skills are missing, reinstall them with the command below, in the Terminal app:

5

Answer round 1

Read every question properly. Your questions may be worded, ordered or numbered differently from mine, because the model is not deterministic, so match them by topic and make the same decision. Here is what I decided, and why:

  • Q1 Who are the actors? → my own answer, not the recommendation: predefined users. A users table with 10 seeded users and a small user switcher at the bottom of the page. No real login. Why: real authentication (passwords, sessions, sign-up) is a whole project of its own and teaches nothing about auctions. A switcher lets us act as different bidders in seconds, which we need badly in guides 11 and 12.
  • Q2 What must a seller provide? → take the recommendation (A): title, category, description, condition, location, seller name, starting price, closing time. These are the fields the Part 1 catalog already shows, so new listings look like the seeded ones.
  • Q3 How should images work? → take the recommendation (A): the seller picks a category and the UI shows that category's illustration. No uploads or image URLs. File uploads need storage, size limits and security checks; we skip all of that.
  • Q4 When does an auction become visible? → take the recommendation (A): it goes live the moment it is created. No draft state, no approval queue.
  • Q5 How is closing defined? → A: the seller picks a future date and time, and the API stores it as an absolute UTC timestamp. UTC is the single world reference time with no time zones or daylight saving. Storing UTC means a bidder in Bangalore and a bidder in New York both see the same auction end at the same real moment; the browser converts it to local time only for display.
  • Q6 How should money be represented? → A: USD only, stored as integer cents. $18,450.00 is stored as 1845000. Never store money as a decimal number like 18450.00 in a floating-point column: computers cannot represent many decimals exactly, and you end up with bids of $10.000000001. Whole integers never round.
  • Q7 What happens to the six existing catalog items? → A: seed them into Postgres, so the catalog, detail and search screens all read from the database instead of a hard-coded list. One source of truth.
  • Q8 What should database reset mean? → I was not sure what Codex meant by this, so I asked it to explain rather than guess. It comes back as a question in round 2. Do the same whenever a question is unclear; “explain this better” is a perfectly good answer.
📘 Concept: seed data

Seed data is the starting content a database is filled with when it is created: our 10 users and 6 hardware items. It is written as a script that runs after the migrations, so every fresh database, on every machine, starts with the same rows. Without seeds a new database is empty and the app looks broken. Seeds are also what makes a “reset” meaningful: drop everything, run migrations, run seeds, and you are back to a known state.

6

Answer round 2

Same approach: match each question by topic, not by number. Round 2 is about how users interact and what the rules are. My decisions:

  • Q9 Database reset → A: restore the 10 users and the 6 original auctions. Only auction_part_2 is dropped and rebuilt. This is the follow-up to my “explain this better” in round 1.
  • Q10 Remembering the active user → A: keep the chosen user ID in localStorage, starting with the first seeded user. localStorage is a small key-value store inside the browser that survives page reloads, so your chosen user stays selected when you refresh. We change this in guide 9 to a random user per browser tab, for reasons you will see then.
  • Q11 Ownership and self-bidding → A: the active user automatically becomes the seller of anything they post, and bidding on your own auction is rejected. Otherwise a seller could inflate their own price.
  • Q12 Minimum valid bid → A: at least $1.00 above the current amount, checked in the API and not only in the browser.
  • Q13 Simultaneous bids → A: correct one-at-a-time bidding now. Proper locking for two people bidding in the same millisecond waits for Part 3. We deliberately leave this problem in, because guides 11–14 are about discovering and fixing it.
  • Q14 Ended auctions → A: show “Ended”, disable the bid form, and have the API reject new bids on an ended auction.
  • Q15 Bid visibility → A: a compact bid history on the auction page with bidder, amount and time.
  • Q16 Posting experience → A: a Sell link in the header that goes to /auctions/new. After posting, you land on the new auction's own page.
  • Q17 Specifications on new listings → B, the one place I go against the recommendation: new listings have no specifications section, and that section is hidden when it is empty. The seeded hardware items have detailed spec tables; asking a seller to fill one in would make the form huge for no benefit.
📘 Concept: validate in the API, not only in the browser

Q12 says the minimum-bid rule is checked “in the API and not only in the browser”. Browser checks are for convenience: they give instant feedback and save a round trip. But anyone can bypass the browser and send a request straight to the API with a tool like curl, or simply have an old page open. If the rule lives only in the browser, a bid of $0.01 above (or below) the current price gets through. The API is the only place every request must pass, so every business rule is enforced in the API; the browser copy is a bonus. This is one of the most important habits in backend engineering, and the AGENTS.md rule “validate inputs” is about exactly this.

Key takeaways

  • Plan mode defines a feature before building it, but it plans from the model's assumptions. The grill skills go further: many focused questions, each with options and a recommended answer, so you make the design decisions.
  • Grilling moves your decisions to the start, where changing them is free. Without it, the agent decides silently and you find out when the code is wrong.
  • Read every question. Take the recommendation when it fits and override it when it does not; here that was Q1 (predefined users) and Q17 (no specifications on new listings).
  • Three backend fundamentals showed up in the answers: store time as UTC, store money as integer cents, and enforce every business rule in the API, not only in the browser.
  • A grilling session ends with 2–4 vertical slices, each with a browser checkpoint. You approve them, Codex builds one, you check it, then the next.
  • One task, one chat. A fresh context window is cheaper, faster and more accurate.
