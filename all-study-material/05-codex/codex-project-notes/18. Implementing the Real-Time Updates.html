📘 Concept: real-time fan-out over WebSockets

Until now our auction page only knew about a new bid when you reloaded it. In Part 4 we flip that around: the server tells every open page the moment something changes. The pipe for this is a WebSocket, a connection that stays open between the browser and the server so the server can push a message down at any time, unlike a normal request where the browser must ask first. When a bid is saved, the server sends one small event, “auction 42 changed”, to every browser that is looking at auction 42. Sending one event to many listeners is called fan-out. Think of a classroom notice board versus a teacher who walks to each desk: fan-out is the notice board, everyone sees it at once. Socket.IO is the library we use; it wraps WebSockets and adds rooms (“everyone watching auction 42”) and automatic reconnects.

📘 Concept: Mermaid diagram

Mermaid is a way of drawing diagrams with plain text. Instead of dragging shapes in a drawing tool, you write lines like Browser --> API --> Database and a renderer turns them into boxes and arrows. Codex likes Mermaid because it can write the text itself, and the Codex app renders it as a picture for you. The important part for you: every box is a component (a browser, a server, a database) and every arrow is a message or call between two components. If you can follow the arrows, you understand the design.

📘 Concept: Redis backplane

Imagine we later run two copies of our API server to handle more users. Browser A is connected to server 1, Browser B to server 2. A bid arrives at server 1. Server 1 can tell Browser A, but it has no idea Browser B exists. A backplane fixes this: every server publishes its events to one shared place, and every server listens to that place. We use Redis for it, a very fast in-memory data store that also offers Pub/Sub (publish/subscribe): one side publishes a message on a channel, every subscriber gets it instantly. So server 1 publishes “auction 42 changed” to Redis, server 2 hears it, and Browser B gets the update. With one server you would not strictly need this, but we build it in now so the design is ready for more than one.

✓ You should see

A diagram with emoji service labels similar to: Bidder and Auction Watcher (🌐 browsers) → POST bid → ⚡ Fastify API → 🐘 PostgreSQL. After the database commit, an auction:changed event goes to 🔌 Socket.IO, which uses 🔴 Redis Pub/Sub as its backplane, then a WebSocket notification reaches both browsers and each browser refetches the auction (asks the API for the latest data).

Two slices are proposed, similar to:

  1. Live auction detail updates: Redis-backed Socket.IO, WebSocket-only clients, post-commit notifications, coalesced refetching, focused tests, two-window browser review.
  2. Reconnect convergence and lifecycle hardening: automatic refetch after reconnect, silent background-refresh recovery, Part 4 config and docs.

And a closing line like: “Please confirm these two slices. Once confirmed, I'll implement and verify Slice 1 only, then stop for your browser review.”

Some words in Slice 1 that I want you to understand before you approve it:

  • WebSocket-only clients: Socket.IO normally starts with an older fallback technique (repeated HTTP requests) and then upgrades to a WebSocket. We tell it to use WebSockets directly. Fewer moving parts, easier to test.
  • Post-commit notifications: the server sends “auction changed” only after the database has saved the bid. If we sent it before, a browser could refetch and still see the old price. Order matters.
  • Coalesced refetching: if five events arrive in one second, the page should fetch the auction once, not five times. “Coalesce” means merge many into one.

📘 Concept: reading a diff

A diff shows only what changed between two versions of a file. Lines with a red background (and a minus sign) were removed; lines with a green background (and a plus sign) were added; unchanged lines around them are shown in grey for context. You do not need to understand every line. Ask three questions per file: Is this file one I expected to change? Does anything get deleted that should not be? Does the new code match what the slice promised? If the answer to all three is yes, move on.

📘 Concept: page reload vs live update

A page reload (pressing refresh, or code calling location.reload()) throws the whole page away and asks the server for everything again: the HTML, the scripts, the data. You see a white flash, scroll position is lost, and every reload is a full round of requests. A live update keeps the page as it is and changes only the numbers that changed, because the server pushed a tiny “something changed” message and the page fetched just the auction data. For the user it feels instant and smooth. For the server it is far less work. From now on, a reload on the auction page is a bug, not a feature. Keep that in mind for step 8.

✓ You should see

Terminal shows the Postgres and Redis containers as healthy, the migrations running, then [server] and [web] log lines. In the browser, the bid appears in both windows within about a second, with no reload and no flash: current price, highest bidder, bid count, minimum next bid and the bid history all change in the window you did not touch. That is the fan-out working end to end.

💡 Tip

If the second window does not change: open Docker Desktop and check that a redis container is running (the root docker-compose.yml maps it to localhost:56379). If Redis is down, the backplane is down, and no events get through. If Redis is fine, ask Codex in the same chat “the second window is not updating, what's wrong?” and let it debug.

When you are done, press Ctrl+C in Terminal to stop the servers. The Redis and Postgres containers keep running in Docker, which is fine and saves start-up time later.

📘 Concept: headed Playwright test

Playwright is a tool that drives a real browser from code: open this page, type here, click there, wait for this text. Normally it runs headless, with no visible window, which is fast and good for automated checks. A headed run opens real browser windows so a human can watch. Our bidding-war test is deliberately headed: it opens four windows, logs in four different users, fires bids on a timer and leaves the windows open at the end. The computer checks the final prices; you check what it looks and feels like. That second check is the one that catches layout problems and unwanted reloads, which no assertion in the code would notice.

✓ You should see

Codex runs the headed Playwright test tests/bidding-war.spec.ts. Four Edge windows open in a 2×2 grid: SELLER · AVERY, BIDDER 1 · MAYA, BIDDER 2 · THEO, BIDDER 3 · PRIYA, each with a countdown badge (T-…s). Bids fly in, every window shows ENDED at the deadline, and Codex reports something like: “BIDDING WAR PROTECTED! Accepted bids: $101 → $102 → $106 → $107. All four tiled Edge windows are open and will remain open for inspection.”

Now watch closely, because in my run two things were wrong even though the test passed. First, the bids did show up live, but the pages also refreshed, a visible flash on every bid. Second, the layout wasted space: a big search bar at the top pushed the price and the bid form below the visible area, so in a quarter-screen window you could not see what mattered without scrolling. Look for both in your windows. You fix them in the next two steps.

Key takeaways

  • Review the diagram before saying go. One question, “is this a separate service?”, is how you stop an agent from building more than you asked for.
  • Real-time means push, not pull. The server saves the bid, then fans out one auction:changed event over WebSockets to every page watching that auction; the pages refetch. Redis is the backplane that lets several servers share those events.
  • Recover cleanly: “continue” resumes after a restart. Branch in new chat from the last good message beats arguing in a thread that has already gone wrong.
  • It isn't verified until bidding wars. The headed, four-window run caught two things the unit tests passed over: leftover page reloads from the old test helper and a cramped layout.
  • A screenshot is a prompt. For anything visual, attach a picture and write two numbered points. Codex fixes both and reruns the test.
  • Read the diff whenever a slice adds a new technology. You now know where Socket.IO lives on the server (realtime.ts) and in the browser (liveAuction.ts).
