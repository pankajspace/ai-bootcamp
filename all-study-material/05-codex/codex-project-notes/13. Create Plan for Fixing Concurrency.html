📘 Concept: injected app clock

The bid route must decide “has this auction ended?” by comparing the closing time with “now”. Where does “now” come from? Two options. The database clock (PostgreSQL's now()) or the app clock (our Node.js server's time). I choose the app clock, and I want it injected: instead of calling Date.now() directly all over the code, the code receives a small clock object from outside, and in tests we hand it a fake clock that we can set to any moment we like. That is how you test “a bid that arrives one millisecond after closing is rejected” without waiting for a real auction to end. Injection just means “pass the dependency in rather than reaching for it”, and it is the single biggest thing that makes time-based code testable.

📘 Concept: polling

Polling means the browser asks the server “anything new?” on a timer, say every two seconds, whether or not anything changed. It is simple and it works, but it is wasteful (most requests return nothing new) and it is never quite live. The alternatives are to refresh only when something happens (after your own bid, or after a conflict error), which is what we choose here, or to have the server push updates to the browser, which is Part 4's topic (WebSockets).

📘 Concept: idempotency key

If a user's network hiccups and the browser sends the same “bid $107” request twice, should the server treat it as two bids? An idempotency key solves this: the client attaches a unique id to each request, and the server remembers ids it has already processed and returns the earlier result instead of doing the work again. “Idempotent” means doing it twice has the same effect as doing it once. It is a real production technique, and payments (Part 7) rely on it. For bidding right now it is extra machinery we do not need, because a duplicate $107 bid would simply be rejected as “not higher than $107”. So I say no.

Answer grilling round 2

Round 2 has about 8 more questions (Q10–Q17 in my run). They are more detailed than round 1: exact transaction shape, the exact fields in an error response, exact wording on screen. My choices, by topic:

  • Q10 Keep $103 in the bid history if it was accepted just before $106 → yes. History is a record of what happened, not just the winner.
  • Q11 Read the app clock after acquiring the auction lock, and store that moment as the bid's createdAt → yes. If you read the clock before waiting for the lock, a bid could be stamped “before closing” but actually be written after.

The output of a grilling session is a plan: the decisions (in GRILL.md), a diagram of how the pieces connect, and a list of slices, each a thin end-to-end piece of the feature that you can check in the browser. A good slice is big enough to be worth testing and small enough to review in ten minutes.

Key takeaways

  • Each part starts in a new chat and in its own folder. Codex copies the previous part and changes only the part-specific settings (database name, ports), so every earlier part keeps working as a “before” version.
  • Side chats let you ask questions, or have Codex draft a prompt, while the main run keeps going. They are temporary scratch paper and never touch your code.
  • A test that passes when the bug is present is a reproduction, not a protection. Part 3 must flip the bidding-war test so it fails on duplicates.
  • Grilling is how your experience gets into the design. I overrode the database clock with an injected app clock so time can be mocked in tests; the agent would not have chosen that on its own.
  • Say no to complexity you do not need yet (idempotency keys, extra UI states, auto-retry). An agent will happily add extras nobody asked for; your job is to keep the scope honest.
