24. Reviewing the Pull Request

Review the Drizzle pull request your goal opened, catch the test it skipped, pay for a won auction through Mock Stripe with your own hands, and start Part 7's Slice 2. This guide is about trusting an agent's work the right way: verify, then accept.

Part 7 · slice 1 → 2≈ 30–45 min hands-onGitHub PR + local /review

What you'll do

  • Read the goal's pull request on GitHub like a reviewer: summary, files changed, commits.
  • Ask Codex whether it really ran the Bidding Wars test, and make it run it for real.
  • Run Part 7's bidding war with the browsers left open, then pay as the winner with the 4242 test card.
  • Start Slice 2, and find out why Codex skipped the test (a gap in AGENTS.md, not a Codex failure).

Before you start

  • Finished guide 23: Codex has finished Slice 1 in the Define winner checkout flow chat and listed browser steps for you to try.
  • Your Drizzle goal from guides 22–23 says Goal achieved in the Pull GitHub issue 2 chat. It took about 17 minutes in my run. Skipped the Drizzle goal? Review your small ADR PR (#3) in steps 1–2 instead, and skip steps 3, 4 and 8.
  • API-key note: we review the PR ourselves on github.com. Codex's automatic GitHub PR reviews and the browser built into Codex are not available with an API-key sign-in. So we use Chrome (or Edge) for GitHub and the local /review command for an AI second opinion. You lose nothing that matters.
📘 Concept: reviewing a PR, what to look for

A pull request review is not “read every line and nod”. A good reviewer asks four questions, in this order. Does the description match the ticket? Read the PR summary against the issue's acceptance criteria. Is the change where I expect it? Skim the list of changed files; surprises (a file that has nothing to do with the ticket) are a red flag. Does the code do what the description claims? Open the three or four most important files and read them properly. Were the claims verified? “Tests pass” is a sentence in a text box until you see the tests run. With an AI author, the fourth question matters most, because agents are very good at writing confident summaries. That is the thread we pull on in this guide.

2

Review the diff yourself

Click the Files changed tab. You get a long page: each changed file is a block, removed lines are red with a minus, added lines are green with a plus. Don't try to read all of it. Skim the file list on the left, then open these three places and read them properly:

  • part-6-async-close-rabbitmq/docs/adr/0002-use-drizzle-across-database-services.md: the decision and the reasoning. Read this first, because it tells you what the rest of the diff is trying to achieve.
  • server/src/db/schema.ts: the tables now defined in code with pgTable(…). Each table from the SQL migrations (auctions, bids, users, …) becomes a TypeScript object listing its columns and their types. This file is what gives the ORM its type safety: every query is checked against it.
  • Tests and services: raw SQL strings such as pool.query('DELETE FROM auctions …') replaced by calls like db.delete(auctions).where(like(…)) and db.insert(auctions).values(…). Pick one service file and compare one red line with the green line that replaced it; you will see the SQL verb (DELETE, INSERT, SELECT) has become a function name.

My point after skimming: it looks right. The description is tidy, the files are where I expect them, the tests are listed as passing. But did it actually work, in the sense of the app still running correctly with four users bidding at once? Nothing on this page proves that.

✓ You should see

About 29 files changed, around +950 / −730 (your numbers will differ). Old SQL lines in red, Drizzle calls in green. At the very top of the file list, the new schema.ts and a new drizzle.config.ts, and in package.json the new dependency drizzle-orm.

📘 Concept: environment variable

An environment variable is a named setting handed to a program when it starts, from outside the code. Writing BIDDING_WAR_HOLD_MS=3600000 npx playwright test … sets the variable BIDDING_WAR_HOLD_MS to 3,600,000 milliseconds (one hour) for that one command only. Inside the test, the code reads that value and keeps the browser windows open for that long before closing them. Same test, different behaviour, no code change. Ports, database passwords and the mock's webhook secret are passed to our app the same way, through its .env file.

📘 Concept: paying for a won auction, end to end

Follow what happens between your click and the “Paid” badge, because every piece of Part 7 is in that chain. (1) You click Complete purchase; the web app calls our API. (2) The API checks you are the winner and the auction is closed, creates a purchases row in pending state (or reuses the open one), and asks Mock Stripe to create a Checkout Session for exactly the winning bid. (3) The API sends your browser to the mock's hosted page on port 7107. (4) You enter the card; the mock decides success or decline. (5) On success, the mock sends a signed webhook to our API; the API verifies the signature, records the event id, and flips the purchase from pending to paid, once. (6) The mock redirects your browser back to the auction page with ?checkout=success, and the page asks our API for the real state and shows Paid. Note that step 6 only displays the state; step 5 is the only thing that changes it.

✓ You should see

The Mock Stripe page at http://127.0.0.1:7107/checkout/cs_test_… shows the item, $107.00, Winning Bid · USD, and a reminder of both test cards (the fix Codex made to the mock in guide 23). After paying you land back on …/items/bidding-war-gpu-…?checkout=success&session_id=cs_test_…, and the panel reads WINNER CHECKOUT · Payment received · Your purchase is paid. Click Complete purchase again if the button is still there: nothing happens, because the purchase is already paid.

📘 Concept: migration, seed and ON CONFLICT DO NOTHING

A migration is a numbered SQL script that changes the database structure: create a table, add a column. They run in order, once each, so every copy of the database ends up with the same shape. A seed is the small set of starter rows (our demo users, for example) that a migration inserts so the app is usable on first run. The bug: when the Drizzle version re-ran the setup against a database that already had those seed rows, the INSERT failed because the rows existed. The fix, ON CONFLICT DO NOTHING, tells PostgreSQL “if a row with this key already exists, skip it quietly instead of erroring”. That makes the seed idempotent: safe to run any number of times. You met idempotency with webhooks in guide 23; here it is again, at the database level.

📘 Concept: AGENTS.md as the agent's checklist

AGENTS.md is the instruction file Codex reads before it touches a folder: how the project is laid out, which commands are safe, what “done” means. An agent treats it as the definition of its job. If the file says “run npm test before claiming done”, the agent runs npm test, and nothing else, and reports honestly that tests passed. The lesson is not “agents cheat”. It is “agents do exactly what the checklist says”, which puts the responsibility for the checklist on you.

✓ You should see

One line from package.json with "test:bidding-war": "playwright test tests/bidding-war.spec.ts …", meaning the scenario exists as a separate script. Then the AGENTS.md list: npm run db:up, npm run db:down, npm run db:reset, npm run migrate, npm run dev, npm start, and npm test. No bidding war anywhere. Codex ran exactly what the instructions told it to run.

💡 Tip

The fix is a one-liner in AGENTS.md, for example “Before claiming done, also run npm run test:bidding-war.” I call this user error, and I mean mine, not Codex's: the agent is only as good as the checks you give it. If you want, add that line to Part 6's and Part 7's AGENTS.md now.

10

Optional: review the branch with local /review

Codex cannot review PRs on GitHub with an API key, but it can review the branch on your Mac, which is the same code. In the Pull GitHub issue 2 chat (it lives in the worktree, on the issue-1-drizzle-refactor branch), type /review in the message box. A small menu appears with review options; pick the one that reviews against a base branch, then choose master (or main). That tells Codex “compare this branch with master and review only the difference”, which is exactly what the PR contains.

📘 Concept: review findings and priorities

A code review tool lists findings, not opinions: each one names a file and line, says what is wrong and why it matters. Findings are ranked. A P1 is a blocker: a bug, a security hole, data loss; the PR must not merge until it is fixed. A P2 should be fixed but could ship; and lower levels are style or suggestions. When you read a review, deal with the P1s first and don't let a long list of small items hide one serious one.

✓ You should see

Codex reads the whole diff and lists findings, most important first, each with the file and line and a short explanation. Or it says it found no blocking issues. Compare its list with what you noticed yourself in step 2: did it flag anything about the migration, the schema or the tests that you missed?

💡 Tip

If your /review menu looks different, pick whichever option compares this branch with master.

⚠ Heads up

A review of a 30-file refactor reads a lot of code, so it costs tokens. Skip it if you are watching spend; you have already done the most important review yourself in steps 2–4.

Key takeaways

  • Review agent PRs like any teammate's: read the summary against the ticket, skim the file list, read the few files that matter, then check that the claims (tests, scenarios) actually happened.
  • Agents can over-claim without lying. A direct question (“did you do the BIDDING WARS?”) got an honest “no”, and the real run then found a real bug that the unit tests had missed.
  • Codex only runs the checks it knows about. List every important test command in AGENTS.md, especially the slow, headed, end-to-end ones.
  • Keep a human in the loop for the user-facing part. I paid for the item myself before moving to Slice 2, and that is how I knew Slice 1 was really done.
  • Idempotency showed up twice in two guides: webhooks that may arrive twice, and seeds that may run twice. Whenever something can happen more than once, make the second time harmless.
