11. Understanding the Concurrency Problem

Find the race condition hiding in Part 2's bid code with your own eyes, then ask Codex to prove it exists with a four-window “Bidding War” Playwright test before anyone touches the fix.

Open the Part 2 folder in VS Code with the command below. Then press Cmd+P (quick open), type server/src/app.ts and press Enter. In that file press Cmd+F and search for INSERT INTO bids.

❯Run in TerminalTerminal app · any folder
code ~/codex-course/workshop/part-2-create-auction-and-bid

code <folder> opens that folder as a VS Code workspace, so the file tree on the left shows only Part 2. Now read the bid route from top to bottom. Notice the order of what it does: first it reads the auction and its current highest bid from the database, then it runs the checks, and only after that does it write the new bid.

📘 Concept: race condition (“check, then insert”)

A race condition is a bug that only appears when two things happen at almost the same time, and the result depends on who gets there first. Our bid route does “check, then insert”: it reads the current price, checks that the new bid beats it, then inserts. Imagine two bidders, Priya and Sam, both bidding $101 on an auction at $100, half a millisecond apart. Priya's request reads “$100”, Sam's request reads “$100” too (Priya has not inserted yet). Both pass the “at least $101” check. Both insert. Now the auction has two $101 bids and no clear highest bidder, and the second one should have been rejected. Nothing in the code is “wrong” line by line; the gap between the read and the write is the bug. Any system with many users and shared data (seats, stock, wallets, bids) has this problem unless you design against it.

✓ You should see

The bid route, app.post('/api/auctions/:slug/bids', …). It does its checks first: sellers cannot bid on their own auction, the auction must not have ended (compared with Date.now(), the current time in milliseconds), and the bid must be at least $1 (100 cents) above the current price. Then, as a separate statement, it runs INSERT INTO bids (auction_id, bidder_user_id, amount_cents) VALUES ($1, $2, $3). The $1, $2, $3 are placeholders that the pg library fills in safely with the real values.

There is no BEGIN, no transaction and no lock anywhere near it. That gap is the bug. Your line numbers and variable names may differ, since your Codex wrote your copy, but the shape (read → check → insert, as separate database calls) will be the same.

💡 Tip

Why it slipped through: every test Codex wrote in guide 10 sends one bid at a time, so “check, then insert” always worked. Tests only catch what they try. Sequential tests cannot find a concurrency bug; you need a test that deliberately sends bids at the same moment, which is exactly what we build next.

4

Now let's see if Codex can spot what you just found. I ask it in a deliberately casual, slightly teasing way, without telling it where the bug is or what it is. If the agent can find the problem from a one-line hint, it understands the code; if it cannot, that tells you something too. Paste the message exactly and press Enter.

✦Paste into CodexCodex message box (new chat)
lol you don't see a problem with bid concurrency?

Codex's answer will mention two database ideas we have not met yet. Read these two callouts first so the reply makes sense.

📘 Concept: transaction (BEGIN / COMMIT)

A transaction groups several database statements into one all-or-nothing unit. You start it with BEGIN, run your reads and writes, and finish with COMMIT (make it permanent) or ROLLBACK (undo everything). If the server crashes halfway, the database throws the half-done work away, so you never end up with a bid inserted but the auction price not updated. Think of it as a bank transfer: debit one account and credit another must both happen or neither. A transaction on its own, though, does not stop two bidders reading the same price at the same time; for that you need the next idea.

📘 Concept: row lock (SELECT … FOR UPDATE)

Inside a transaction, SELECT … FOR UPDATE reads a row and locks it until the transaction ends. If a second transaction tries to lock the same row, it has to wait. Apply that to bids: Priya's request locks the auction row, reads $100, checks, inserts $101, commits. Only now does Sam's request get the row; it reads $101, checks its $101 bid, and correctly rejects it. The lock turns a race into a queue, one bidder at a time, but only for that one auction. Bids on other auctions are not slowed at all. This is the fix we will build in Part 3 (guide 14).

✓ You should see

Within about 15 seconds, a reply similar to: “Lol, yes—you're right. I missed a real lost-race bug.” Codex explains that the bid endpoint does three separate steps (read the current max bid, validate the amount, insert the bid) with no transaction or auction-row lock in app.ts. It gives an example like two requests both reading $100 and both inserting $101. It suggests wrapping the bid in a transaction with SELECT … FOR UPDATE on the auction row, and may point out that GRILL.md records concurrency as deferred to Part 3.

What it means: Codex found the same gap you found in Step 1, and it proposes the same fix the two callouts describe. It has not changed any code yet; it only answered the question.

💡 Tip

📘 Concept: end-to-end test with Playwright (headed)

The tests Codex wrote so far are unit and API tests: they call a function or an endpoint directly and check the answer. An end-to-end (E2E) test instead drives a real browser like a user would: open the page, click Sell, type a price, press Place bid, read what appears on screen. Playwright is the library that does this driving; it can control Chrome, Edge, Firefox and WebKit from a script. Normally it runs headless, meaning the browser runs invisibly in the background, which is fast and fine for automation. Headed means the browser windows are actually shown on your screen. We want headed here because the point is to watch four users collide. Each Playwright “context” is like a separate browser profile with its own storage, which is how the three bidders become three different users.

📘 Concept: red before green

In testing, red is a failing test and green is a passing one. “Red before green” means: write a test that fails because of the bug before you fix the bug. Two reasons. First, it proves the test actually detects the problem; a test that was never red might pass for the wrong reasons. Second, when you then apply the fix and the same test turns green, you have evidence the fix works, not just a feeling. With an agent this matters even more, because the agent will happily say “fixed” whether it is or not. The red test is how you hold it accountable.

6

Let Codex build and launch the test

Now just watch. Do not close Codex, the chat, or the Terminal running Part 2. While it works, I want to give you the idea behind all of this. Every time Codex finishes a change, something has to tell it whether the change is right. Type checks do that for shapes of data. Tests do that for behaviour. Code review does that for design. Each of these is back pressure: a force pushing back on the agent, catching mistakes before they reach you. The more back pressure you give an agent, the more it can correct itself without you, and the faster you can safely move. A test that reproduces this bug is back pressure we did not have before.

✓ You should see

Over the next few minutes, in roughly this order:

  • Codex adds Playwright to the project, creates a playwright.config.ts (Playwright's settings: which browser, headed or headless, timeouts), a tests/bidding-war.spec.ts file (the test itself) and a test:bidding-war script in package.json so you can run it with npm run test:bidding-war.
  • It explains that to make the race reliable (not “maybe we get lucky”), the test installs a temporary PostgreSQL trigger that slows down inserts for that one test auction, so simultaneous bids always collide. A trigger is a small piece of code the database runs automatically on an event such as “before a row is inserted”; here it just adds a short delay, which widens the gap between check and insert so the bug shows up every time.
  • It runs the baseline checks (server and web tests, TypeScript) to make sure nothing was broken while adding Playwright.
  • Finally it runs BIDDING_WAR_HOLD_MS=3600000 npm run test:bidding-war and browser windows start popping up on your screen. BIDDING_WAR_HOLD_MS=3600000 is an environment variable: a setting passed to the command through the shell. Here it tells the test to hold the windows open for 3,600,000 milliseconds (one hour) after the auction ends, so you can look at the result instead of the windows vanishing instantly.

Key takeaways

  • “Read, check, insert” as separate statements is a race condition: two simultaneous requests can both pass the check and both write. The fix, coming in Part 3, is a transaction with a row lock (SELECT … FOR UPDATE), which makes bidders on one auction wait their turn.
  • Reproduce the bug before fixing it. A test that is red because of the bug, and turns green after the fix, is proof. An agent's “done” is not.
  • Sequential tests cannot find concurrency bugs. You need a test that deliberately makes things happen at the same time; a headed Playwright test with four windows lets you watch it happen.
  • Tests, type checks and reviews are back pressure: they let Codex check and correct itself. More back pressure means you can move faster, not slower.
  • One task, one chat. A fresh chat plus well-kept AGENTS.md and GRILL.md files beats a long chat every time.
