16. Code Reviews with Codex & Claude

Have Codex review your Part 3 commit with its built-in code review, learn to read the P1/P2 findings and decide what deserves a fix, and (optionally) get a second opinion from a different model, Claude.

Code review≈ 15–25 min hands-on/reviewClaude part optional

What you'll do

  • Confirm that your last Git commit is the Part 3 work, so the review has a clean target.
  • Find Codex's built-in Code review in the / menu and understand its two modes.
  • Ask Codex to review your last commit, and steer it away from external review skills if it tries to use one.
  • Read the findings: priority badges (P1/P2), file and line for each, and decide, one by one, whether they matter for this project.
  • Optional: ask Claude for a second opinion, because a different model catches different things.

Before you start

  • You committed Part 3 at the end of guide 15 (or ran the catch-up command, which commits for you). Your last commit must be the Part 3 work; Step 1 checks this.
  • With an API key sign-in, local code review inside the Codex app works fine. Codex's GitHub pull-request reviews and cloud reviews do not work with an API key, and this guide does not need them.
  • The Claude steps (6 and 7) need a separate Claude subscription or Anthropic API access. If you do not have one, read them and move on; nothing later depends on them.

📘 Concept: code review

In a software team, nobody's code goes into the product unread. A second engineer reads the diff (the exact lines that changed) and looks for bugs, security holes, missing tests and unclear code, then leaves comments pointing at a file and a line. The author fixes what matters and explains what does not. This is code review, and it is the single biggest reason team code is better than solo code. When an AI agent writes the code, review becomes even more important, not less: the agent is fast, confident and sometimes wrong. In this guide the reviewer is also an AI. Your job is the judgement at the end: which findings are real, which are noise, and which are real but not worth fixing today.

1

Check what your last commit is

The review in this guide targets the last commit. If your last commit is something else, or if you have uncommitted files lying around, the review will look at the wrong thing. Thirty seconds of checking saves a confusing review. Run this in the Terminal app.

❯Run in TerminalTerminal app · workshop folder
cd ~/codex-course/workshop && git status --short && git log --oneline -3

Three commands joined with && (each runs only if the previous one succeeded): cd ~/codex-course/workshop moves into your workshop; git status --short lists files that changed since the last commit, one per line, and prints nothing when everything is committed; git log --oneline -3 shows the last three commits, one line each, newest first, with a short id and the message.

📘 Concept: git commit and diff

A commit is a saved snapshot of the whole project with a message. The short id in front of it (like a1b2c3d) is how Git names that snapshot. A diff is the set of line-by-line differences between two snapshots: lines added, lines removed, per file. “Review the last commit” therefore means “read the diff between the Part 2 snapshot and the Part 3 snapshot”, which is exactly everything Codex built in guides 13–15. This is why we committed before reviewing: the commit draws the boundary that tells the reviewer what to look at.

✓ You should see

git status --short prints nothing (no uncommitted changes). The top line of the log is your Part 3 commit, for example a1b2c3d Part 3: bid concurrency protection and auction closing (or Catch up: part 3 from reference if you used the catch-up command). Your short id will be different; it is random.

💡 Tip

If git status --short lists files, commit them first (guide 15, Step 7). If the top commit is not Part 3, stop and work out why before continuing; do not review a half-finished state.

2

Start a new chat and open the Code review menu

In Codex, hover over workshop in the left sidebar and click the pencil icon that appears to start a new chat. A review is a new task, so it gets a new chat; the Part 3 build chat is full of context about writing the code, and we want a reviewer that comes in cold. Now type / (just the slash) in the message box. A menu of built-in commands and skills pops up. Click Code review, described as “Review uncommitted changes or compare against a branch”.

📘 Concept: slash commands and skills

Typing / at the start of the Codex message box opens a menu of slash commands. Some are built into Codex (like Code review); others are skills you installed, such as the grilling skills from guide 5. A skill is a folder with a SKILL.md file that tells Codex how to do one job well. Picking an item from the menu either runs it directly or inserts the command into your message so you can add detail after it. Press Esc to close the menu without choosing anything.

📘 Concept: branch and base branch

A Git branch is a separate line of commits. The default one is called main or master. Engineers usually do a feature on its own branch, then ask for a review that compares the feature branch with the base branch it started from: “show me everything this branch changed relative to main”. That is what “Review against a base branch” does. Our workshop so far has only one branch, so we do not use that mode here; it becomes useful in guide 22, when we work in a worktree on its own branch.

✓ You should see

After a short “Loading review options…”, two choices: Review uncommitted changes and Review against a base branch (followed by a list of branches; yours shows a local branch such as master or main, because the workshop has no remote). Press Esc to close the menu. Everything is committed, so there is nothing uncommitted to review, and we have only one branch.

💡 Tip

The first time I did this I clicked Review uncommitted changes out of habit. It sends “Please review my uncommitted changes” in Review mode, and I had to stop it, because I wanted the last commit instead. Remember that option for next time: run it before you commit, while the changes are still uncommitted. “Against a base branch” is the mode I use most in real work, when a feature lives on its own branch in a worktree.

3

Ask Codex to review the last commit

Start another new chat (pencil icon next to workshop), so the aborted menu from Step 2 leaves nothing behind. Type the line below and press Enter. The built-in menu has no “last commit” option, so we type the command and add plain English after it. That is fine: /review puts Codex into review mode, and “last commit” tells it what to look at. Codex understands the intent.

✦Paste into CodexNew chat in workshop
/review last commit

Why this matters: a review done in the build chat would be biased by everything that chat already believes about the code. A fresh chat reads the diff the way a colleague would: without memory of the reasoning, only the result.

✓ You should see

Your message /review last commit appears in the chat and Codex starts working: it runs git commands to find the commit, reads the changed files, and begins running tests. The chat gets a title like “Review last commit”.

💡 Tip

If pressing Enter picks an item from the / menu instead of sending your message, press Esc to close the menu, then press Enter again.

4

If Codex picks a review skill, stop and steer

On my machine I have extra review skills installed, so when I ran this Codex announced “I'm using the codex-code-review skill…”. That skill hands the review to an external reviewer, which is not what I wanted here; I wanted Codex's own built-in review. So I pressed Stop (the square button where Send normally is) and sent the message below. You installed only the four grilling skills in guide 5, so you will most likely skip this step. Use it only if Codex mentions a review skill by name.

✦Only if Codex says it's using a review skillSame review chat
don't use that skill please, just use your internal review tool to review the last commit

The lesson is general: when Codex picks a tool you did not intend, do not let it run to the end and then complain. Stop early, say plainly what you want, and let it restart. Every minute an agent spends on the wrong path costs tokens.

✓ You should see

Similar to: “Understood—I won't use the external review skill or CLI. I'll review the last commit directly with the built-in workspace tools, focusing on concrete regressions introduced by that commit.” (A “regression” is something that used to work and now does not.)

5

Read the review findings

Wait for the review to finish; in my run it took about 3 minutes. Codex does not just read the diff. It runs the backend and frontend tests and the TypeScript checks itself, so its findings are backed by evidence, not only by reading. When the findings arrive, click each one to expand it. Each shows a short title, a priority badge, the file and line range, and a paragraph explaining the problem.

📘 Concept: P1 / P2 severity

Reviewers rank findings so the author knows where to look first. P1 (priority 1) means “this is a real bug or risk that affects users or data; fix it before shipping”. P2 means “worth fixing, but the product works without it”: a missing feature behind a button, an inefficiency, unclear code. Some teams go on to P3 for nitpicks. The number is the reviewer's opinion, not a law. Your job is to read each finding, decide whether you agree with the severity, and then decide whether it matters for what you are building. In a course project we deliberately leave some P1s alone that we would never leave in production.

✓ You should see

A Review findings message, similar to:

  • Verification completed: server tests 8 passed, web tests 8 passed, server and web TypeScript checks passed, worktree remained clean (meaning the review did not change any files)
  • a small Mermaid diagram (React/Vite Web App → Fastify API → PostgreSQL)
  • a “5 comments” card. Each comment has a priority badge (P1 = more serious, P2 = less) and a file:lines link that opens the code at that spot.

My five: P1 “Expired auctions remain in the live catalog” (server/src/app.ts), P1 “Slug allocation races concurrent listings”, P2 “Sort control has no behavior” (web/src/App.tsx), P2 “Category selection is ignored”, P2 “Countdown only refreshes at the deadline”. Yours will differ in number and wording.

Look at my second P1 for a moment: two sellers creating listings at the same instant could be given the same URL slug. That is the same check-then-act race we just fixed for bids, showing up in a different place. Once you know the pattern you start seeing it everywhere, and that is exactly what a good reviewer does. I did not fix any of the five. I judged each against what we are building (a learning project with a handful of test users) and decided none of them matters for this course. In a real product the two P1s would be fixed before release.

💡 Tip

Codex may report that its sandbox blocked the connection to Postgres (an EPERM error) and then rerun the tests with local-service access. The sandbox is the restricted environment Codex runs commands in; by default it cannot reach network services, even on your own machine, until it asks for permission. That message is normal, not a failure.

6

Optional: get a second opinion from Claude

Here is my point with this step: a model reviewing code it wrote itself shares the blind spots of the author, because it is the author. A different model, trained differently, finds different things. So I open Claude in the same repository folder (model Opus 5, effort High) and ask it for an independent review of the same commit. This needs a separate Claude subscription or Anthropic API access; skip the step if you do not have one.

If you have Claude Code (Anthropic's command-line coding agent, started with the claude command), open the Terminal app and start it inside your workshop folder. It then sees the same files and the same Git history that Codex sees.

❯Run in TerminalTerminal app · starts Claude Code in the workshop
cd ~/codex-course/workshop && claude

Now paste the prompt into Claude, not into Codex. The second sentence matters: like Codex, Claude may have custom review skills available, and we want its own built-in judgement, so the comparison is model vs model.

✦Paste into Claude (not Codex)Claude Code in Terminal, or the Claude desktop app
do a code review on the last commit in this app. do not use any custom review skills, just use your own internal review tools
✓ You should see

Claude starts with something like “I'll start by looking at the last commit”, then runs a series of commands and narrates them (in my run: “A full new slice. Let me read the substantive files…”, then “Postgres is up. Let me empirically verify two suspected defects.”). Notice that last line: it does not just suspect a bug, it starts the database and tries to trigger the bug. The review takes several minutes. When it finishes, put its findings next to Codex's: some overlap, some are new, and each list has items the other missed.

⚠ Heads up

Reviews read the whole diff, read surrounding files and run the test suites, so they use a fair number of tokens on either side. Two full reviews of one commit is a real cost; do it for work that matters, not for every small change.

7

Just know: the Claude Code Review skill

One more tool, for information only. In Codex I can type /claude and the menu shows a Claude Code Review skill I have installed (“Review code changes for bugs, security issues, and code quality using Claude…”). It makes Codex send the diff to Claude Code, take Claude's findings, push back on the ones it disagrees with, and argue over the findings for several rounds. This is an adversarial review: two reviewers challenging each other, so weak findings get dropped and strong ones get confirmed. It is totally optional, and you did not install it in guide 5.

If you want it later, run the installer again (same command as guide 5, in the Terminal app) and this time tick claude-code-review in the list. It needs the Claude Code CLI (claude) installed and signed in, because Codex calls that command to talk to Claude.

❯Optional: install laterTerminal app · any folder
npx skills@latest add schneidenbach/skills

After installing, you can read exactly what the skill tells Codex to do by opening ~/.agents/skills/claude-code-review/SKILL.md in VS Code. Reading a skill file before using it is a good habit; it is just plain instructions, nothing magic.

✓ You should see

Nothing to run in this step. The skill is read-only: it reports findings and does not change any files.

⚠ Heads up

Very token-heavy. On a $20/month Claude plan, one round once used up my whole five-hour allowance. Sometimes I also have to tell Codex explicitly that it is allowed to send the code to Claude before it will run the skill.

Stuck or got a very different result?

If Codex reviews something other than Part 3 (for example it says “no changes found” or talks about Part 2 files), go back to Step 1: either you have uncommitted files or the last commit is not Part 3. If the review runs for more than ten minutes with no findings, press Stop, open a new chat and send /review last commit again.

If you do not have a Part 3 commit to review at all, take the finished reference Part 3. The reference folder is the end state of the whole part. The command below deletes your Part 3 (cannot be undone), copies the reference in, and commits it, so it becomes your last commit and the review in Step 3 has something to look at.

❯Run in TerminalTerminal app
cd ~/codex-course/workshop && rm -rf part-3-business-rules-concurrency && cp -R ../reference/part-3-business-rules-concurrency ./ && git add -A && git commit -m "Catch up: part 3 from reference"

Key takeaways

  • Codex has a built-in Code review with two modes: review uncommitted changes, or compare against a base branch. For a finished commit, just type /review last commit in a fresh chat.
  • Review in a new chat, and commit before you review, so the reviewer sees a clean diff with no memory of how the code was written.
  • P1 means “real bug, fix before shipping”; P2 means “worth fixing, not blocking”. The badge is an opinion. You decide what matters for what you are building, and you do not have to act on every finding.
  • A model reviewing its own code shares its own blind spots. In my experience a second model (Claude) finds things the first one missed, and the two lists together are far better than either alone.
  • Use the strongest model you can afford for reviews. I would not trust a small model with one; a review that misses the one real bug is worse than no review, because it gives you false confidence.
