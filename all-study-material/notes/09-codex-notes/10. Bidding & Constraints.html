Use any Git tool you like: VS Code's Source Control panel (the branch icon in the left bar, or Ctrl+Shift+G) with a message and the ✓ Commit button, or the single Terminal command below.

What the three parts do, joined by && (which means “only continue if the previous part succeeded”):

A line like [master 1a2b3c4] part 2 slice 1 followed by a count such as 42 files changed. 📘 Concept: vertical slices

A slice is one thin, complete piece of a feature that goes all the way through the stack: the database change, the server code, the web page, and the tests for it. “Post an auction” is a slice: a form in the browser, a server route that receives the form, a row written to the database, and a page that shows the new auction. The alternative, building the whole database first, then the whole server, then the whole frontend, means you cannot click anything until the very end. With slices you can check something real in the browser after every step, which is exactly how I want you to work with an agent: build a little, verify, commit, repeat.

✓ You should see

A reply similar to: “I'm starting Slice 2: a complete “post an auction” path. I'll add the validated Fastify endpoint, derive artwork and seller ownership server-side, add the Sell navigation and /auctions/new page, redirect successful posts to their database-backed detail page, and verify that the new auction survives refresh and appears in catalog/search. I'll stop again after this slice for your review.”

A new to-do list appears above the message box showing Step 1/3. In my run this slice took about 7 minutes. Let it work; the next step shows you what to look at while you wait.

💡 Tip

“Derive seller ownership server-side” is a small but important phrase. It means the server decides who the seller is (the currently active user) instead of trusting a value sent from the browser. Anything the browser sends can be edited by a user, so the server must never trust it for ownership or money.

4

Watch the changes in Git

While Codex builds, I like to watch the list of files it is touching. You do not need to read every line; you want to know which files change, and whether that matches what Codex said it would do. Any Git view works: VS Code's Source Control panel (Ctrl+Shift+G) lists changed files live, or run this command in Terminal every minute or so.

❯Run in TerminalTerminal app · any folder
cd ~/codex-course/workshop && git status --short

git status --short prints one line per changed file. The two letters at the start tell you the kind of change: M means an existing file was modified, ?? means a new file that Git has not seen before, D means deleted. Because you committed in Step 2, everything listed now belongs to Slice 2 only.

📘 Concept: API route (endpoint)

The browser and the server talk over HTTP. The server exposes a list of addresses it answers to, called routes or endpoints, each with a method. GET /api/auctions means “give me the auctions”; POST /api/auctions means “here is a new auction, save it”. The web page calls these endpoints behind the scenes when you click. Our server is written with Fastify, a Node.js library whose job is to receive these HTTP requests, run our code, and send back a response. When you see “a new create-auction route” in the diff, that is a new POST /api/auctions handler being added to app.ts.

✓ You should see

Changed files inside part-2-create-auction-and-bid, similar to server/src/app.ts (the new create-auction route), server/src/app.test.ts (a test for it), web/src/catalog.ts, a new web/src/components/NewAuctionPage.tsx (the Sell form), web/src/App.tsx (the new page wired into the app's navigation) and web/src/style.css.

Notice the pattern: one server file, one server test, a few web files. That is the shape of a slice.

💡 Tip

How closely should you watch? My rule: the riskier or more important the feature, the more closely I follow along. Money, permissions and anything concurrent get my full attention. A plain create-and-list slice like this one only needs a quick look at the file list and a proper check in the browser afterwards.

📘 Concept: input validation (Zod) and prices in cents

Two things from Codex's summary deserve a word. Validation means the server checks every incoming field before it touches the database: is the title non-empty, is the price a positive whole number, is the closing time in the future. Zod is the library our server uses to describe those rules and reject bad input with a clear error. Integer cents means a price of $20,000 is stored as the whole number 2000000, not as 20000.00. Computers cannot store most decimal fractions exactly (0.1 + 0.2 is not quite 0.3), so every serious money system stores the smallest unit as a whole number and only formats it as dollars for display. This was your Q6 answer from the grilling session.

📘 Concept: business rules and constraints

A business rule is a rule of the product, not of the programming language: “a seller cannot bid on their own auction”, “a bid must be at least $1 above the current price”, “no bids after the auction ends”. The server must enforce every one of them, because the browser can be bypassed by anyone with a terminal and curl. Rules can be enforced in two places. In code: the route handler reads the auction, checks the rule, and rejects the request if it fails. Or as a database constraint: a rule written into the table itself, such as “this column cannot be empty” or “this pair of values must be unique”, which the database refuses to break no matter who writes to it. Slice 3 enforces its rules in code. In Part 3 you will see why some rules also need help from the database.

✓ You should see

A reply similar to: “I'm starting the final slice on the existing ConnectX-7 auction. I'll add the sequential bid endpoint and domain checks, return auditable bid history with auction details, wire the active-user bid form with seller/ended/minimum-bid states, and browser-test rejected self/low bids plus accepted bids from multiple users. Simultaneous-bid locking will remain intentionally out of Folder 2, as agreed.”

Soon app.ts gets a new POST /api/auctions/:slug/bids route (the :slug part is a placeholder for the auction's URL name). Inside it you will find checks such as “Sellers cannot bid on their own auctions” returning HTTP status 409, an ended-auction check, and a minimum-bid check.

💡 Tip

HTTP 409 Conflict is the status code a server uses to say “your request is well-formed, but it clashes with the current state of things”. It is the right code for a rejected bid: the request was fine, the rules said no. Compare with 400 (you sent garbage) and 404 (that auction does not exist).

“Out of Folder 2, as agreed” is your Q13 answer at work. Two people bidding at the exact same instant is a hard problem, and we deliberately pushed its fix to Part 3. Guide 11 shows you exactly what goes wrong when we do not handle it.

While Slice 3 builds, let's answer a question every learner asks me: “when should I start a fresh chat?” Codex can show you a meter for how full the current chat is. Turn it on:

⚙ Codex settings
AlsoSettings → General → Composer → Show context window usage: On
📘 Concept: context window and tokens

The model does not remember your chat the way you do. Every time you send a message, Codex sends the whole conversation so far (your prompts, its replies, the files it read, the command output it saw) to the model again, and the model answers from that. The amount it can take in one go is the context window, measured in tokens, which are word-pieces of roughly three-quarters of an English word each. A long build like Part 2 fills the window fast because every file Codex reads and every test run it watches is added to it. When the window is nearly full, two bad things happen: older details get pushed out, and the model's answers get vaguer. That is why you want to see the meter.

✓ You should see

A small donut chart next to the model picker. Hovering shows something like Context window: 74% full, 190k / 258k tokens used. Mine was at 74% after almost three slices of work in one chat, which is a lot.

💡 Tip

The underlying model can take close to a million tokens, but Codex caps a chat at about 258k, because models start to drift with very long context. When a chat gets close to the cap, Codex compacts it automatically (Step 9 shows you how to do it yourself). My habit: one chat per feature, a new chat for the next feature, and a new chat any time the agent starts giving odd answers.

The Speed setting higher up on the same page (Fast shows a ⚡ next to the model name) can stay as it is.

Compact the chat

Wait for Slice 3 to finish (about 4 minutes in my run) and read its summary. Then shrink the chat before we do anything else in it. Type /comp in the message box; a small menu of slash commands pops up above it. Pick Compact. Codex writes a summary of the chat so far, and from then on sends that short summary to the model instead of the full history.

≡Type in Codexmessage box, then pick Compact from the menu
/comp
📘 Concept: compaction

Compaction replaces the long transcript with a condensed version of it: what the task is, what decisions were made, which files were changed, what is still open. Think of it as a hand-over note you would write for a colleague taking over your work. The model keeps the important facts and loses the noise (every test log, every file it skimmed). The trade-off is real: anything not in the summary is gone for the model, so compact at a natural pause, after a slice is finished and committed, not in the middle of a fix.

✓ You should see

The menu shows Compact – Compact this chat's context (76% full). After you pick it, Codex shows Compacting context for a few seconds, and the donut drops a lot. In my run it went from about 190k tokens down to about 8k. The chat looks the same to you; only what gets sent to the model has changed.

💡 Tip

The Codex app has no /clear command. To start completely fresh, click New chat. Also, since you are signed in with an API key, every message re-sends the chat's context and you pay for those tokens. Cached tokens are cheaper than fresh ones, but a 10k-token context still costs far less than a 190k one. Compacting saves money as well as quality.

Test the bid rules in two tabs

Codex says it browser-tested the bid rules. Now you check them yourself; never take an agent's word for a business rule. You need two users, so you need two tabs with two different identities:

  1. In the tab where you posted your auction in Step 5 (so you are the seller there), open that auction's page.
  2. Open a new tab (Cmd+T, not “Duplicate Tab”) and paste the same auction URL. Check the top right shows a different user. If it shows the seller again, use the Browsing as switcher in the footer to pick someone else.
  3. As that second user, type exactly the starting price, 20000, in the bid box and click Place bid.
  4. Then type the starting price plus one, 20001, and place the bid again.
  5. Go back to the seller's tab and reload it.
✓ You should see

Codex's summary, similar to: “Minimum bid is current amount plus $1.00. Ended auctions reject bids. Accepted bids update price, bidder, and count immediately. Newest-first bid history with bidder, amount, and timestamp…”, ending with “The intentional boundary remains: ordinary sequential bids are correct, while simultaneous-bid locking is deferred to Folder 3.”

In Chrome:

  • As the seller: the text You are selling this auction. and a greyed-out Place bid button. The rule is enforced in the UI and in the API (the 409 you saw in Step 7).
  • As the other user, bidding 20000 shows Enter at least $20,001. The bid is rejected because it does not beat the current price by at least $1.
  • Bidding 20001 shows Bid accepted. You are the highest bidder. The price becomes $20,001 · 1 bid, and the bid appears under Bid history with the bidder's name, the amount and the time.
  • After reloading the seller's tab, it also shows $20,001 and 1 bid, because both tabs read from the same database row.
💡 Tip

“Duplicate Tab” copies the tab's saved storage, including the chosen user, so you would still be the seller. That is why I open a plain new tab instead.

I would rather let the very first bid equal the starting price exactly, but I leave it as it is for now. It is a product decision, not a bug.

Key takeaways

  • Approve slices one at a time. Check each one in the browser with your own hands before you say “continue”; an agent's “verified” is a claim, not proof.
  • Commit after every slice. A commit is a free checkpoint, and it keeps each slice's diff small enough to actually review.
  • Business rules live in the API, not just the UI. The server rejects bids on your own auction, bids that are too low, and bids on ended auctions, and answers with 409 Conflict.
  • Money is stored as integer cents and validated on the server (Zod), never trusted from the browser.
  • Watch the context-window meter. Compact at a natural pause, and start a new chat for a new task or as soon as the agent starts drifting.
  • Simultaneous bids are still unsolved on purpose (your Q13). That is the whole story of guides 11 to 14.
