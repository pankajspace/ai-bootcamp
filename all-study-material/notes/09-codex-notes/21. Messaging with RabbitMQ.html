📘 Concept: worker processes

Until Part 5 our backend was one program: the API server. From Part 6 it is three. A process is simply one running program with its own memory. The API process answers HTTP requests and holds the WebSocket connections. The close worker process does nothing but poll the database and close auctions. The notification worker process does nothing but read messages from RabbitMQ and push popups. They share the same codebase (all three live in server/src/) and the same database, but each one can be started, stopped, crashed and restarted on its own. That is why npm start now prints four prefixes in the log: one per process, plus the web app.

📘 Concept: exchange, routing key, queue, ack

Inside RabbitMQ a message does not go straight into a queue. The producer sends it to an exchange, a kind of sorting office, together with a routing key, a short label such as auction.closed. The exchange looks at the key and copies the message into every queue that has asked for messages with that key (this is called a binding). A consumer reads from a queue, one message at a time. When it has finished the work it sends an ack; only then does RabbitMQ delete the message. If the consumer dies before acking, the message goes back on the queue and is delivered again. In our project Codex declares one exchange (auction.events in the reference copy) and one queue (auction.notifications) bound to it. You will see both in the dashboard in step 7.

📘 Concept: loose coupling (why not just call the other service?)

The obvious alternative is for the close worker to call the notification service directly over HTTP: “hey, auction 42 closed, go notify people”. That builds a chain: for a close to succeed, the notification service must be up, reachable and fast at that exact moment. Add two more services to the chain and the whole feature breaks whenever any one of them is restarting. A queue works like a post office: the close worker drops the letter and walks away, and the notification worker collects it whenever it is ready, even if that is ten seconds later after a restart. Neither service needs to know the other's address or whether it is alive. This is loose coupling, and it is the main reason real systems put a queue between workers.

  • server/src/app.ts: the API now returns the winning-bid fields on an auction, read from the close row.
  • tests/bidding-war.spec.ts: updated to point at the Part 6 URL and database, so the war from Part 4 still runs here.
📘 Concept: migration and SKIP LOCKED

A migration is a numbered SQL file that changes the database's structure: create a table, add a column. They run in order (001, 002, 003…) on every machine, so everyone's database ends up with the same shape. Codex adds 002_… because Part 4 already had 001. SKIP LOCKED is a PostgreSQL option on a locking SELECT: “give me the due auctions, but if another transaction is already holding one of those rows, skip it instead of waiting”. The result is that you can run two or three close workers at once and they will never fight over the same auction, nor block each other. One line of SQL, and the worker is safe to scale.

✓ You should see

Mostly green (new) lines. A migration similar to:
CREATE TABLE auction_closes (auction_id … PRIMARY KEY, closed_at …, winning_bid_id … UNIQUE REFERENCES bids(id))
CREATE TABLE outbox_events (id uuid PRIMARY KEY, event_type …, payload jsonb …, published_at timestamptz, UNIQUE (event_type, auction_id))

Read the constraints: auction_id … PRIMARY KEY means an auction can be closed only once. UNIQUE (event_type, auction_id) means there can be only one AuctionClosed event per auction. published_at being empty is how the publisher knows a row still needs sending. The database itself enforces “one close, one event”, which is idempotency at the first boundary.

💡 Tip

I like that the winning bid is stored on the close row (winning_bid_id) rather than recomputed from the bids table every time someone opens the page. A close is a historical fact; store it. And the polling worker? Is it a perfect architecture? Maybe not. Will it keep working reliably for years? Yes. Simple and boring beats clever here.

4

Review Slice 2's code

Same review panel, Last Turn again, which now shows only Slice 2's files. New pieces to look at:

  • 003_notification_deliveries.sql in server/migrations/: a table with one row per event and recipient, with UNIQUE (outbox_event_id, recipient_user_id). This is the idempotent consumer from guide 20 made real: if RabbitMQ redelivers the same event, the second insert for the same recipient fails the unique check, so no second popup.
  • server/src/close-worker.ts: the close worker now also publishes pending outbox rows to RabbitMQ on a confirm channel, meaning it waits for RabbitMQ's “got it” before setting published_at.
  • server/src/notification-worker.ts: the separate process that consumes from RabbitMQ, decides the recipients, and emits through Redis to Socket.IO.
  • server/src/notificationDelivery.ts: INSERT … ON CONFLICT DO NOTHING, then emit. “On conflict do nothing” is PostgreSQL for “if this row already exists, skip quietly instead of throwing an error”. Insert first, emit second: if the insert was skipped, there is nothing to emit.
  • tests/outcome-notification.spec.ts: the multi-window Edge check that opens seller, winner and an unrelated user and asserts who gets a modal.
  • web/src/…/OutcomeModal.tsx: the React component for the popup itself, with the dismiss button and the three text variants.

Key takeaways

  • Message queues decouple services. The close worker drops a message in RabbitMQ and moves on. The notification worker picks it up when it is ready. No chain of HTTP calls that all have to be up at the same time.
  • Outbox + publisher confirms + idempotent consumer is the full reliability recipe: the close and its event commit together in Postgres, the event is marked published only after RabbitMQ confirms it, and a unique delivery row per (event, recipient) stops duplicate popups when a message is redelivered.
  • Let the database enforce “only once”. PRIMARY KEY, UNIQUE and ON CONFLICT DO NOTHING do more for correctness than any amount of careful application code.
  • Polling with SKIP LOCKED lets several close workers run safely side by side. Polling is simple and boring, and that is a compliment.
  • Work alongside Codex: read the diff while it builds, and queue the next instruction when the tests you care about are green. Save your own browser check for slices that have a visible UI.
  • Verify the whole chain, not just the code: the bidding war, a hand-made auction, and the RabbitMQ dashboard each showed you a different part of the same message's journey.
