📘 Concept: tech stack

A tech stack is the list of languages, frameworks and services an app is built from, layer by layer: what runs in the browser, what runs on the server, where the data is stored, and the helper services around them. Choosing the stack is one of the most important decisions in any project, because every later decision depends on it. In this course I chose the stack before asking Codex to write a single line, and I tell Codex exactly what to use. If you leave the choice to the AI, you get whatever was most common in its training data, and you will not understand why it picked what it picked.

📘 Concept: frontend, backend, database

Almost every web app has three layers. The frontend is what runs in the user's browser: buttons, forms, the list of auctions. The backend (also called the API or the server) is a program running on a machine somewhere that the frontend talks to: “give me the auctions”, “place this bid”. The database is where the backend stores data permanently, so it survives restarts. The frontend never touches the database directly; it always goes through the backend, which checks the request and enforces the rules. Keep this picture in mind while you read the stack list below.

✓ You should see

In the README, find these three sections:

  • Stack: TypeScript + ESM, React + Vite, Fastify, Zod, PostgreSQL, Redis + Socket.IO, RabbitMQ worker, OpenTelemetry + Jaeger, Docker Compose (infra in Docker, apps on host).
  • The parts: a table with one row per folder and the slice each part adds. Part 1 is the React → Fastify → Postgres “health path”: a page that asks the server, which asks the database, “are you alive?”.
  • Anatomy of a part: inside every part folder, GRILL.md records the questions asked and the decisions locked before building; CODEX.md records the prompts used, what Codex did and the steering feedback given; codex-logs/ holds the raw Codex transcripts; everything else is the app itself at that stage.

Here is what each item in the Stack line does, in plain words. You do not need to memorise this; come back to it whenever a name confuses you.

  • TypeScript: JavaScript with types, so mistakes like passing text where a number is expected are caught before the code runs. The whole app, frontend and backend, is TypeScript. ESM is the modern way TypeScript files import each other.
  • React + Vite: React builds the frontend out of reusable components. Vite is the tool that bundles it and serves it on your machine while you develop.
  • Fastify: the backend web framework. It receives requests from the browser, runs our logic and sends back responses.
  • Zod: validates data. When a bid arrives from the browser, Zod checks it has the right shape (a number, not empty, not negative) before our code trusts it.
  • PostgreSQL: the database. Auctions, bids and users live here as rows in tables.
  • Redis + Socket.IO: real-time updates. When someone bids, every other browser watching that auction sees the new price instantly without refreshing. Socket.IO keeps the live connection; Redis lets several server copies share those messages.
  • RabbitMQ worker: a message queue plus a background program. Slow or risky jobs (closing an auction, charging the winner) are put on a queue and handled by a separate worker, so the web server stays fast.
  • OpenTelemetry + Jaeger: observability. They record what happened inside each request so you can see where time went when something is slow or broken.
  • Docker Compose: runs the services (Postgres, Redis, RabbitMQ, Jaeger) in containers, while our own apps run directly on the Mac. That is what “infra in Docker, apps on host” means.

📘 Concept: vertical slice

Each part of this app is a vertical slice: one thin feature built all the way through, from the button in the browser, through the backend, down to the database table. Part 1 is the thinnest possible slice (a health check). Part 2 adds “create an auction and place a bid”, again top to bottom. The opposite approach, building the whole database first, then the whole backend, then the whole frontend, means nothing works end to end until the very end. Slices mean you have a working app after every part, and Codex gets a small, clear job each time.

4

Look at the Docker services

docker-compose.yml is the file that defines the Docker services the app will need. Instead of opening it and reading YAML, ask Docker to list the service names for you:

❯Run in TerminalTerminal app
cd ~/codex-course/workshop
docker compose config --services

docker compose config reads the docker-compose.yml in the current folder and checks it. --services tells it to print only the service names, one per line. This command only reads the file; it does not start anything.

📘 Concept: Docker Compose and services

In guide 1 you learned that a container is an isolated box running one piece of software. Docker Compose lets you describe several containers in one file, docker-compose.yml, and start or stop them all with one command. Each named entry in that file is a service: which image to run, which port to open, which password to set. Later, docker compose up -d will start every service in the background, and docker compose down will stop them. Your Mac stays clean because nothing is installed outside the containers.

✓ You should see

Four names, in any order: postgres, redis, rabbitmq, jaeger. These are the four pieces of infrastructure the finished app depends on: the database, the real-time message sharer, the job queue and the tracing viewer. Part 1 only needs postgres; the others switch on in later parts as the app grows.

💡 Tip

If you see “Cannot connect to the Docker daemon”, that's fine for now; the names are usually still printed, because this command only reads the file. If it fails entirely, open the file in VS Code instead (code ~/codex-course/workshop/docker-compose.yml) and look for the four indented names under services:.

📘 Concept: AGENTS.md

AGENTS.md is a plain Markdown file that Codex reads automatically at the start of every chat in that project, before it does anything else. Whatever you write in it becomes standing instructions: which technologies to use, which to avoid, how to run the tests, how to name things. Think of it as the onboarding document you would hand a new engineer on day one. The difference from the custom-instructions box in guide 3 is scope: custom instructions follow you everywhere, AGENTS.md belongs to this project and travels with the code. A project can have one at the root and more inside sub-folders; the closer one wins.

✓ You should see

A file titled Project Guidelines. It holds rules Codex follows automatically, for example “Stay within the core stack: TypeScript, PostgreSQL, Docker Compose, Fastify, Zod, and React/Vite”, plus a Workshop specific stuff section (use Mermaid for diagrams, use Chrome or Edge for browsing, limits on how long grilling sessions may run). You don't need to change anything. Just notice that the stack from the README is repeated here as a rule, so Codex cannot drift to a different database or framework halfway through.

Stuck or got a very different result?

If code says “command not found”, open VS Code, press Cmd+Shift+P, run “Shell Command: Install 'code' command in PATH”, close Terminal fully and open it again.

If the Part 2 count is not 0, or Part 1 is missing files, your workshop copy was not created correctly. Delete it and redo guide 1 step 5; it takes under a minute.

If docker compose says “unknown command”, you have an old Docker that only knows docker-compose (with a hyphen). Update Docker Desktop; the course uses the modern docker compose form throughout.

Key takeaways

  • Libraries: TypeScript (whole stack), React (frontend), Fastify (API), Zod (validate data between frontend and backend), Socket.IO (real-time updates), Playwright (end-to-end browser tests, which we meet in guide 6). I consider Playwright possibly the most important of all, because it is how we prove the app actually works.
  • Services: Docker runs Postgres (database), Redis (cache and pub/sub), RabbitMQ (messaging) and Jaeger (observability). Many real apps can stop at app + Postgres; we go further because the extra pieces teach you the hard parts of backend engineering.
  • Two ways to take this course: “I know nothing about this” (ask Codex to explain each concept as you go) or “I know what I want, I just want to go faster” (my way: pick the stack yourself and let Codex type). Both work; the guides support both.
  • Pick your tech stack yourself, or ask the AI to help you pick and explain the trade-offs. Never let it just choose for you, because you are the one who has to maintain the result.
  • Every part is a vertical slice with the same anatomy: GRILL.md (decisions), CODEX.md (prompts and steering), codex-logs (transcripts), and the app.
