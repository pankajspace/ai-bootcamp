📘 Concept: observability, in one line

Observability is being able to see what your running system did, from the outside, after the fact. In guide 25 we chose traces as our main signal because, unlike logs (text lines per service) and metrics (numbers over time), a trace follows one request through every service it touches. Today you read those traces.

📘 Concept: trace and span

A span is a single timed operation with a name, a start time, a duration and a few labels called tags (for example auction.id = 42). A trace is the set of related spans that together make up one full workflow, even when the spans come from different services minutes apart. Spans form a tree: the request that came in is the root, and every piece of work it caused (a database query, a message publish, a call to Mock Stripe) is a child under it. Jaeger draws this tree as an indented timeline, one row per span, with bar length showing duration.

📘 Concept: OpenTelemetry and the OTLP listener

OpenTelemetry (OTel) is the library inside each of our Node.js services that creates spans and sends them out. It sends them using a standard wire format called OTLP. Jaeger has an OTLP listener, a port that accepts spans in that format, plus a web UI to search and view them. So the flow is: service code → OTel → OTLP over the network → Jaeger stores it → you read it at http://localhost:16686. Nothing in the app shows traces; Jaeger is the only place to see them.

📘 Concept: the Jaeger UI

Jaeger's web page has two screens you care about. The Search screen filters traces by service (which program emitted the root span), operation (the root span's name) and lookback (how far back in time). Each result card shows the root operation, how many spans and services are inside, and the total duration. Clicking a card opens the Trace screen: a header with duration, number of services, depth (how deep the parent/child tree goes) and total spans, then a timeline where every row is one span, indented under its parent and coloured by service. Clicking a row expands it to show its tags, process info and logs.

✓ You should see

The Service dropdown lists the Part 8 services: auction-api, auction-close-worker, notification-worker, mock-stripe (and possibly jaeger-all-in-one, Jaeger's own). The traces you find come from Codex's own test runs while it built Part 8.

The trace page header reads something like auction-api: auction.bid.accept · Duration 1m 37s · Services 4 · Depth 10 · Total Spans 57, with a timeline and an indented list of spans below it. A long duration like that is normal here: the trace runs from the bid until the test paid for the item.

3

Read the spans

Scroll the Service & Operation list on the left of the timeline. Each row is one span: the service name in bold, then the operation name. Rows are indented under their parent, so a Postgres query sits one level under the business step that ran it. Click any row and it expands to show three sections: Tags (the labels we chose in guide 25), Process (which service and host emitted it) and Logs (timestamped events inside the span). Now look for the story you asked for in guide 25:

  • auction-api auction.bid.accept, with pg.query:SELECT/INSERT/UPDATE auction_part_8 children. These are the Postgres spans you kept in Q4: one row per SQL statement the bid ran, against the auction_part_8 database.
  • auction-close-worker auction.close → auction.closed.publish: the worker picked the winner and published the close event to RabbitMQ.
  • notification-worker auction.closed.consume: the second worker received that message and told the seller and winner.
  • auction-api winner.checkout.start → mock-stripe mock-stripe.checkout.create / mock-stripe.payment.attempt → auction-api winner.purchase.mark-paid. These only appear if that auction was paid for.

Why this matters: these 8–10 named spans are the whole reason we grilled in guide 25. Anyone on the team can now open one trace and read the business story without opening a single source file.

✓ You should see

Clicking a pg.query:INSERT auction_part_8 row shows its service, its duration (for example 626µs, that is microseconds, under a millisecond) and tags such as db.name = auction_part_8 and the statement type, but no SQL text, exactly as agreed in Q7. Rows are indented by parent/child, and the bar colour changes per service, so you can see at a glance where the request crossed from the API into a worker.

4

Find the error span

Scan the span list for a row with a small red ! icon next to its name. In my run it was an auction-api POST span sitting under winner.checkout.start. Click it, then click Logs to expand the events recorded inside that span.

📘 Concept: error span

When code inside a span throws an exception, OpenTelemetry marks the span with the tag error = true and attaches a log event carrying exception.type and exception.message. Jaeger shows such spans with a red marker so they stand out in a list of hundreds. That is exactly why we decided in Q6 that rejected bids and declined cards are not errors: if every normal “no” were red, you would stop noticing the red that matters. Red should mean “something actually broke”.

✓ You should see

A span tagged error = true with an exception in its logs. In my run: exception.message connect ECONNREFUSED 127.0.0.1:7107 and exception.type ECONNREFUSED. ECONNREFUSED means “I tried to open a network connection to this address and nothing was listening there”. Notice the port: 7107 is Part 7's Mock Stripe port, while Part 8 runs Mock Stripe on 7108. My best guess is that one of Codex's early test runs still pointed at the old port before it finished updating the config. Your trace may have no error at all, and that is fine.

💡 Tip

This is tracing earning its keep. Without it you would have a vague “checkout sometimes failed in a test” and a pile of logs from five services. With it, one click tells you which service, which call, which address and which error, in context.

✦Paste into CodexAdd Jaeger auction tracing chat
do the bidding wars, then open jaeger full screen and walk us thru the relevant trace
📘 Concept: following one request across API → Postgres → RabbitMQ → worker

The trace Codex is about to show you crosses three processes. The winning bid hits the API, which writes to Postgres (the query spans). A minute later the close worker, a separate program, closes the auction and publishes a message to RabbitMQ. Then the notification worker, a third program, consumes that message. These three never call each other directly, so how do they end up in one trace? The API saved the trace ID in the auction's outbox row; the close worker read it and put it in the RabbitMQ message headers; the notification worker read it from there. Each one continued the same trace instead of starting a new one. This is the trace continuity we asked for in Q2, and it is why Jaeger can show a bid and a notification a minute apart as one story.

✓ You should see

Four tiled windows on http://localhost:5108/items/bidding-war-gpu-… (Codex picks the port; 5108 in my run). Bids climb to $107, then the seller sees Your auction has closed and Theo sees Congratulations.

In my run Codex then noticed a problem: “the very last $107 trace was lost when Playwright shut down the worker processes immediately after the final assertion”. OTel sends spans in batches, and the test killed the workers before the last batch left. Codex re-ran with a short hold, BIDDING_WAR_HOLD_MS=8000 npm run test:bidding-war, giving the workers 8 seconds to flush. Yours may not need this.

Then a browser window opens Jaeger full screen on the winning trace, and Codex writes a walkthrough similar to:

  1. auction.bid.accept: the winning $107 bid. The 805ms PostgreSQL INSERT is the intentional concurrency-delay trigger from the bidding-war test, not a slow database.
  2. auction.close: the close worker selects the winner, records the close and inserts the outbox event.
  3. auction.closed.publish: publishes the message to the auction.events exchange and marks the outbox row as published.
  4. auction.closed.consume: the notification worker receives the same message, creates two delivery records, and emits outcomes to seller and winner.
  5. Total: 18 spans, three services, 2.29 seconds, depth five.
💡 Tip

Codex read Jaeger with plain curl requests to its API. Letting an agent read traces is powerful: it can chase a slow span or an error across services faster than you can click. In production I only allow this with read-only credentials, so the agent can look at anything and change nothing.

Key takeaways

  • A span is one timed operation; a trace is the related spans of one whole workflow. OpenTelemetry creates them inside each service, Jaeger receives, stores and shows them, free and local.
  • Saving the trace context in the database row and in the RabbitMQ message is what turns a bid, a close a minute later and a notification into one trace across three processes.
  • Traces surface real problems fast: a red ECONNREFUSED span tells you which service, which address and which error; an 805ms INSERT stands out in the timeline without reading any logs.
  • Agents are good at digging through traces. Let them, but with read-only access when it is production.
  • Look at what you built across Parts 1 to 8: a real auction house with a React frontend, PostgreSQL with row locking for concurrent bids, Redis for live updates, RabbitMQ with a transactional outbox for reliable close events, Stripe-style checkout with webhooks, and Jaeger tracing across all of it. You planned every part by grilling before building, proved it with bidding-war tests instead of hoping, used /goal for issue-driven work, and learned to hand simple work to cheaper models while keeping the review yourself. That workflow, not any single prompt, is what you take with you.
