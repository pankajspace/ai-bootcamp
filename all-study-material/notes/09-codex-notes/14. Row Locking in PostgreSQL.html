📘 Concept: the race condition we are fixing

In guide 12 you saw the same amount, $107, accepted three times on one auction. Here is why. When a bid arrives, the server does two things: it checks (“is $107 higher than the current price?”) and then it acts (“insert the bid”). If three requests arrive at the same moment, all three read the old price, all three pass the check, and all three insert. Nobody did anything wrong; they simply never saw each other. This is called a check-then-act race condition, and it is one of the most common bugs in any backend that many people use at once. The fix is not “check more carefully”. The fix is to make the bids for one auction take turns.

📘 Concept: injected app clock

Code that needs the current time usually calls Date.now() directly. That is a problem in tests: you cannot make “now” be 11:59:59 to test what happens one second before an auction closes. So instead we build one small clock object and hand it (“inject” it) into the API when the app starts. Real runs get a clock that reads the system time; tests get a fake clock they can set to any moment. The code that checks “has this auction ended?” never knows the difference. “Injected” just means “passed in from outside instead of created inside”.

📘 Concept: transaction (BEGIN … COMMIT)

A transaction is a group of database operations that either all happen or none happen. You open it with BEGIN, do your reads and writes, and finish with COMMIT (save everything) or ROLLBACK (throw everything away as if nothing happened). Think of a bank transfer: debit one account, credit another. You never want only the debit to survive a crash. For a bid, the transaction wraps “read the current price, check the amount, insert the bid” so the whole thing is one unit of work.

📘 Concept: row lock (SELECT … FOR UPDATE)

A database table is like a spreadsheet; each auction is one row. SELECT … FROM auctions WHERE slug = $1 FOR UPDATE reads that one row and locks it until the transaction ends. If a second request runs the same statement for the same auction, PostgreSQL makes it wait at that line until the first transaction commits or rolls back. Then the second one gets the row, reads the new price, and does its own check. This is why the lock serialises bids: bids for one auction now happen strictly one after another, like people taking turns with a single talking stick. Bids on a different auction lock a different row, so they are not slowed down at all. The lock is held only for a few milliseconds, so users never notice the waiting.

✓ You should see

Similar to: “Totally fair. PostgreSQL (‘Postgres’) is the database—the program that stores auctions and bids.” Then a worked example: Maya bids $103 and Theo bids $106 at the same time, and both read $102 as the current price. With locking the backend does:

The lock is described as “the only talking stick for that specific auction”. You will probably also get a small Mermaid diagram (Auction A lock / Auction B lock) showing that different auctions do not block each other.

When the answer arrives, match each quoted line to the picture from Step 3: open a connection, BEGIN, lock the row, re-read, insert, COMMIT. The ROLLBACK in the catch block is what runs if anything throws an error halfway, so a half-finished bid is never saved. The client.release() in finally gives the database connection back to the pool whether the bid succeeded or failed. A pool is a small set of ready-made connections the server reuses, because opening a fresh connection for every request would be slow.

📘 Concept: transaction isolation level

The isolation level is a database setting that decides how much one running transaction can see of other transactions that have not finished yet. PostgreSQL's default is READ COMMITTED: you only ever see data that another transaction has already committed. That is good, but on its own it does not stop our race, because both bidders can read the same committed price before either of them writes. Stricter levels exist (REPEATABLE READ, SERIALIZABLE) that make the database detect such clashes and fail one of the transactions, which you then have to retry. We chose the explicit row lock instead because it is simple to read and needs no retry logic. Isolation levels come up again in guide 15.

✓ You should see

Codex quotes the real lines from server/src/app.ts (your line numbers will differ), similar to:

  • SELECT … FROM auctions WHERE slug = $1 FOR UPDATE: lock this auction row until the transaction ends
  • re-read the latest bid while holding the lock
  • await client.query('COMMIT');: save the bid and release the lock

Key takeaways

  • The duplicate-bid bug was a check-then-act race: several requests read the same old price, all passed the check, all wrote. More careful checking cannot fix it; only taking turns can.
  • A transaction + row lock (BEGIN … SELECT … FOR UPDATE … COMMIT) makes bids for one auction take turns. Each bid re-reads the latest price after it gets the lock, so its check is always against fresh data.
  • Lock only what you need: one auction's row. Bids on other auctions use other rows and are never blocked.
  • Use Codex as a tutor while it builds: ask for the simple version first, then the exact lines, then things to Google. The vocabulary is what lets you keep learning on your own.
  • Trust, but verify. Codex said the tests passed; we still ran the bidding war and read the bid history ourselves.
