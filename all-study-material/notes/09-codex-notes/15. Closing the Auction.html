📘 Concept: what “closing” an auction really means

Every auction has an endsAt time. After that moment, no bid may be accepted. That sounds trivial, but there are two separate problems hidden inside it. First, the backend must decide, for every bid, “did this arrive before or after the deadline?”, and it must make that decision with a clock it controls and can test. Second, the frontend must show the user that bidding is over at the right moment, even if they have had the tab open for ten minutes and never refreshed. Slice 2 solves both. The backend is the authority: whatever the browser shows, the server's decision is final.

📘 Concept: injected app clock (why we don't call Date.now() directly)

The obvious way to get the current time in JavaScript is Date.now(). The problem is that it always returns the real current time, so a test can never say “pretend it is one second before closing and send a bid”. The fix is to put the clock behind a tiny object, for example clock.now(), and inject it (pass it in from outside) when the app is created. In production we pass a real clock. In tests we pass a fake clock that we can set to any moment and move forward by hand. The bid-checking code calls clock.now() either way and never knows which one it got. This is why your tests can prove the closing rule exactly at the boundary, deterministically, every time.

📘 Concept: polling

Polling means the browser asks the server “anything new?” again and again on a timer, for example every two seconds. It is simple, and it is wasteful: a thousand open tabs mean a thousand requests every two seconds, most of them returning “nothing changed”. For the “Ended” switch we do not need polling at all. The page already knows endsAt, so it can set a timer in the browser that fires at that moment, and re-check once if the tab wakes up after sleeping. The server is still the authority on whether a bid is accepted; the timer only updates what the user sees.

📘 Concept: transaction isolation levels

When two transactions run at the same time, the database has to decide how much each one is allowed to see of the other's unfinished work. The isolation level is that setting. Picture two accountants working on the same ledger at the same desk. At the weakest level they can read each other's pencil notes before the ink is dry (“dirty reads”). At Read Committed, PostgreSQL's default, you only see what the other person has finished and signed off; but if you read a value, then they commit a change, then you read again, you may see two different values inside one transaction. At Repeatable Read you work from a fixed photocopy taken when your transaction began. At Serializable, the strictest, the database guarantees the result is as if the transactions ran one after another, and it cancels one of them if that is impossible, so your code must be ready to retry. Stricter levels cost performance and add retry logic. Our auction keeps the default Read Committed and adds one explicit row lock on the auction. That gives us the exact serialisation we need, only where we need it, and nothing has to be retried.

✓ You should see

Similar to: “PostgreSQL—usually called Postgres—is a database system, not a plant.” An isolation level answers “When two database transactions happen at the same time, how much are they allowed to see and interfere with each other?” Then the levels from weakest to strongest:

  • Read Uncommitted: could see unfinished changes (“dirty reads”); Postgres treats it as Read Committed
  • Read Committed: the Postgres default; each statement sees data committed before it began. It does not by itself protect a read-validate-write sequence
  • Repeatable Read: a stable snapshot for the whole transaction
  • Serializable: strongest; Postgres may cancel a transaction, so the app must retry

And “What our auction uses”: the default Read Committed plus a row lock, like a single checkout lane per auction.

📘 Concept: git commit and git diff

A commit is a saved snapshot of the whole project at one moment, with a message. Git stores the chain of commits, so you can always go back to any snapshot. A diff is the difference between two snapshots (or between the last commit and your current files): which lines were added, which were removed, in which files. This is what makes AI-assisted work reviewable. Because you committed at the end of Part 2, the diff since then is exactly “what Codex did in Part 3”, no more, no less. In guide 16 we hand that diff to two different reviewers and ask them to find problems in it. Without a clean commit boundary, there would be no clean diff to review.

Why this matters: commit at the end of every part, before the next one starts. It costs five seconds, it gives you an undo point, and it gives the code review in guide 16 a precise scope.

Key takeaways

  • Inject the clock. Never call Date.now() inside business rules. An injected app clock makes every time-based rule testable at the exact boundary, and a single clock source means the app and the database can never disagree about “now”.
  • Read the time after taking the row lock, so the decision and the stored timestamp belong to the same moment.
  • Isolation levels decide how much concurrent transactions can see of each other. We keep PostgreSQL's default (Read Committed) and add one explicit row lock, instead of paying for Serializable and writing retry logic.
  • Two side-chat habits: tell the model what you already know, and ask “what am I NOT thinking about?” when you are new to a domain. Read the risk list, but do not let it change today's scope.
  • Commit at the end of every part. The commit boundary is what makes the diff reviewable in guide 16.
  • Backend plumbing matters, and so does what the user sees. Verify both in a real browser, then commit.
