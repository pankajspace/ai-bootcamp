19. Finding a Concurrency Defect

Part 5 is a game. We ask the strong Sol model to plant a subtle concurrency bug in a copy of Part 4 and delete the tests that would catch it. Then we switch to the small 5.6 Luna model in a fresh chat, with no memory of the crime, and see whether it can find the bug.

Part 5≈ 15–25 min hands-onModel switch: 5.6 LunaBug hunt

What you'll do

  • Copy Part 4 into part-5-hidden-defect-review and have Codex plant a concurrency defect in the PostgreSQL bidding query.
  • Hide the evidence by deleting the tests that fail because of the defect.
  • Open a new chat on 5.6 Luna and ask it to find the bug, first with a vague question, then with a hard boundary that limits it to the Part 5 folder.
  • Understand the difference between the FOR UPDATE and FOR SHARE row locks, which is the whole bug.
  • Learn why agents “cheat” by reading other folders and Git history, and how to stop them when you want a fair test.

Before you start

  • You finished guide 18 with Part 4 committed, or you caught up from the reference copy (see the box at the bottom of guide 18).
  • Docker Desktop is running. Codex will run Part 5's tests, and those tests talk to a real PostgreSQL. Part 5's npm start brings up Postgres + Redis, exactly like Part 4. Codex will give Part 5 its own addresses: web 5105, API 3105 and database auction_part_5. You do not need to open the app in the browser in this guide; everything happens in Codex and Terminal.
  • Do not commit Part 5 until the hunt is over (step 7). LLMs love reading Git history, and a commit message like “plant concurrency defect” would hand the answer to the hunting model on a plate.

📘 Concept: planting a defect, and small vs large models

Why would anyone deliberately break working code? Because it is the cheapest way to test two things at once. First, it tests you: can you recognise a concurrency bug when you see one? Second, it tests the tool: can a small, cheap model do real detective work in a codebase? Models come in sizes. Sol is the largest and smartest tier, slow and expensive. Luna is the smallest: fast, cheap, and weaker on big open-ended tasks. The question we answer today is practical: for a focused investigation in a small codebase, is Luna good enough? If yes, you can save a lot of money by using Sol to plan and Luna to investigate.

1

Plant the defect (with Sol)

Click New chat under workshop in the left sidebar. Check the picker under the message box still reads 5.6 Sol Medium. We use the strong model to plant the bug because we want it subtle: a one-line change that compiles, typechecks and passes most tests, not a crash. Then send:

✦Paste into CodexNew chat · workshop · 5.6 Sol
copy 4 to 5 and work from 5

introduce a concurrency defect in the postgres bidding query, we're going to see if another LLM can find it

Two things in the wording. “Copy 4 to 5 and work from 5” is the same pattern we used for every new part: Codex copies the previous part's folder, renames ports and database so the two do not collide, and from then on only touches the new folder. The second line tells Codex exactly where to put the bug (the bidding query) and why (another model will hunt it). Telling it the purpose makes it pick a realistic defect rather than something silly.

📘 Concept: concurrency defect (race condition)

A concurrency defect is a bug that only appears when two or more things happen at the same time. Run the code with one user and it is perfect. Run it with two users clicking “bid” in the same millisecond and it breaks. The classic example is ours: two bidders both read “current price is 100”, both decide “105 is valid”, and both bids get accepted, when only the first should have. This is called a race condition because the two requests race each other and the result depends on who wins by a few microseconds. These bugs are nasty because they do not show up in normal testing and they are hard to reproduce. The usual protection is a row lock in the database, which makes the second bidder wait until the first is done.

✓ You should see

Codex inspects Parts 4 and 5, copies Part 4 into part-5-hidden-defect-review and gives it its own config (database auction_part_5, API 3105, web 5105, Redis 56379). It then changes the bid transaction's locking and runs the checks. The summary is similar to: “A subtle PostgreSQL bidding concurrency defect is planted. Verification: server and web typechecks pass; 9 unaffected server tests pass; all 10 web tests pass; the concurrency test fails as intended: three simultaneous equal bids are accepted instead of one.”

Read that last sentence again. Three equal bids accepted instead of one. That is the race condition, and exactly one test in the project knows about it.

💡 Tip

Want to play detective yourself first? Do not open the diff, and do not read step 3, until after step 6. Read Part 5's server/src/app.ts around the bid handler and see if you can spot the change on your own.

2

Delete the failing tests

A failing test would point straight at the bug. The hunting model would just run the tests, read the failure message and be done in ten seconds. That is not a test of its code-reading skill. So we remove the evidence first. Stay in the same Sol chat and send:

✦Paste into CodexSame Sol chat
delete the failing tests

Why this matters beyond the game: this is also what happens in real teams, by accident. Someone changes a query, a test starts failing, and instead of understanding why, they delete or skip the test. Then the bug ships. Keep that picture in your head whenever you are tempted to delete a red test.

✓ You should see

Similar to: “Done :) Removed: the concurrency test and its PostgreSQL delay fixture, tests/bidding-war.spec.ts, the obsolete test:bidding-war npm script. Verification: both typechecks pass; all remaining tests pass. The bidding defect remains planted.” An “Edited 3 files” card lists package.json, server/src/app.test.ts and tests/bidding-war.spec.ts. “All remaining tests pass” is the scary part: the project now looks healthy and is not.

3

Optional spoiler: look at the planted change

I wanted to see exactly what Codex had done. The diff view inside Codex was too large to read comfortably, because the copy step touched many files, so I opened server/src/app.ts in VS Code instead. The command below is even quicker: it prints only the lines that differ between Part 4's and Part 5's copy of that one file. Skip this step if you want to hunt the bug yourself.

❯Run in TerminalTerminal app · workshop folder
cd ~/codex-course/workshop
diff part-4-realtime-socketio-redis/server/src/app.ts part-5-hidden-defect-review/server/src/app.ts

Line by line: cd ~/codex-course/workshop moves to the root of your practice copy. diff A B compares two files and prints only the differing lines: lines starting with < are from the first file (Part 4), lines starting with > are from the second (Part 5), and a header like 286c286 means “line 286 changed into line 286”.

📘 Concept: FOR UPDATE vs FOR SHARE

Both are row locks you add to the end of a SELECT inside a transaction. Picture the auction row as a chair. SELECT … FOR UPDATE says “I am sitting on this chair and I am going to change it; nobody else may sit or change it until I stand up (commit).” A second bidder's transaction has to wait, and when it finally reads the row it sees the new price. That is what makes bids on one auction run strictly one after another. SELECT … FOR SHARE says “I am looking at this chair, please don't move it while I look”, and it lets many transactions hold that lock at the same time. Two bidders both read price 100, both pass the “is my bid higher?” check, and both get written. The lock is still there, so the code looks safe. That is why this is a good planted bug: one word, and the protection is gone.

✓ You should see

In my run the change was a single line around line 286, in the query that loads the auction inside the bid transaction. diff prints something like 286c286, then a < line ending in FOR UPDATE (Part 4) and a > line ending in FOR SHARE (Part 5).

Your Codex may have planted a different defect, for example removing the lock clause entirely, or moving the price check outside the transaction. Any of those is fine for the game; the hunt in steps 5 and 6 works the same way.

💡 Tip

If the diff also shows other lines, with port numbers or the database name, those come from the copy step in step 1, not from the bug. Look only for the change to the locking query.

💡 Tip

Luna is the smaller, faster and cheaper model. People ask me about running Luna on Ultra effort. Ultra mostly makes it spin up sub-agents, which costs a lot and rarely helps a small model think better, so I usually stop at Extra High with Luna. A pattern I like on real work: Luna on Extra High doing the legwork, directed by a stronger model like Sol that writes the plan.

5

Ask Luna to find the bug

Send my deliberately vague question. I do not hint at concurrency, I do not name a file, I do not even say what “bug” means. This is how a real bug report from a user sounds: “bidding is broken”. We want to see what the small model does with almost no information.

✦Paste into CodexNew chat · 5.6 Luna
in part 5 there is a bug with bidding, can you find it?
✓ You should see

Within about 30 seconds, something like: “Yes. The bidding bug is in server/src/app.ts (line 283): FOR SHARE allows multiple bid transactions to acquire the lock simultaneously… Part 3 correctly used FOR UPDATE… Part 5 appears to have regressed.”

It found the bug. But look at how: it mentions Part 3. It read app.ts from another part's folder and compared the two. With a correct version sitting right next door, spotting the one-word difference is trivial. It cheated. I call this breaking out of the sandbox: we meant “look at Part 5” and it looked wherever it could.

💡 Tip

This is not the model misbehaving. It did the smart thing: when you have a known-good copy, diff against it. The lesson is about you: if you want a fair test, you have to say what is off-limits.

6

Try again, limited to Part 5

Start another New chat, still on 5.6 Luna Medium, so the model also forgets the first hunt. Send the same question, this time with a hard boundary. The capital letters are not politeness, they are emphasis; models do pay attention to shouted constraints.

✦Paste into CodexAnother new chat · 5.6 Luna
in part 5 there is a bug with bidding, can you find it? DO NOT LOOK IN ANY OTHER FOLDERS! JUST FOLDER 5!
📘 Concept: prescriptive prompt vs vague prompt

A vague prompt states the goal and leaves the method to the model: “find the bug.” It is fast to write and it lets the model use every trick it knows, including tricks you did not expect, like comparing against another folder. A prescriptive prompt adds rules about how: which folders to read, which files not to touch, which steps to take and in what order. It costs you a few more words and buys you predictability. Neither is “correct”. Use vague prompts when you want speed and do not care how the answer is reached. Use prescriptive prompts when the method matters: a fair test, a fragile production system, a security boundary, or a task where the obvious shortcut is wrong. Step 5 was vague; this step is prescriptive. Watch how the model's behaviour changes with one extra sentence.

✓ You should see

First an acknowledgement: “I'll inspect only part-5 (including its local instructions), trace the bidding flow, and run the tests documented there. I won't read any other project folders.” It reads Part 5's AGENTS.md, CONTEXT.md, README.md and app.ts, then answers similar to: “The bidding bug is in server/src/app.ts (line 283): FOR SHARE allows concurrent bid transactions to read the same auction state. Two bidders can therefore both see the same current price, pass validation, and submit identical bids. This should use FOR UPDATE… All existing Part 5 tests pass, but they don't cover two simultaneous bids, so this defect is currently undetected. No files were changed.”

Two things to notice: it reasoned about the lock from first principles this time, with no other folder to copy from, and it correctly pointed out that the test suite has a hole. “No files were changed” is also right: we asked it to find, not to fix.

💡 Tip

Even the smallest model finds it fast. In a codebase this small, FOR SHARE on a bidding query is a dead giveaway to any model that has read about database locks. Leave the bug in place: I do not fix it, and Part 6 is copied from Part 4, not Part 5, so the defect never spreads.

Key takeaways

  • Row locks decide who waits. SELECT … FOR UPDATE makes bids on one auction run strictly one after another. FOR SHARE lets concurrent transactions read the same price, so duplicate or stale bids slip through. One word, and the protection is gone.
  • Concurrency bugs hide from normal tests. The project passed every remaining test with the defect in place. Only a test that fires simultaneous bids could catch it, and the moment that test was deleted the project looked healthy.
  • Agents look wherever they can: other folders, Git history, reference copies. Say exactly what is off-limits when you want a fair test. And turn it around when you debug for real: “reproduce the bug, then look at the Git history of the related files to find where it regressed.”
  • Vague vs prescriptive: a vague prompt gives the model freedom to take shortcuts; a prescriptive prompt controls the method. Choose on purpose.
  • Give agents broad access only on dev systems. Your local Docker Postgres or Redis, or a test deployment, is fine. Never give an agent production or cloud-admin credentials.
  • A smaller model (Luna) is faster and cheaper, and good enough for focused investigation in a small codebase. Save Sol for planning and big multi-file builds.
