📘 Concept: WebSocket vs HTTP polling

Normal web traffic is HTTP: the browser asks, the server answers, the connection is done. The server cannot speak first. So if a page wants to know about a new bid, it has two options. Polling: ask “anything new?” every second or two. Simple, but wasteful, and still up to two seconds late. WebSocket: open one connection and keep it open, like a phone call instead of a series of text messages. Now either side can talk whenever it likes, so the server can push “new bid on auction X” to the page within milliseconds, and nobody has to keep asking. Our Part 3 pages refresh only after you place a bid or when the auction ends; Part 4 makes them update live, for every watcher, the instant any bid is accepted.

📘 Concept: Socket.IO

Socket.IO is a Node.js library that makes WebSockets easy to use. Raw WebSockets give you a pipe for messages and nothing else. Socket.IO adds the things every real app needs: named events (“auction:changed”), rooms (a browser joins the room for one auction and only gets that auction's events), automatic reconnection when the network drops, and a fallback to HTTP long-polling for networks that block WebSockets. It has a server part that plugs into our Fastify API and a client part that runs in the React page. It also has an official adapter for Redis, which is how the backplane in the next box is wired up.

📘 Concept: Redis and why a backplane is needed

Redis is a very fast in-memory data store that runs as its own server (for us, in a Docker container next to Postgres). It is often used as a cache, and it has a built-in messaging feature we use here. Now the problem it solves. Picture the app in production with two API replicas, two identical copies of the server behind a load balancer that spreads users across them. Bidder A's browser is connected to replica 1; bidder B's to replica 2. B places a bid, which lands on replica 2. Replica 2 pushes “auction changed” to its connected browsers, but replica 1 never hears about it, so A's page stays stale. The fix is a backplane: every replica publishes each event to Redis, and Redis forwards it to every replica, which then pushes it to its own browsers. Redis is the shared channel behind all the replicas. With a single replica you do not need it, but we build for the distributed case from the start, because retrofitting it later is painful.

📘 Concept: Plan mode vs grilling

Plan mode is built into Codex. What my answers decided, and why. Match these to your question numbers by topic:

  1. What counts as real-time success → take recommend: pages normally update within about a second, and always end up matching the database. “Eventually correct” is the real guarantee; “instant” is the goal.
  2. Which screens go live → only the auction detail page, not the homepage or search cards. Smallest useful scope.
  3. Distribution boundary → several API replicas in one region, one Redis server as the backplane. We are not designing for multiple data centres.
  4. Restrictive networks / long-polling / sticky sessions → keep it super simple, only Redis as backplane. (Long-polling is the HTTP fallback for networks that block WebSockets; sticky sessions make a load balancer send the same user to the same replica every time. Both are real production concerns, and both are out of scope today.)
  5. Where bid writes live → take recommend: bids stay on HTTP, sockets only push updates. The write path we hardened in Part 3 does not change at all; the socket is read-only notification.
  6. Redis unavailable → take recommend: keep accepting bids, Postgres is the source of truth. Live updates are a nice-to-have; accepting bids is the business.
  7. How interrupted clients recover → take recommend if it is simple. A laptop sleeps, the Wi-Fi drops; the page must catch up when it comes back.
  8. Who may subscribe → take recommend: public, read-only, same as the REST API. There is no login in this app, so there is nothing to protect.
  9. Show connection health in the UI → no. (Different from the Plan-mode answer, on purpose; I wanted even less UI here.)
  10. Prove distribution with a multi-replica demo → don't add that right now. Building and running two replicas locally is a project of its own.

6

Answer grill round 2

Round 2 is about the technical shape. The questions get more specific, and a couple of them hide important ideas. What my answers decided, and why:

  1. Recovery architecture → take recommend: the ordinary Redis Pub/Sub adapter for Socket.IO, plus an automatic HTTP refetch after every reconnect. After a disconnect the page simply asks the API for the current state once, instead of trying to replay missed events.
  2. WebSocket-only transport (no long-polling fallback) → yes. One transport, less to test.
  3. Event = notification or full state → take recommend: a small auction:changed notice (slug + bid ID), then the browser refetches the auction over HTTP. The socket says “something changed”; the API, which already has the correct, tested read logic, says what. This keeps the socket payload tiny and keeps one source of truth.
  4. Subscription rooms → take recommend: one room per auction slug. A page watching auction A never receives events about auction B.
  5. Emission boundary → take recommend: broadcast only after the bid transaction commits. If we emitted before the commit and the transaction then rolled back, every watcher would see a bid that does not exist. This connects straight back to guide 14.
  6. Should the bidder get their own event → yes. Simpler than special-casing the sender, and harmless.
  7. Redis failure at startup → don't start the API unless Redis is running. I chose this on purpose: when Redis is down, Codex notices immediately in the startup error and starts the container itself, instead of the app half-working and us hunting for why live updates are silent.
  8. Silent refresh failures → take recommend: keep the last good snapshot on screen, no error UI. A failed background refetch should not scare the user.
  9. Verification → yes to focused tests and a normal two-window check, but no multi-replica demo.
📘 Concept: pub/sub

Publish/subscribe is a messaging pattern. A sender publishes a message to a named channel without knowing or caring who is listening. Any number of receivers subscribe to that channel and get a copy of every message. The sender and receivers never talk to each other directly; the channel decouples them. Redis has this built in. In our design every API replica subscribes to the Socket.IO channel in Redis; when a bid commits on any replica, that replica publishes “auction:changed” once, Redis delivers it to all replicas, and each replica forwards it to the browsers in that auction's room. Socket.IO's Redis adapter does all of this for us behind one line of configuration.

Key takeaways

  • WebSockets keep one connection open so the server can push updates the moment they happen; polling asks again and again and is always a little late.
  • Redis as a backplane: with one API instance, Socket.IO works on its own. With several instances behind a load balancer, Redis pub/sub forwards each event to every instance, so a browser gets the update whichever instance it is connected to.
  • Prompts bias the model. A joke about 100,000 users became capacity requirements, and AGENTS.md nudged the choice of Redis. Write only what you mean.
  • Grilling vs Plan mode: Plan mode asks a few questions and then hands you a big plan to accept. grill-with-docs asks better questions round by round and records every decision in GRILL.md and CONTEXT.md.
  • Use your answers to cut scope: “detail page only”, “one Redis server”, “don't add that right now”. Real-world distributed-systems questions are important, but only when you actually need them.
  • Emit events only after the transaction commits, and let the socket carry a small “something changed” notice while HTTP stays the source of truth.
