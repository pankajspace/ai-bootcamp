📘 Concept: observability (logs vs metrics vs traces)

Observability means understanding what your running system is doing from the outside, without adding print statements and restarting it. There are three kinds of signal. Logs are text lines a service writes (“bid accepted for auction 42”): good for detail, bad for the big picture. Metrics are numbers over time (requests per second, error rate): good for dashboards and alarms, but they cannot tell you what happened to one specific request. Traces follow one request through several services and show how long each step took. Our app now has an API, a database, Redis, RabbitMQ, two workers and a payment service. Logs from seven places are useless unless you can join them. Tracing joins them. That is what Part 8 adds.

📘 Concept: trace and span

A span is one timed step with a name and a few labels, for example “auction.bid.accept, auction 42, took 12 ms”. A trace is the whole family of spans that belong to one request or one story, even when they happen in different services and minutes apart. Think of a courier parcel: each scan at a depot is a span, and the tracking page that lists every scan in order is the trace. Spans have parents and children: “handle the bid” is the parent, “run the INSERT query” is one of its children. In Jaeger you see this as an indented timeline.

📘 Concept: OpenTelemetry (OTel)

OpenTelemetry, shortened to OTel, is the open-standard library that creates spans inside your code and ships them out of the process. Ours is the Node.js version. It can wrap common libraries (HTTP, PostgreSQL, Redis) so they produce spans automatically, and it lets you create your own named spans for business steps. OTel does not store or display anything; it only produces the data and sends it to a backend you choose. Here that backend is Jaeger.

📘 Concept: Jaeger

Jaeger is a free, open-source tool that receives spans from all your services, stores them and shows them as traces in a web page. Think of it as the CCTV control room for your app: every service sends its footage to one place, and you watch the replay there. In our project Jaeger runs as a Docker container. It listens on one port for incoming spans and serves its web UI on port 16686, so you open http://localhost:16686 to look at traces. You never send data to Jaeger by hand; the OpenTelemetry library in each service does that.

📘 Concept: following one request across API → Postgres → RabbitMQ → worker

When the winning bid arrives at the API, OpenTelemetry creates a trace ID, a random identifier for this story. Every span created while handling that request records the same ID, including the Postgres query spans, which become children of the API span. The hard part comes later: the close worker runs a minute afterwards in a different process, and the notification worker in a third. For Jaeger to show one trace, the ID has to travel with the data. It is saved in the auction's database row and put into the headers of the RabbitMQ message; the worker reads it and continues the same trace instead of starting a new one. This is trace context propagation, exactly what Q2 asked for. Without it you would see three unrelated traces and match them by timestamp by hand.

📘 Concept: instrumenting code

Instrumenting means adding small pieces of code that record what the program is doing: “start a span named auction.bid.accept here, attach the auction ID, end it there”. Automatic instrumentation is when the OTel library hooks into packages you already use, such as pg or the HTTP server, and produces spans for every call without you writing a line: quick but noisy. Manual business spans are the ones you create and name after a business step (accept bid, close auction, publish event). Q4 keeps the automatic Postgres spans, turns the other automatic ones off, and adds 8–10 hand-named business spans.

📘 Concept: webhook

After the card is accepted, our API does not keep asking Mock Stripe “is it paid yet?”. Mock Stripe makes an HTTP request of its own into our API, carrying a checkout.session.completed event. A request that an outside service sends to your server when something happens is a webhook. It is signed, so the API can check it really came from Mock Stripe. The API then marks the purchase paid in the database and pushes the new state to the seller's browser over the live Socket.IO connection, so the page updates without a reload.

✓ You should see

Within about a second the seller's yellow Awaiting payment panel turns green: WINNER PAYMENT · Paid · The winning bidder completed payment. The winner's window lands back on the auction page with Payment received · Your purchase is paid.

In that blink: the payment went to Mock Stripe, its signed webhook reached our API, the API updated the purchase row in Postgres, and the seller's page received the new state over the live connection. Remember this chain. It is exactly the path Part 8's golden trace records, and in the next guide you see each hop as a span.

📘 Concept: custom instructions and model delegation

Custom instructions are a text box in Codex settings. Whatever you write there is silently added to the start of every chat, in every project. It is like AGENTS.md, but it belongs to you rather than to one repo. Delegating means the main model does not write the code itself; it hands that part to a helper agent on a different model and checks the result. 5.6 Luna is the smallest, cheapest tier. Max is the highest reasoning level, so Luna thinks longer to make up for being smaller. Planning stays on the strong model; the many lines of typing happen on the cheap one.

Key takeaways

  • Observability means you can follow one story (bid → close → notification → payment) across many services. Spans are the timed steps, a trace is the whole story, OpenTelemetry produces them and Jaeger shows them.
  • The trace ID has to travel with the data, inside the database row and the RabbitMQ message, or the story breaks into separate traces at every service boundary.
  • High signal beats more data. Decide which business spans matter, which automatic spans to switch off, and which fields are safe to record: IDs and amounts yes, names and card data never.
  • You control the grill. “Grill me shorter - just one round” worked, and so did pushing back on three slices that did not fit the work. The agent proposes, you decide.
  • Finish and commit the previous part before Codex copies it forward. Clean snapshots make the next review easy.
  • Good tests make it safe to hand the typing to a cheaper model: they catch its mistakes before you see them.
