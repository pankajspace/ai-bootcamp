7. Create Auctions & Bids Site

The warm-up is over. In this guide you throw away the practice project, read the rules file that will steer Codex for the rest of the course, add ~/codex-course/workshop as your Codex project, and get Part 1 of the real auction app running at http://localhost:5101. Every later guide starts from here.

Part 1 · run it≈ 20–30 minNo prompts, setup only

What you'll do

  • Remove the throwaway project from Codex and delete its folder from disk.
  • Read the root AGENTS.md of the workshop: the rules that shape how Codex behaves in every guide from here on.

1

Stop the throwaway site

The Vite server from guide 5 is probably still running in the throwaway chat's bottom panel. A running server holds on to its port, and leaving old servers running is the number one cause of “port already in use” errors later. So we stop it cleanly first.

In Codex, click the throwaway chat in the sidebar, open the bottom panel with the toggle bottom panel icon (top-right), click inside the terminal and press Ctrl+C. Ctrl+C is the universal “stop the program running in this terminal” key; it is not Copy on a terminal. Also close the Playwright Chrome window from guide 6 if it is still open.

✓ You should see

The Vite output stops and you get your shell prompt back (a line ending in % or $). Nothing is listening on port 5173 any more, so http://localhost:5173 now shows a “can't connect” page in Chrome. That is what we want.

💡 Tip

If you cannot find that terminal, quitting Codex completely (Cmd+Q) and reopening it stops every terminal Codex was running, including this one.

VS Code opens with the workshop folder in the Explorer. Click the AGENTS.md at the top level, directly under the folder name, not the one inside part-1-foundation. Press Cmd+K then V for the formatted preview, as in guide 6.

📘 Concept: vertical slice

A vertical slice is one thin, complete piece of a feature that cuts through every layer of the app: a bit of database, a bit of API, a bit of UI, all working together end to end. The opposite is building horizontally: finish the whole database first, then the whole API, then the whole frontend, and only see anything work at the very end. Slices are better with an agent because after each slice you can open the browser and check real behaviour, catch a wrong assumption early, and correct it before it spreads. Our AGENTS.md tells Codex to build every part in 2–4 slices and to stop after each one for you to look.

📘 Concept: PostgreSQL tables and migrations

PostgreSQL (often just “Postgres”) is the database we use. It stores data in tables: a table is like a spreadsheet with fixed columns (id, title, current_bid) and one row per record (one row per auction, one row per bid). A migration is a small, numbered script that changes the shape of the database: create a table, add a column, add an index. Migrations are saved in the project and run in order, so every developer, every test run and the production server end up with exactly the same database structure. The rule “keep DB changes in explicit migrations” means Codex must never alter the database by hand; it must write a migration file we can read and review.

✓ You should see

A section # Project Guidelines that tells Codex to:

  • work in one specific numbered part- directory, and ask if it is unclear which one
  • stay within the core stack: TypeScript, PostgreSQL, Docker Compose, Fastify (the Node.js web framework our API uses), Zod (a library that checks incoming data has the right shape), React/Vite
  • keep each part self-contained, and read the part's own AGENTS.md and CONTEXT.md before working
  • use strict types, validate all inputs, and keep database changes in explicit migrations
  • run tests after changes, and start services only through the documented npm and Docker commands

Then a section ## Workshop specific stuff that covers:

  • draw Mermaid diagrams (text-based diagrams that render as pictures) with emoji after grilling
  • “use Chrome/Edge, not the built-in browser”
  • Playwright always runs headed, so you can watch
  • screenshots go in a temp directory, not in the repo
  • grilling uses grill-with-docs, with 8–10 questions per round, 2 rounds max
  • then build in 2–4 vertical slices, confirmed with you first, stopping after each one so you can check in the browser
💡 Tip

The Chrome/Edge rule and the headed-Playwright rule already suit your API-key setup, so you do not need to edit anything. If your copy ends with a short quotation, ignore it; it changes nothing. Also open part-1-foundation/AGENTS.md: that is Part 1's own file, with its ports (API 3101, web 5101) and its commands. Each part has one, and Codex reads the root file plus the part's file together.

6

Leave “Local” and your branch as they are

The throwaway folder was not a Git repository, so you never saw these chips before. Now that the workshop has Git history, Codex offers choices about where it works. Let's look at them once so they do not confuse you later, and then leave them alone.

Click the Local chip to see the “Work in” options, read them, then press Esc to close the menu without changing anything. Next click the branch chip (master or main) to see the branch list, then press Esc again.

📘 Concept: Git branch and Git worktree

A branch is a named line of history inside a Git repo. The default branch (master or main) is where our work goes. A worktree is a second, separate folder on disk that is checked out to a different branch of the same repo. Why would you want that? Because two agents editing the same files in the same folder at the same time would trample each other. With a worktree each agent gets its own folder and its own branch, and you merge the results later. It is a powerful setup for running several Codex tasks in parallel, and I recommend it for real projects, but in this course we keep things simple and stay in one folder on one branch.

✓ You should see

Under Work in: four options: Local ✓, New local worktree, Connect Codex web, Cloud. Under Branches: your single branch with a ✓ next to it, plus “Create and checkout new branch…”. Keep Local and your current branch for the whole course.

💡 Tip

Connect Codex web and Cloud run Codex on OpenAI's servers instead of your Mac. Both need a ChatGPT sign-in, so they will not work with your API key. You lose nothing: everything in this course runs locally.

Install Part 1's packages from Codex's terminal

From now on we run the app from the terminal built into Codex, so that the app and the agent live in one window. Click the toggle bottom panel icon (top-right). The terminal opens already inside the workshop root folder. Run:

❯Run in TerminalCodex bottom panel · workshop
ls
cd part-1-foundation
npm install

Line by line:

  • ls lists the workshop root, so you can confirm the terminal is in the right place before you go deeper.
  • cd part-1-foundation moves into Part 1's folder. Every part is its own small project with its own package.json, so commands must be run inside the part, not at the root.
  • npm install reads package.json, downloads every package the project depends on (Fastify, React, Vite, the Postgres driver and so on) and puts them in a node_modules folder. The cloned repo does not include node_modules, because it is huge and can always be rebuilt from the list, so this step is mandatory on a fresh clone.
✓ You should see

ls prints AGENTS.md README.md docker-compose.yml part-1-foundation … part-8-cross-stack-debugging scripts stripe-service. npm install runs for a minute or two and ends with added … packages. A few npm warn lines about deprecated packages are normal; only red npm ERR! lines are a problem.

💡 Tip

If you run the app before installing, you get sh: concurrently: command not found. concurrently is one of the installed packages: it runs the frontend and the backend together in one terminal. No install, no package, no app. That is why npm install always comes first in a fresh folder.

8

Start Part 1

Still inside part-1-foundation, start everything with one command. Use npm start, not npm run dev. The start script does three things in order: it starts the PostgreSQL container through Docker Compose, it creates Part 1's database (auction_part_1) and runs its migrations, and only then does it launch the two development servers (frontend and API).

❯Run in TerminalCodex bottom panel · part-1-foundation
npm start
📘 Concept: Docker Compose services

In guide 1 you met Docker containers. Docker Compose is the tool that starts several containers together from one file, docker-compose.yml at the workshop root. Each entry in that file is a service: a named container with its image, its ports and its settings. Right now the only service we need is postgres. In later guides the same file also gives us Redis, RabbitMQ and Jaeger, each one a service we start with a single command instead of installing anything on the Mac. All eight parts share this one Postgres container, but each part gets its own database inside it, which is why the database is named auction_part_1.

✓ You should see

Three phases of output:

  • Docker lines as the postgres container starts. The very first time, Docker downloads the postgres:16-alpine image (a few hundred MB), so give it a minute. Later starts are instant.
  • A migration line such as 0 migrations applied or 1 migration applied. Either is fine; it just means the database is now at the structure Part 1 expects.
  • Then interleaved lines tagged [web] (the Vite frontend) and [server] (the Fastify API): [web] VITE v7.x ready, [web] ➜ Local: http://localhost:5101/, and [server] … "msg":"Server listening at http://…:3101".

Two ports, two servers: 5101 serves the pages you look at, 3101 answers the data requests those pages make.

💡 Tip

Leave this running for the rest of the guide. If you see “Cannot connect to the Docker daemon”, Docker Desktop is not running: open it, wait for “Engine running”, then run npm start again. You can stop everything any time with Ctrl+C; the Postgres container keeps running in the background, which is fine.

10

Check the API and database are connected

A pretty page does not prove the backend works; a static page would look identical. Part 1's whole purpose is a working path “React → Fastify → Postgres”, so let's prove each link in that chain with the health check endpoint.

📘 Concept: API route (endpoint), request and response

An API is the part of the backend that the frontend talks to. It has no pages, only routes (also called endpoints): URLs that accept a request and return data as a response, usually in JSON format. When the auction page loads, the React code sends a request to a route like GET /api/items, the Fastify server queries Postgres, and sends back a JSON list the page renders. A health route is a special, tiny route whose only job is to answer “I'm alive, and here is whether I can reach my database”. Every production service has one, and monitoring systems call it every few seconds.

↗Open in browser
http://localhost:5101/api/health

Why port 5101 and not 3101? The Vite dev server on 5101 is configured to forward anything starting with /api to the Fastify server on 3101. The browser thinks it is talking to one server; behind the scenes there are two. This is called a proxy, and it is why the frontend code can use simple relative URLs like /api/items.

✓ You should see

Plain JSON text in the browser: {"ok":true,"db":"ok","requestId":"…"}. ok:true means the API answered, db:"ok" means the API could reach Postgres, and requestId is a unique id the server attaches to every request for tracing. You are now at the starting point for the real build: Part 1 running from ~/codex-course/workshop, and Codex open on the workshop project. Leave both exactly as they are for guide 8.

💡 Tip

"db":"down" means the API is running but cannot reach Postgres. Make sure Docker Desktop is running, press Ctrl+C in the terminal, and run npm start again so the compose step gets another chance to bring the container up.

Key takeaways

  • The root AGENTS.md sets the guardrails for the whole course: the fixed stack, one part directory at a time, strict types, migrations for every database change, tests after changes, and npm/Docker commands only. Its workshop rules make Codex draw diagrams, use Chrome or Edge, run Playwright headed, cap grilling at 2 rounds, and build in 2–4 reviewable vertical slices.
  • Keep AGENTS.md groomed like a garden. Stale or contradictory rules make the agent drift, and you will not notice until the code is wrong.
  • Each part is its own small project with its own ports (Part 1: web 5101, API 3101; Part 2: 5102/3102, and so on) and its own database inside the shared Postgres container, so parts can run side by side without clashing.
  • npm install downloads the packages; npm start brings up Docker Compose services, runs migrations and starts both servers. In a fresh folder, install always comes first.
  • The /api/health route proves the full chain React → Fastify → Postgres is alive. Check it whenever something looks broken before blaming the code.
  • We work Local on one branch. Worktrees are for running several agents on one repo in parallel; Cloud options need a ChatGPT sign-in.
