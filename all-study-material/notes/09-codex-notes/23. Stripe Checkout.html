📘 Concept: Stripe Checkout, and why we use a mock

Stripe is a payment company. With Stripe Checkout, your server never touches a card number. Instead, the server asks Stripe to create a Checkout Session: “this customer owes $107 for this item”. Stripe returns a link to a payment page that Stripe hosts. The buyer is sent to that page, types the card there, and is redirected back to your site. Afterwards Stripe tells your server “session paid” through a webhook, a message sent to your server (explained properly in step 5). That is the real flow. Our mock Stripe service copies it exactly: Auction House creates a session on it, the winner pays on its hosted card page (port 7107), and it sends a signed checkout.session.completed webhook back to our API. Why a mock? Because it runs on your Mac with no account, no internet, no test-mode keys and no risk, and it is deliberately imperfect, so you learn what can go wrong with payments without any money moving.

Answer round 2

Back in the Define winner checkout flow chat. Round 2 is about integrity: making sure a purchase can never be paid twice, never marked paid without proof, and never gets stuck. Read the two concept boxes below before you answer; they explain the vocabulary in Q13 and Q14. These are my choices:

  • Q10 Mock service hardening: I did not understand what this question was really asking, so I asked “what do you mean?”. Codex explains in the next step. It is fine to do this during grilling.
  • Q11 Mock persistence: keep checkout sessions in memory inside the mock. Auction House, our app, keeps the durable purchase record in PostgreSQL. The provider can forget; we must not.
  • Q12 Purchase creation: create the purchase row when the winner first clicks checkout. One purchase per auction, enforced by the database.
  • Q13 Payment authority: only a signed checkout.session.completed webhook marks a purchase paid. The redirect URL the browser comes back on is not proof; anyone can type a URL.
  • Q14 Webhook replay safety: record each provider event once, and allow only one pending → paid transition per purchase.
  • Q15 Purchase states: just pending and paid. No refunds, no failed state; a declined card simply leaves it pending.
  • Q16 Checkout retries: if the winner clicks checkout again, reuse the open session instead of creating a new one. Also disable the button on click, so a double-click cannot fire two requests.
  • Q17 Return experience: after paying, go back to the auction page and reload the real purchase state from our server.
  • Q18 Service access: no API keys between our API and the mock. Keep it simple; this is a local mock.
  • Q19 Repository operation: keep stripe-service/ at the repo root, add its lockfile, and let Part 7's npm start start the mock along with the API and the web app.
📘 Concept: webhook

Normally our server makes requests and waits for answers. A webhook turns that around: another system calls our server when something happens on their side. The payment provider finishes a payment and sends an HTTP request to a URL we gave it, say POST /webhooks/stripe, with a JSON body describing the event (checkout.session.completed, which session, how much). Because anyone on the internet could send a request to that URL, the provider signs each webhook with a secret that only it and we know, and our server checks the signature before believing anything. That is why Q13 says only a signed webhook may mark a purchase paid.

📘 Concept: replay safety (idempotency)

Webhooks are delivered at least once, not exactly once. If our server is slow to answer, the provider sends the same event again. If we processed “session paid” twice, we might record two payments or two emails. A replay-safe, or idempotent, handler produces the same result no matter how many times it receives the same event. The usual recipe is exactly what Q14 asks for: store each event's unique id in a table, ignore an id you have seen before, and make the status change itself a guarded update (“set paid only if currently pending”). You met the same idea with RabbitMQ consumers in guide 21; payments are where it matters most.

📘 Concept: vertical slice

A vertical slice is a piece of work that cuts through every layer of the app at once (database, API, web page, tests) to deliver one complete, usable behaviour. Slice 1 here is “the winner can pay”: a purchases table, a checkout endpoint, a webhook endpoint, a button in the UI, and a browser test. The opposite approach, building all the database work first and all the UI last, leaves you with nothing testable for a long time. Slices give you something you can click on at the end of each one, which is also exactly what an agent needs: a clear finish line.

📘 Concept: headed end-to-end test

An end-to-end test drives the real app the way a user would: open the page, click, type, read what appears. Playwright is the tool that does the driving. Headed means the browser windows are visible on your screen, as opposed to headless, where the same test runs invisibly and faster. We run the bidding war headed because watching four users fight over one auction is the fastest way to understand concurrency, and because you will need the windows open to pay in the next guide.

Key takeaways

  • Stripe Checkout keeps card numbers off your server: you create a session, the buyer pays on a hosted page, and a signed webhook tells you it is paid. A local mock that behaves the same way (hosted page, test cards, signed webhooks) lets you build and test the whole flow with no account and no money.
  • Grilling surfaced the real design decisions before any code existed: the server owns the amount, only a signed webhook proves payment, and every webhook must be replay-safe.
  • Short answers like “take recommend” keep grilling fast. Spend your words on the exceptions (“no API keys, KISS”, “just disable the button on click”) and on honest questions (“what do you mean?”).
  • Work is delivered in vertical slices with a clear finish line, and a finished slice is something you can click, not just a green test.
  • Codex runs several chats at once. The Part 7 grill and the Drizzle goal ran side by side, one in your folder and one in a worktree.
