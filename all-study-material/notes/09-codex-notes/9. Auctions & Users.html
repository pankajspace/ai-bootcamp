Codex is building Slice 1. In this guide you learn how to review what an agent writes while it writes it: the database migration first, then the API and its tests, then the written design record. Then you open Part 2 in Chrome and send your first follow-up change.

1

Open the list of changed files

You do not have to wait for Codex to finish before you start reviewing. While it works, a line like Step 1/4 · 9 files changed +108 -56 appears under its to-do list. The +108 is lines added, the -56 lines removed. Click the words files changed. A Review panel opens on the right side of the Codex window, with one entry per file.

📘 Concept: diff

A diff shows the difference between two versions of a file, line by line. Lines Codex added are marked with + and shown in green; lines it removed are marked - and shown in red; unchanged lines are grey context. Reading diffs instead of whole files is how professional engineers review each other's work, because it shows only what changed. With an agent it matters even more: you did not type this code, so the diff is your first and best view of what actually happened.

✓ You should see

The Review panel, labelled Last Turn at the top, lists files like AGENTS.md, GRILL.md, README.md, package.json and 001_marketplace.sql, each with a mostly green diff because they are new. The file list and the counts keep growing while Codex works, so do not worry if your numbers are different from mine.

💡 Tip

Why review while it runs? Because if the very first file, the migration, is wrong, you can stop Codex with the ■ button and correct it before it builds an API and a UI on top of a wrong foundation. Ten minutes of agent time is cheap; ten minutes of agent time spent on the wrong design is not.

2

Check the database migration first

In the Review panel, click server/migrations/001_marketplace.sql. I always check the database first, because so much goes wrong at the database level, and everything else depends on it. If a column is missing or a price is stored as a decimal, the API and the UI inherit that mistake. Compare each table with your grilling answers from guide 8.

📘 Concept: SQL, CREATE TABLE, INSERT

SQL is the language you use to talk to a relational database like PostgreSQL. A migration file is just SQL statements run in order. CREATE TABLE users (…) defines a new table and its columns, each with a type (TEXT, INTEGER, TIMESTAMPTZ for a timestamp with time zone). A column like seller_user_id that points at a row in another table is a foreign key: it links an auction to the user who posted it, and the database refuses to save an auction whose seller does not exist. CREATE INDEX builds a lookup structure so that searching by that column is fast. INSERT INTO users (…) VALUES (…) adds rows; that is how the seed data gets in.

✓ You should see

Something similar to:

  • CREATE TABLE users with columns id, display_name, handle
  • CREATE TABLE auctions with slug, seller_user_id, title, category, starting_price_cents, ends_at, location, condition, description, specs and more
  • CREATE TABLE bids with auction_id, bidder_user_id, amount_cents, created_at
  • two indexes, then INSERT INTO users with 10 people (Avery Chen, Maya Thompson, Theo Brooks, Priya Shah, Jordan Lee, Sam Rivera, Nora Williams, Eli Martin, Zoe Patel, Marcus Green) and INSERT INTO auctions with the 6 catalog items

Map it back to your decisions: three tables because you asked for users, auctions and bids; ends_at as a timestamp with time zone because you chose UTC closing times; the _cents suffix on every price because you chose integer cents.

💡 Tip

My run used integer IDs (1, 2, 3…). In another run Codex used GUIDs, long random identifiers like 3f9a…. Either is fine for us. What is not fine is a price column without _cents or with a decimal type; if you see that, stop Codex and point at your Q6 answer.

3

Skim the API and the tests

Still in the Review panel, open server/src/app.ts and then server/src/app.test.ts. You are not reading every line; you are checking two things: that the routes match the slices you approved, and that the code follows the project's rules. Part 2's AGENTS.md asks for plain SQL through the pg library (the standard Node.js Postgres driver) with no ORM, and Zod for checking inputs.

📘 Concept: ORM vs plain SQL, and parameterized queries

An ORM (object-relational mapper) is a library that hides SQL behind language objects: you call Auction.find() and it writes the query for you. Convenient, but you stop seeing what hits the database, and that is exactly where our concurrency bugs will live later. So this project writes SQL directly. Direct SQL must be parameterized: the query uses placeholders like $1 and the values are passed separately, never glued into the string. If a user's search text were pasted straight into the SQL, a malicious search like '; DROP TABLE users; -- would run as a command. That attack is called SQL injection, and placeholders make it impossible.

✓ You should see

In app.ts: routes like GET /api/users, GET /api/auctions (with a Zod schema that validates the search query parameters) and GET /api/auctions/:slug, where :slug is a placeholder for one auction's URL-friendly name. All reads, no writes yet; posting and bidding are Slices 2 and 3. In app.test.ts: tests with names such as “lists the ten seeded users” and “lists and searches the six database-backed auctions”.

💡 Tip

Test names are the fastest way to check an agent's understanding. Read them as a list of sentences. If a sentence describes behaviour you did not ask for, or an important behaviour is missing from the list, you have found a gap before you have run anything.

6

Let Codex check its work in a real browser

Go back to the Codex chat and let it finish. Near the end of Slice 1 it does four things in order: resets the Part 2 database, runs the migration, runs the tests and the TypeScript type checks, and then opens the app in a real browser to click through it. I want to stress this part. An agent will tell you “done” very confidently whether the code works or not. Confidence is not evidence. The only defence is to give it tools that produce evidence: tests that pass or fail, a compiler that accepts or rejects, a browser that renders or throws errors.

📘 Concept: automated tests and type checks

An automated test is a small program that runs part of your app and checks the result: “call GET /api/users, expect 10 rows”. You run all tests with one command and get a pass/fail list in seconds, every time anything changes. A type check is different: TypeScript reads the code without running it and verifies that every value is used the way its type allows, so passing a string where a number is expected is caught before the app even starts. “Strict” TypeScript, which our AGENTS.md demands, turns on the toughest version of these checks. Tests catch wrong behaviour; type checks catch wrong plumbing. Together they are how Codex proves a slice to you, and how you will later prove your fixes to Codex.

✓ You should see

A message similar to: “Database reset, migration, all six tests, and both strict TypeScript checks pass. I'm using the Chrome control skill now because the project requires real browser verification…” followed by a Chrome window opening on the Part 2 site. In my run the browser check found a real bug: the dev server kept restarting because tsx watch (the tool that restarts the server when files change) was also watching OpenTelemetry files inside node_modules. Codex noticed the restarts, worked out the cause and fixed the watch configuration on its own. Tests alone would never have caught that; the browser check did.

💡 Tip

With an API key, Codex's built-in browser is not available. Your Codex will most likely use Playwright with Chrome instead, as in guide 6, and it may ask to install it: approve that. If it says it cannot check in a browser at all, do not worry; you do the check yourself in Step 8.

Ask for a random user on page load

The slice works, but one detail bothers me: the “10 Demo users” label at the top right is meaningless to a visitor, and every new window starts as the same first user. I want each window to start as a random user, with that user's name shown at the top right. The reason is practical: in guides 11 and 12 we open several browser windows and make them bid against each other, and we need to see at a glance who is who in each window. Send this follow-up in the same chat:

✦Paste into CodexCodex message box, same chat
randomly assign the user on page load AND put the user's name on the top right, not "10 demo users"

Notice the prompt is short, specific and names the exact text to replace. Two concrete changes, nothing vague. You do not need to re-grill for a tweak like this; grilling is for design decisions, not for every edit. This is also a change to a decision recorded in GRILL.md (Q10 said “start with the first seeded user”), so watch whether Codex updates the document as well as the code. It should.

✓ You should see

Codex replies with a short plan similar to: “I'll make the initial user random per browser tab, then keep that identity stable through navigation and reloads in the same tab; the footer switcher can still override it… replacing “10 Demo users” with the selected user's actual name. This updates the earlier localStorage decision in GRILL.md.” Then it edits a few files, mostly under web/src/, and runs the tests again before it stops. 💡 Tip

Even a small change ends with tests. “Never stop without running tests” is, in my experience, a big part of why this workflow produces code you can trust. If you ever see Codex finish an edit without running anything, ask it to run the tests before you look at the result.

Key takeaways

  • Review the database first. Tables, column types and the _cents suffix tell you in thirty seconds whether the agent understood your design; everything else is built on top of them.
  • Read diffs and test names, not whole files. The diff shows what changed; the test names show what the agent thinks the behaviour is.
  • GRILL.md (or CONTEXT.md and ADRs) keeps the grilling decisions next to the code, so Codex keeps following them in later chats, and so you can catch a misunderstanding before it spreads.
  • Make the agent prove its work: tests, type checks and a real browser check before it says “done”. Confidence is not evidence.
  • Small follow-up changes do not need grilling. A short, specific prompt that names the exact change is enough, and it still ends with the tests running.
  • On existing projects, a well-kept AGENTS.md plus the docs from grilling save you from answering the same design questions again and again.
